## 2026-09-20 07:56 — round 1

- Container: the `align` prop has no style binding — `maxWidth` and `paddingInline` are the only two — yet it must produce `margin-inline: auto | 0`. I implemented it as a plain rule on `:host([align='start'])` with no `--ds-container-*` hook and no entry in `ContainerOverridableBinding`, so unlike every other visual property it cannot be overridden per instance or from consumer CSS. If the margin is meant to be overridable it needs to be declared as a binding.
- Container: the doc says an override of `maxWidth` at `width: full` (and `paddingInline` at `gutter: none`) is a no-op with no dev warning, but not whether the hook should still be written to the host's inline style. Since the CSS at those values sets `max-inline-size: none` / `padding-inline: 0` directly, writing the hook is invisible either way; I chose to skip the `style.setProperty` entirely, matching React's `inEffect` gate, so `element.style` stays clean. A consumer reading the inline style would see a difference.
- Container: `element: section` is inert on Lit. The note says a section sets no role 'since a section is a region only when it is named', and Container has no label/heading prop, so `section` and `div` are byte-identical in output — the enum value exists only for API parity with web. The derived scenario `renders-element-section` can therefore only assert that the element renders. Either the doc should say the value is a no-op on Lit, or Container needs a label prop for the named-region case.
- Container: `element: main` sets the role through ElementInternals, which the doc itself says the test accessibility lookup cannot read, so the `main-element-is-the-page-landmark` scenario is web-only and `renders-element-main` degrades to a render assertion. Nothing on Lit verifies the main landmark is actually set — the one semantic Container has is untested on this platform. A hook the tests can read (or an exception to the no-`role`-attribute rule, as Box took) would close it.
- Container: the note that the plain `:host` rules must be the prop defaults 'before the first update' states the requirement but not the mechanism, and the obvious reading (put the defaults on bare `:host`) collides with the four `[gutter=...]` rules. I resolved it by adding bare `:host` to both media-query selector lists and relying on attribute-selector specificity (0,2,0 over 0,1,0) rather than source order, so an explicit gutter still wins. Worth stating in the doc, since ordering the rules the other way silently breaks `gutter: narrow` above 960px.
- Container: the responsive `default` gutter's breakpoints (960 / 1280) are the calm-precise resolved px, duplicated by hand in the Lit CSS exactly as in React's. The doc marks the theme-independence as a known limit but nothing in the package ties these two numbers to the token file — a theme change to layout.maxWidth.content/page leaves both platforms' media queries silently stale. A generated constant or a build-time check would catch that.
