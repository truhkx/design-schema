# Gaps reported while generating Menu for lit

Each entry is a place the doc made the generator guess. Fix the doc, re-run parse, regenerate.

## 2026-09-10 00:06 — round 1

- Menu: the trigger's aria-haspopup/aria-expanded/aria-controls are set as plain attributes directly on the composed <ds-button> host (Button has no dedicated props for them, and the web platform notes describe them on a plain <button>). This relies on the browser reflecting host-level ARIA attributes to the accessible node of a shadow-DOM custom element, which holds in current Chromium/Firefox/Safari but is a known cross-shadow-boundary ARIA nuance worth re-checking with a screen reader.
- Menu: `items` shape string is recursive (`group.items: MenuItem[]`), which literally permits a group containing another group or separator. I kept the type verbatim and render/flatten recursively so nesting doesn't crash, but the docs' guidance ('groups render a non-interactive heading row') implies groups are meant to be flat (leaf action items only) — nesting is untested against any behavior scenario.
- Menu: `iconOnly` + `triggerIcon: 'none'` is a valid prop combination per the schema but produces a trigger with no visible content (label hidden, no icon) — implemented literally since the docs don't forbid it.
- Menu: shortcuts are rendered as a display-only `<span aria-hidden="true">` rather than mapped to `aria-keyshortcuts`, since the free-text `shortcut` strings (e.g. '⌘S') don't match the `aria-keyshortcuts` value syntax the spec would require; this matches the docs' 'display-only' framing but means shortcuts are entirely invisible to assistive tech rather than announced.
- Menu: no design token covers the typeahead reset delay, so I used a plain 500ms JS constant (APG's common convention) rather than a token — flagged since the theme rules forbid literal timings elsewhere.
- Menu: default Storybook args render the menu closed (only the enum-value and content stories force `open: true`) to avoid a focus race in the auto-generated behavior tests — opening triggers an async `focusItem` chain (waits on `updateComplete` before calling native `.focus()`), which could otherwise race with a synchronous `el.focus()` call in a freshly mounted test element.
- Could not execute the Vitest suite in this session (shell command required interactive approval that wasn't granted); `Menu.test.ts` is written and `tsc --noEmit` passes, but the 13 behavior-scenario tests are unverified at runtime.

## 2026-09-16 06:45 — round 1

- Menu: platforms.web.attributes asks for aria-haspopup=menu and aria-controls on the trigger, but ds-button only forwards `expanded` to its inner <button>, and an IDREF can't cross from ds-button's shadow root to the popup anyway. The trigger gets `.expanded` only; aria-haspopup and aria-controls are not exposed. Button's schema needs a haspopup prop, or the Lit notes should waive them.
- Menu: the open-change reasons don't cover Tab, focus leaving the menu or the window losing focus, although overlay.dismiss lists focus-out and the keyboard table says Tab closes. I used reason `outside` for all three.
- Menu: open-change `fires` lists `controlled`, but the reason says the menu never raises it itself. I chose to fire nothing when the `open` property changes.
- Menu: there is no defaultOpen, so a menu can only start open in controlled mode, and a controlled menu with nothing flipping `open` never closes. Stories with `open: true` (including Keyboard) flip `open` from open-change as a parent would. The docs should say whether the Keyboard story is controlled or add a defaultOpen.
- Menu: when a controlled menu handles Escape, Tab or a chosen item, focus returns to the trigger right away, even if the parent never flips `open`. The spec doesn't say whether focus restore waits for the property change.
- Menu: the `anchor` shape `RefObject<HTMLElement | View>` has no Lit counterpart. I typed it `HTMLElement | undefined` (the element itself).
- Menu: the anatomy lists `popup` and `list` as separate parts. Only the web notes say they are one node. I followed web: a single role=menu element with data-part="popup" and part="popup list". The Lit notes should say this too.
- Menu: the minWidth, maxHeight, border, borderWidth, shadow, radius, fontFamily, fontSize, lineHeight, layer and enter bindings name no part. I applied them to the popup. typeaheadReset is read at runtime from the computed --ds-menu-typeahead-reset and parsed as a CSS time.
- Menu: overlay.layer says `popover` while the `layer` style binding is layer.dropdown. I used --layer-dropdown for the position: fixed fallback's z-index; the Popover API path uses the top layer.
- Menu: groupLabel padding has no binding. I reused the itemPaddingBlock and itemPaddingInline hooks so the label lines up with the items.
- Menu: popupOffset is applied as a margin on the side facing the trigger (data-side), and the flip check reads the computed margin. The spec doesn't say how the offset works with the flip.
- Menu: the item shape is recursive but groups hold only action items, so nested groups and separators inside a group are dropped silently, with no dev warning. The spec doesn't say whether to warn.
- Menu: the only dev warning the doc asks for is iconOnly with triggerIcon none (issued once). The old checks for a missing label, empty items, and anchor without controlled open were dropped because the doc doesn't ask for them.
- Menu: behavior scenario `a-disabled-item-does-nothing` needs a forced click in the browser test, because Playwright won't click an aria-disabled element.

## 2026-09-17 10:38 — round 1

- Menu: keyboard rule for Tab says focus moves to the tabbable after/before the trigger, but on Lit the popup sits after the trigger in shadow-tree order; a controlled menu whose parent does not flip `open` synchronously leaves the popup visible, so the browser's Tab from the trigger lands back on the roving item. Chose: park focus on the trigger (or anchor) and let native Tab move on; uncontrolled hides the popup immediately, controlled relies on the parent flipping `open`.
- Menu: with `anchor`, the spec does not say whether a pointerdown or focus move onto the anchor counts as outside/focus-out. Chose: the anchor stands in for the trigger (as the Tab rule says), so neither closes the menu; the consumer toggles `open` from the anchor.
- Menu: `iconOnly` + `triggerIcon: none` must warn in development, but with `anchor` there is no trigger to press. Chose: no warning when `anchor` is set.
- Menu: after focus-out/outside the spec is silent on focus restore; controlled close from the parent (reason not raised by the menu) is also unspecified. Chose: restore to trigger for trigger/escape/action, and additionally whenever focus is still inside the popup when it hides (so it is never dropped to body); never for outside/focus-out/tab-out.
- Menu: when the menu is already open and focus is on the trigger, the keyboard table lists no Escape rule and ArrowDown/ArrowUp only as 'opens'. Chose: Escape on the trigger does nothing; ArrowDown/ArrowUp on an open menu focus the first/last item.
- Menu: `window` blur also produces a host `focusout` with a null relatedTarget, so a controlled menu whose parent does not flip `open` synchronously can see two `open-change` (focus-out) events. Not deduplicated.
- Menu: `minWidth` computed `calc(var(--space-20) * 2.5)` must also be at least the trigger width; Lit writes `max(calc(var(--ds-menu-min-width) * 2.5), <trigger width>px)` inline on the popup, since the trigger width is only known at runtime.
- Menu: `maxHeight` says 'the viewport minus the gutter' without naming the gutter token. Chose `layout.gutter` (2× for both edges).
- Menu: `part` attributes (`item`, `separator`, `group`, `groupLabel`, `itemIcon`, `itemShortcut`, `trigger`) are kept on shadow elements alongside `data-part`, though the overrides contract says no ::part is exposed for styling; the lit notes only specify `part="popup list"`.

## 2026-09-21 07:40 — round 1

- Menu: the `part` contract contradicts itself — the package convention says `part` and `data-part` carry the anatomy names, while the Lit notes say `part="popup list"` is "the only `part` attribute". I followed the notes and removed `part` from trigger, group, groupLabel, item, itemIcon, itemShortcut and separator, which silently breaks any consumer styling `ds-menu::part(item)` today. The doc should state that the removal is intended.
- Menu: the doc says the menu "uses real focus (not aria-activedescendant)" and has "one roving tabindex" but never says which wins when they diverge — when focus reaches an item without the component moving it (a click, a screen reader, the keyboard gate's own `focusAt`). Reading the roving state as the origin makes every arrow key move from the wrong item, which is what failed the ArrowDown/next gate here. Chose: DOM focus is authoritative for arrows, Home/End, typeahead and activation, and the roving tabindex follows focus through a `@focus` handler on each item. This should be stated for every roving-tabindex component, not just Menu.
- Menu: the Tab rule says the menu "sets every item to tabindex -1" when a controlled parent keeps the popup shown, but the roving tabindex always has to put a 0 somewhere (a null active item means "first item is the entry point"). Chose a separate suppression state, so after Tab no item is tabbable at all and the next open starts from the first item.
- Menu: the doc does not say whether a disabled item may hold focus (it keeps `aria-disabled`, stays in the DOM, and the package convention keeps disabled elements focusable). Chose: a click can focus it, and an arrow pressed while it holds focus goes to the first (ArrowDown) or last (ArrowUp) enabled item rather than to its neighbour.
- Menu: `popupOffset` and `gutter` are "read in px from the popup's resolved hook" with nothing said about an unresolvable value (no token stylesheet — every bare test page). Chose 0 for both, so the popup sits flush against the trigger and can be clamped to the viewport edge, rather than hard-coding the token's current value.
- Menu: the inline-shift rule says the popup "is shifted inline instead so it stays `gutter` away from the side edges" but not what happens when the popup is wider than viewport − 2 × gutter, where both constraints cannot hold. Chose the leading edge to win (clamp to `gutter` on the start side).
- Menu: `placement` says start/end "resolve against the layout direction" without saying where the direction is read from. Chose `getComputedStyle(trigger ?? anchor).direction`, so a menu inside an RTL subtree of an LTR page resolves against its own trigger, not the page.
- Menu: with `anchor`, focus that would return to the trigger "returns to the element that had focus when the menu opened" — but not what to do when nothing had focus (ActionSheet's wide presentation opens the menu from a fresh render). Chose to leave focus alone rather than fall back to the anchor, which need not be focusable.
- Menu: the doc says a window blur and the focusout it causes are one focus loss, but not what to do with the focusout the menu's *own* Tab parking causes. In a controlled menu whose parent does not flip `open` synchronously that would report a second close (`tab-out` then `focus-out`). Chose to count the Tab as the focus loss so only `tab-out` is reported.
- Menu: `platforms.lit.reflect` lists `open`, but an uncontrolled menu's state lives in internal state and the property stays undefined, so the `open` attribute never appears and `ds-menu[open]` selectors only ever match controlled menus. Reflecting the real state instead would make the attribute write back into the property and turn every menu controlled. The doc should say which it wants.
- Menu: `minWidth`'s runtime floor needs a value CSS can read, and the bindings list has no hook for it. Added a platform-private `--ds-menu-trigger-width` (`0px` in `anchor` mode) that the `min-inline-size` rule maxes against, mirroring web; it is not an overridable binding and is not in the overrides type.
- Menu: `maxHeight` uses `layout.maxWidth.prose` — a width token — as a block-size cap, and `phoneBreakpoint` reuses the same token. Implemented verbatim, but the binding name and token disagree about axis, so an adopter retheming prose width silently changes how tall every menu can be.
- Menu: `anchor`'s shape is `RefObject<HTMLElement | View>`, which has no Lit counterpart, and the notes only say it is "a property (the element)". The `AnchorPositioned` story therefore wires it with the `ref` directive pointing the menu at its own parent element; the doc gives no Lit idiom for handing an element to a property before first render.
- Menu: story parity with React means the four `Placement*` stories now render *closed* (React's carry no `open`), so the component page shows no popup for any placement value on either platform — the one rule they exist to illustrate is the one they do not show. I dropped Lit's extra `DisabledItem` story for the same parity; the disabled row still appears in `Default` via the shared item list.
- Menu: the generated behavior test `a-disabled-item-does-nothing` cannot pass as generated — the doc requires disabled items to be announced with `aria-disabled="true"`, and Playwright's actionability check then refuses to click them (`element is not enabled`). The hand-written `Menu.test.ts` uses `{ force: true }`; `tools/behavior_tests.ts` has no way to express that, so this scenario fails the behavior gate on every regeneration. This is pre-existing, not introduced by this round.
- Menu: Escape pressed on the trigger while open is specified for its reason and focus, but not whether the event should stop bubbling (a Menu inside a Dialog would otherwise close both). Chose preventDefault + stopPropagation, matching the in-popup Escape and web.
- Menu: the groupLabel row has no padding binding of its own; I reused the `itemPaddingBlock` and `itemPaddingInline` hooks so the label lines up with the items, which means overriding item padding also moves every group label.
- Menu: `typeaheadReset` is read at runtime from the popup's resolved hook, with nothing said about an unresolvable value. Chose to clear the buffer after each keypress, so typeahead degrades to single-character matching rather than accumulating forever.

## 2026-09-23 14:34 — round 1

- Menu: the Behavior section says the four Placement* stories render open on every platform, but the React stories (Menu.stories.tsx) render them closed with only `placement` as an arg, so 'story parity: same args' and the Behavior rule contradict each other. I followed the Behavior rule and gave Lit's Placement* stories `open: true`; React needs the same change, or the doc should say which rule wins.
- Menu: popupOffset is described as the gap 'on the side facing the trigger', read in px at open and reposition. The doc doesn't say whether the gap goes into the computed top/left or is a CSS margin. I compute top from the trigger rect plus the offset in JS and removed the margin rules, so the gutter clamp and the offset go through one calculation.
- Menu: gutter must be 'kept from the block edges too', but the doc doesn't say whether the flip check counts gutter or only the viewport edge. I flip when popup height + offset + gutter doesn't fit and the other side does, and clamp top to [gutter, viewport height - gutter - height] in either case.
- Menu: the rule for a popup wider than the viewport minus 2 × gutter ('the leading edge wins, clamped to gutter on the start side') doesn't say what that means in right-to-left layouts. I pin the right edge at gutter in right-to-left and the left edge in left-to-right; max-inline-size calc(100vw - 2 × gutter) makes the case rare anyway.
- Menu: the `open` Lit property is `boolean | undefined` with reflect. The doc says only the controlled property reflects, but not what setting `open = false` writes: the attribute disappears, so `ds-menu[open]` can't tell a controlled-closed menu from an uncontrolled one. I kept that behaviour.
- Menu: the example stories carry meta.args defaults (triggerVariant ghost, placement bottom-start, triggerIcon chevron-down) alongside their `given`. 'Exactly its given as args' and 'restates the props it relies on being at their default' pull in different directions; I left the merge as it is, matching React.
