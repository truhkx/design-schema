## 2026-09-17 04:36 — round 1

- Container: anatomy names one part, `column`, and web/Lit mark it with data-part="column", but the rn notes don't say whether the root should also carry `testID="Container.column"`. The root is the part and a View takes only one testID, so I kept `testID="Container"` and added no part testID, as Box does for `surface`.
- Container: the paddingInline description says the responsive `default` gutter measures the viewport. On native, useWindowDimensions gives the window width, not the width of the parent, while SwiftUI measures the container's own width with GeometryReader. So a nested `gutter: default` Container inside a narrower parent picks its gutter from the window width on RN but from its own width on SwiftUI. I used the window width, as the rn notes say.
- Container: the rn notes say `width: 100%` together with alignSelf, but not what happens inside a row-direction parent, where a 100% width combined with alignSelf crosses axes. I applied both as written.
- Container: the Default story's `children` isn't given. The spec says string children are drawn inside a Text but gives no Default text, so I used `<Text>Container content</Text>`.
- Container: all 11 scenarios only check that it renders. None checks maxWidth, alignSelf or the gutter breakpoints, so the style contract isn't covered by tests on native.

## 2026-09-20 08:35 — round 1

- Container: the spec's `element` prop is web/Lit-only and the `main-element-is-the-page-landmark` behavior is scoped `platforms: [web]`, so on RN there is no way to express it — no prop, no test. Omitted entirely (as Box does) rather than accepting a prop that does nothing.
- Container: `align: start` is specified for web as `margin-inline: 0` on BOTH sides so the column never picks up an asymmetric margin. RN has no margin here and the schema maps it to `alignSelf: 'flex-start'`, but `alignSelf` only positions the box — it carries none of the 'symmetric margin' intent, and in a parent narrower than the cap `center` and `start` are visually identical. Implemented the documented mapping; the two props' equivalence on narrow viewports is untestable and untested.
- Container: the responsive `default` gutter is specified against 'the active theme's maxWidth tokens', unlike web/Lit which bake the calm-precise px into media queries. So under a non-default theme RN switches gutters at different widths than web — a real cross-platform divergence the docs note for web ('a known limit') but never state as a native/web mismatch. Followed the RN platform note (live theme tokens) rather than matching web's frozen breakpoints.
- Container: no `given` in the 11 behavior scenarios varies the viewport, so the entire responsive `default` gutter (three bands, two boundaries) and the inclusive-`>=` rule have no coverage — `renders-gutter-default` only asserts the tree is non-null at jsdom's default window width. Wrote the scenarios exactly as listed and added none; the branch is unverified by the suite.
- Container: the overrides contract says an override of `paddingInline` 'replaces the value at every viewport width, including the whole responsive default gutter'. Resolved the override before the responsive branch so it wins at all three bands, but the schema never says whether an override should also win over an explicit `gutter: narrow`/`wide` — assumed yes (it replaces the binding's default token regardless of which enum value selected it), and only `gutter: none` suppresses it.
