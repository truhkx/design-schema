The schema has reserved the platform id `swiftui` since the first cut (`schema/component.ts` lists `web`, `lit`, `rn`, `swiftui`, `compose`). This page turns the reservation into a plan and the plan into the first artifacts: `prompts/conventions/swiftui.md`, `prompts/templates/swiftui.md`, and a `platforms.swiftui` block in every component doc. Generation for iOS then works exactly as it does for the three existing platforms: parse builds `generated/prompts/<Name>.swiftui.md`, `generate` asks the model for one file, the gates say yes or no.

## What "native iOS" means here

SwiftUI, not UIKit. Every component is a `struct <Name>: View` in a Swift package, styled from the same tokens, with the same anatomy, props, events and copy as the other platforms. UIKit appears only where SwiftUI has no API (`UIAccessibility.post` for announcements is now `AccessibilityNotification.Announcement`; `UIPasteboard` for DataGrid copy). No third-party dependency at all — the iOS equivalent of the react-native-svg rule is stricter, because SwiftUI's `Path` draws the Icon glyphs itself.

Toolchain: the latest stable Xcode and Swift (Xcode 26.6 / Swift 6.3 today; Xcode 27 / Swift 6.4 ships with iOS 27 on 2026-09-14 and becomes the target the week it lands, per the currency policy). Deployment target: the current major minus one (iOS 26 once 27 ships), reviewed each September. Swift 6 strict concurrency on; every view is `Sendable`-clean by construction (value types, `@MainActor` where UIKit is touched).

## Package layout

```
packages/swiftui/
  Package.swift                     // products: DesignSchemaTokens, DesignSchema
  Sources/DesignSchemaTokens/       // generated by the token build — never edited
    CalmPrecise.swift               // enum CalmPrecise { enum Light { static let colorBackground: Color … } enum Dark … }
    WarmFriendly.swift
    TokenRef.swift                  // enum TokenRef: String, CaseIterable — every token name
    Theme.swift                     // struct Theme { subscript(TokenRef) }, EnvironmentValues.dsTheme, .dsTheme(_:) modifier
  Sources/DesignSchema/
    <Name>.swift                    // one file per component: the View, its option enums, its Overrides type
    Icon+Paths.swift                // the 16×16 path table, generated from the same source as Icon.tsx
    Support/                        // FocusScope engine, Portal (overlay window), Announce, ReducedMotion
    Support/SVGPath.swift           // SVG path data → Path, for the glyph table above
    Support/Testing.swift           // DSHost: the harness the generated behavior cases drive
  Tests/DesignSchemaTests/          // Swift Testing: the theme table, the icon snapshots
  Tests/DesignSchemaTests/Generated/ // <Name>BehaviorTests.swift, derived from the docs' `behavior` blocks
  Tests/DesignSchemaUITests/        // XCUITest: performAccessibilityAudit per component, keyboard on iPad
apps/ios-gallery/                   // the Storybook equivalent: one screen per component, mode + theme switcher
  project.yml                       // XcodeGen: the app bundle and UI-test host the gates generate on the runner
tools/icon-paths.json               // the glyph table itself — the source Icon+Paths.swift is generated from
tests/icon-snapshots/               // one PNG per glyph, rendered from that table by Playwright
```

Tokens: `tokens/build.mjs` has a `swift` platform. Colors become `Color(red:green:blue:opacity:)` from the hex; dimensions `CGFloat` (points — the px values are read as pt, which is the RN convention too); durations `TimeInterval` (seconds, so the DTCG milliseconds are divided); easing `Animation.timingCurve(x1,y1,x2,y2)`; font families a `FontFamilyToken` whose `Font.Design` comes from the stack's first system generic (`system-ui` → `.default`, `ui-monospace` → `.monospaced`) and which also keeps a real family name when the stack starts with one; shadows a small `ShadowToken` struct; `layer.*` are `zIndex` doubles. Light and dark are two static enums; `Theme` resolves by `colorScheme` at render time so a component reads `theme.colorBackground` and never checks the scheme itself.

The platform is formatted rather than built — SwiftUI wants one file per theme carrying both modes, so each mode's enum is rendered in memory and the pair is assembled into `packages/swiftui/Sources/DesignSchemaTokens/<ThemeName>.swift`, beside a generated `TokenRef.swift` (one case per dotted name, plus the `Theme` extension that gives each one a named accessor) and `Themes.swift`. `tokens/__tests__/swift.test.ts` checks that each theme's Swift file lists exactly the tokens `json/tokens.{light,dark}.json` do, which is the only check that runs on Windows.

Overrides keep the contract: `overrides: [Name.Binding: TokenRef] = [:]`, where `Binding` is a per-component enum of its overridable bindings (locked ones are not cases). No `.modifier`/style escape hatch; the only per-instance styling surface is the override map.

## Mapping the schema to SwiftUI

Props are `init` parameters with the doc defaults; `content` props are `@ViewBuilder` closures (`primary: () -> Primary`); `array`/`object` props are `struct`s named from the shape (`DataGridColumn`, `FeedItem`); `function` props are closures. Enum props are nested `enum`s with `String` raw values matching the doc.

Events are closures named from the platform mapping (`action`, `onChange`, `onOpenChange`) and controlled/uncontrolled pairs become the SwiftUI idiom: a `Binding<T>` parameter for the controlled form and a `default…` initial value for the uncontrolled one, exactly as `value`/`defaultValue` on web.

Accessibility maps the a11y block onto SwiftUI modifiers and the keyboard block onto iPadOS hardware-keyboard handling:

| Doc concept | SwiftUI |
| --- | --- |
| role / accessible name | `.accessibilityElement(children:)`, `.accessibilityLabel`, `.accessibilityAddTraits(.isButton/.isHeader/.isSelected/.isModal…)` |
| aria-valuenow / valuetext | `.accessibilityValue(Text)` and `.accessibilityAdjustableAction` for ranges |
| expanded / checked / selected | `.accessibilityAddTraits`/`.accessibilityRemoveTraits`, `.accessibilityValue("expanded")` where no trait exists |
| live region / announcements | `AccessibilityNotification.Announcement(text).post()` |
| aria-hidden / decorative | `.accessibilityHidden(true)` |
| focus management (FocusScope, return focus) | `@AccessibilityFocusState` for VoiceOver focus, `@FocusState` for keyboard focus |
| keyboard table | `.focusable()` + `.onKeyPress(.upArrow)` etc. on iPadOS/Catalyst; Escape = `.onExitCommand`; Tab order via `.focusSection()` |
| roving tabindex | one `.focusable()` container with `@FocusState` moved by the arrow handlers |
| target-24px / 44px | `size.target.min` / `comfortable` tokens as `frame(minWidth:minHeight:)` plus `.contentShape` |
| reduced motion | `@Environment(\.accessibilityReduceMotion)` |
| contrast pairs | unchanged — the contrast gate checks tokens, not platforms |
| Dynamic Type | font-size tokens through `@ScaledMetric` so type scales; layouts use `ViewThatFits` where the docs say "collapses below the prose width" |

Overlays: Dialog and AlertDialog are `.fullScreenCover`/`.sheet` with the system's own scrim on phones and `.popover` on iPad where the doc says so; BottomSheet is `.sheet` with `.presentationDetents`; ActionSheet is `.confirmationDialog`; Menu is `Menu`; Popover is `.popover(attachmentAnchor:)`; Tooltip has no native pattern and, as on RN, becomes `accessibilityHint` plus long-press; Toast is a custom overlay in a top-level `ZStack` at `layer.toast`. Table/DataGrid/TreeGrid render with `Grid`/`LazyVGrid` and `ScrollView`, never `List` (its row semantics fight the explicit-role rule). Rows stay data.

Testability hook: `.accessibilityIdentifier("<Name>")` on the root and `"<Name>.<part>"` on parts — the `data-part` equivalent, and what XCUITest and the accessibility audit query.

## Gates, and the Mac problem

Parse, contrast and the keyboard-spec derivation run anywhere (they read docs). The typecheck and behavior gates for `swiftui` need SwiftUI, and SwiftUI compiles only on macOS: the swift.org Windows toolchain has Foundation but no SwiftUI module, so `swift build` on the Windows machine cannot even typecheck a View. Two options, both in the plan:

- **Remote gate (default).** `generate` writes the Swift file, commits it on a `gen/swiftui/<Name>` branch and pushes; a GitHub Actions workflow on `macos-26` (free minutes on a public repo) runs `xcodebuild -scheme DesignSchema -destination 'generic/platform=iOS' build`, `swift test`, and the XCUITest accessibility audit on a simulator, then uploads `gates/<Name>.swiftui.json`. `generate` polls with `gh run watch` and feeds errors back to the model as round 2, exactly like the local typecheck loop. Latency is minutes per round, so the swiftui phases run as batches (`-Platform swiftui` waits on a whole phase's runs, not one target at a time). Job 400 built the workflow; job 430 built the client, which is `tools/swiftui_gate.ts`:

`start()` makes a git worktree at HEAD — the main checkout is never touched, so a batch's branches cannot collide with each other or with what the generator is still writing — copies the working tree's Swift inputs into it (`packages/swiftui`, `apps/ios-gallery`, `tools/icon-paths.json`, `tests/icon-snapshots`, `generated/keyboard`, the workflow itself: what the gate compiles is what is on disk, the way a local `tsc` judges the working tree), commits, force-pushes `gen/swiftui/<Name>` — the generator owns that namespace — and dispatches the workflow with `-f target=<Name>`, finding its run by the sha it just pushed. `waitAll()` watches a single run with `gh run watch` and polls a batch's runs together, then downloads each `gates/<Name>.swiftui.json` and turns `{ build, tests, audit }` into the same `GateResult` list `tools/checks.ts` produces, so a `swift build` error becomes a fix round with no special case anywhere in `generate`. A section the workflow marks `skipped` — the XCUITest audit, when the gallery app or the simulator never got far enough to run it — is printed and never counted against a round. A component that passes is folded back into the main checkout and its branch deleted; one that fails keeps its branch, because that is the only copy of the code the runner rejected.

The workflow itself (job 440) answers in three parts. `build` is `xcodebuild -scheme DesignSchema -destination 'generic/platform=iOS' build` — the typecheck for the platform the code is actually for, not for the macOS host `swift build` would compile against — plus the host build of the tests and the gallery app. `tests` is `swift test`, the whole Swift Testing suite. `audit` is `XCUIApplication().performAccessibilityAudit()` on the target's gallery screen, and beside it the doc's own `keyboard` rules, pressed on an iPad simulator with a hardware keyboard attached; a rule that fails is a `tests` failure, because it is behavior, and only the audit's findings are `audit` issues.

Two things make that last part work. The UI tests need an app bundle to attach to, which SwiftPM does not produce, so the runner generates an Xcode project with XcodeGen from `apps/ios-gallery/project.yml` — the `.yml` is the reviewable source and the `.xcodeproj` is build state, which is what lets the whole thing be written on a machine that cannot open Xcode. And the rules have to reach a process on a simulator: `tools/keyboard_tests.ts` writes the `keyboard` block out as `generated/keyboard/<Name>.json` beside the Playwright specs it derives from the same data, `tools/swiftui_gate.ts` ships that file with the branch, and the workflow hands it to the test as `TEST_RUNNER_DS_KEYBOARD_SPEC`. A finding comes back the same way in reverse: the only channel from the simulator to the host is the xcodebuild log, so every failure the test raises is prefixed `DS-AUDIT:` or `DS-KEYBOARD:` and `tools/swift-gate-report.mjs` splits the log on those markers. A rule whose starting state the test could not establish is printed as a skip and counted as neither — a gate that cannot check a rule must not claim it passed.

What stays local for `swiftui` is what reads docs: parse and contrast. `generate` runs those as the preflight and per round, exactly as it does for the other platforms, and asks the Mac for the rest.
- **Local Mac.** A Mac (mini or a runner on someone's laptop, registered as a self-hosted GitHub runner) makes the same workflow near-instant; nothing in the scripts changes. This is the recommendation once the phase count makes CI minutes annoying.

The behavior scenarios in that suite are derived, not written (job 460). `tools/behavior_tests.ts` — the same script that writes the web, Lit and React Native cases — has a `swiftui` emitter that turns each scenario into a `@Test` in `packages/swiftui/Tests/DesignSchemaTests/Generated/<Name>BehaviorTests.swift`: the component is built with the scenario's `given` props inside a `DSHost` (`Sources/DesignSchema/Support/Testing.swift`), which lays it out in an offscreen window and reads the accessibility tree the platform built from it. The `when` is performed through the identifiers the conventions already require — a tap is the element's activate action on `<Name>.<part>`, falling back to `<Name>` because `.accessibilityElement(children: .combine)` folds parts into the root; a key goes through `.dsOnKeyPress`, which installs SwiftUI's own `.onKeyPress(keys:)` *and* registers the handler with the host, because nothing in a `swift test` process can synthesize a key event. The `then` is read back off that tree: identifier presence for `renders`, the root's label for `name`, any element's label/value/hint for `text` and `copy`, traits for `role` and `selected`, `.accessibilityValue` for `expanded`, the enabled flag for `disabled`, and a recorded payload for `event` (a `DSEventLog` hands the initializer a spy closure per event and reflects what it was called with, since Swift cannot take a `vi.fn()` that fits any signature).

Two things it deliberately will not do. Focus is unreachable — a hosted view cannot move or observe `@FocusState` — so every `focusable`/`focused` scenario is emitted as `@Test(..., .disabled("…"))` naming the iPad keyboard gate that does check it, and the same goes for typing and for a state the conventions give no accessibility spelling (`checked`). And a required `array` prop has no literal this generator can synthesize — there is no `meta.args` on this platform, only the initializer's own defaults — so the scenarios of a DataGrid or a Listbox are skips until the docs describe a row literal. A skip is a line in the report, not a pass. These files are also the one derived artifact in the repository that is *committed*: the macOS runner never runs `pnpm install`, so it cannot derive them, and `pnpm gates:behavior:check` in the ordinary CI is what stops them drifting from the docs.

One gate is neither a typecheck nor a behavior scenario: **Icon**. Its glyphs are authored once, as SVG path data in `tools/icon-paths.json`, and each platform draws that data with its own renderer — the browser's SVG, react-native-svg, and now `Support/SVGPath.swift` building a SwiftUI `Path`. Nothing about "the same `d` string" guarantees the same picture, so `pnpm icons:snapshots` renders every glyph with Playwright at 16 pt into `tests/icon-snapshots/`, and `IconSnapshotTests` renders the SwiftUI side through an `ImageRenderer` at the same size and compares: a pixel counts as different when a channel is off by more than 32/255, and at most 2% of them may be. That is loose enough for two rasterizers' antialiasing and tight enough that a misread arc or relative coordinate fails. The check runs in the `swiftui-gates` workflow, where SwiftUI exists; `pnpm icons:check` (the generated Swift matches the table) and `pnpm icons:snapshots:check` (the PNGs match the table) run in the ordinary CI on Linux.

`swift-format` runs locally on Windows via the swift.org toolchain. The no-literals gate needs no Mac either: `tools/lint_literals.ts` has a Swift matcher, so `pnpm lint:literals` walks `packages/swiftui/Sources/DesignSchema` (subdirectories included) alongside the three `src` trees. It flags a bare number anywhere in the argument list of `.padding(`, `.frame(`, `.cornerRadius(`, `.lineSpacing(`, `.font(.system(size:`, `Color(`, `.opacity(`, `.animation(` or `.zIndex(` — `0`, `1`, `2` and fractions like `0.5` are allowed, as on the other platforms, and anything else needs the same `// literal-ok: <reason>` mark. The matcher tracks open parens across lines, so the usual multi-line `.frame(\n    width: 44,\n)` is caught too.

## Phases

The same composition order as `regen.ps1`, so a component never precedes what it composes: Primitives (Icon, Text, Heading, Box, Stack, Container, Landmark) → Core (Button, Link, Input, Form, Card, Divider) → Controls (Checkbox, Switch, RadioGroup, Fieldset, Alert, Disclosure, Breadcrumb, Meter) → Focus (FocusScope, Tooltip, Toast) → Overlays → Selection → Numeric → Rows → Grids → Streams. Icon first because its glyph table is a code-generation job of its own (SVG path data → `Path` commands) and everything else composes it.

Estimated cost mirrors the other platforms (Sonnet: ≈ $20 per large phase, $2–3 per component), plus CI wall-clock rather than dollars for the remote gate.

## What is done today

The rest of this page's promises are represented in the repository by: `prompts/conventions/swiftui.md` (the package conventions the model reads), `prompts/templates/swiftui.md` (the generation prompt), `platforms.swiftui` in all 51 component docs with `swiftui` event names (Button and Link map `onPress` to `action`, the SwiftUI idiom; every other event keeps its web name) — which is enough for `pnpm parse` to emit 51 SwiftUI prompts, verified.

Jobs 400 (package skeleton), 410 (Swift tokens), 420 (glyph table), 430 (the generator's `swiftui` platform and its gate client) and 440 (the workflow's three halves) have landed. `node tools/generate.ts --platform swiftui --component Button` runs the whole loop: prompt, model, doc gates, branch, workflow, report, fold. What none of it can do on the Windows machine it was written on is finish — there is no `gh`, no remote and no Mac, so the run stops at the gate's preflight with that message rather than pretending. Everything about job 440 that can be checked without a Mac has been: the workflow and `project.yml` parse, the iPad the job boots is chosen by `tools/swift-sim.mjs` and unit-tested against a recorded `simctl` listing, and `tools/swift-gate-report.mjs` is tested against the logs each step tees — but the first run of `xcodebuild` on a real runner is still the first run of `xcodebuild` on a real runner. The first round trip, and with it the first generated SwiftUI component, needs a repository with an `origin`.
