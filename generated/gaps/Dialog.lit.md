## 2026-09-09 23:11 — round 1

- Dialog: the schema names the title prop `title`, but `HTMLElement` already defines `title` as the native tooltip attribute (per this package's own rule for `role`/`title`). Renamed the JS property and attribute to `heading` (not just the JS name, since leaving the HTML attribute as `title` would trigger native browser tooltips on hover). The `initialFocus` enum value `'title'` was kept as-is since it's a literal, not a property name.
- Dialog: the 'action' close reason (distinct from escape/close-button/scrim) has no described trigger mechanism for the Lit platform. Inferred it from native <dialog> semantics: whenever the inner <dialog> fires its native `close` event without ds-dialog having driven it via the `open` property (e.g. a slotted form submitted with `formmethod="dialog"`), ds-dialog reports reason `action` and syncs `open` back to false. Not verified against a real form-in-dialog scenario.
- Dialog: footer action alignment (justify) isn't specified by the schema. Left it at Stack's default (start-aligned), matching Card's footer convention, rather than assuming a right-aligned action row — worth confirming against the intended visual.
- Dialog: enter/exit animation technique (opacity + translateY via CSS `@starting-style` and a `transitionend`-driven finish/dispatch, gated by `prefers-reduced-motion`) was chosen as the modern idiomatic approach for a native top-layer `<dialog>`; the schema doesn't prescribe an exact mechanism for Lit the way it does for RN's `Animated`.
- Dialog: when `dismissible` is false, the close button stays visible and focusable but its click/press handler is a no-op ('the close button and scrim do nothing' per the doc), rather than being disabled or hidden — flagging the literal reading in case a disabled/hidden affordance was actually intended.
- Dialog: `initialFocus: 'close'` or `'title'` is honored even when `dismissible` is false (the schema doesn't state a conflict rule), so a non-dismissible dialog can still be told to focus the close button, which is present but inert.
- Could not execute `vitest run` in this sandboxed session (the shell tool call required interactive approval that wasn't available here); typecheck (`tsc --noEmit`) passes, and the two non-trivial test assertions (`has-accessible-name`, `control-is-focusable`) were manually verified against Lit's `delegatesFocus`/shadow-retargeting semantics rather than run live.

## 2026-09-16 06:28 — round 1

- Dialog: the web notes say `::backdrop` is the scrim, but the Parts contract needs a `scrim` part with a `data-part` element and a hook, and a part drawn as a pseudo-element has no hook. Chose a real `.scrim` element filling a full-viewport `<dialog>` (backdrop left transparent), and a scrim click is a click whose target is that element. The lit notes should say which one Lit uses.
- Dialog: `descriptionGap` names part `description` (a composed Text), but the gap sits between heading and description, and a child can't be styled or given a margin. Applied it as the flex `gap` of an unnamed titles group wrapping heading and description. The anatomy lacks a part for that group.
- Dialog: `footerGap` is forwarded to the footer Stack as `overrides.gap`, which takes a TokenRef, so the `--ds-dialog-footer-gap` CSS hook is declared but can't reach the Stack. Only the `overrides` property changes the footer gap. The doc should say whether the CSS hook must work too (for example via Stack's `--ds-stack-gap`).
- Dialog: the footer Stack gets `direction="horizontal"` and `justify="end"` (the end-aligned action row from the footerGap description), and `hidden` when the footer slot is empty, although the Parts contract lists only the `footerGap` forward. Heading gets `level="2"` and `tabindex="-1"`, and the close button `variant="ghost" size="sm" icon-only label` from the lit notes. The composition should list these props.
- Dialog: `initialFocus: first` doesn't say what happens when the body has no focusable control. Chose the footer's first focusable, then the close button, then the heading (APG's first focusable in the dialog). Only `close` has a documented fallback.
- Dialog: `hideHeading` and the heading's focus ring need styles on the composed `<ds-heading>` host (the visually-hidden clip and a `:focus-visible` outline using the locked focusRing tokens), which comes close to the rule against styling a child. Heading has no `visuallyHidden` prop and no focus style of its own for `tabindex=-1` use.
- Dialog: `focusScope` is placed around the surface (it carries layout: sizing and flex), and `scrim` sits outside it. The anatomy order (scrim, surface, focusScope, header…) suggests it sits inside the surface. The doc doesn't say how the parts nest.

- Dialog: Chromium fires a non-cancelable `cancel` for Escape when the page has no user activation, and the native dialog closes anyway. The doc assumes `preventDefault` always works. Chose to report `escape` from `cancel`, then call showModal() again and restore focus if the consumer hasn't set `open` false.
- Dialog: the `layer` binding (z-index var(--layer-dialog)) has no effect inside the top layer that showModal() uses. Kept the hook as specified.
- Dialog: the examples' `children` and `footer` values are prose ("An email Input and a role Select"), not args, so each example story has its own render that builds that content; the args are exactly the example's `given` minus those two keys.
- Dialog: the `closed-dialog-renders-nothing` scenario has no platform-specific meaning for 'renders nothing'. Chose an empty shadow root while closed (and not animating out), tested as no `<dialog>` and zero element children.

## 2026-09-17 10:19 — round 1

A <ds-box data-part="body"> would lose the part and become a second [data-part=surface]. I put data-part="body" on a Dialog-owned scroll wrapper around the Box instead; either Box should keep a passed data-part on Lit or the doc should list body as a wrapper part on Lit.
- Dialog: `inset` is 'Padding of header, body and footer', applied by header, footer wrapper and the body Box (paddingBlock and paddingInline), while `partGap` separates the same three parts. Taken literally the space between parts is inset + partGap + inset, and the doc doesn't say whether header/footer padding should drop the block edge facing the body. I applied full inset on all three plus partGap on the surface; the surface itself has no padding.
- Dialog: composition.body.forwards lists only `inset → paddingBlock`, but the `inset` style description says the body Box receives it as both paddingBlock and paddingInline. I forwarded both; the forwards map should list paddingInline too.
- Dialog: forwards to a child's `overrides` and the documented CSS hook route (footer wrapper sets --ds-stack-gap from --ds-dialog-footer-gap) conflict if the forward is always set: the child's inline style from overrides beats the parent stylesheet, so a consumer's CSS override of --ds-dialog-footer-gap would be ignored. I forward to overrides only when the Dialog's own override for that binding is set and rely on the CSS hook otherwise (same for inset → --ds-box-padding-block/inline). The doc should say whether a forward is unconditional.
- Dialog: the non-cancelable `cancel` handling covers the case where Chromium fires a non-cancelable cancel, but a close watcher can also close the <dialog> with no `cancel` at all (repeated Escape without user activation). I report `escape` from the native `close` event when no cancel announced it, so it's reported exactly once either way; the doc names only the non-cancelable-cancel case.
- Dialog: the Lit notes don't say which element the heading's tabindex -1 goes on now that the heading part is a wrapper. I put it on the <ds-heading> (not the wrapper) so the wrapper's `:has(:focus-visible)` ring matches, and set it for `initialFocus: title` and when the heading ends up as the last fallback of `first`/`close`.
- Dialog: 'the footer wrapper is not rendered when there is no footer' needs footer presence without a rendered slot (no slot → no slotchange). - Dialog: controlled-state contract says `open` is 'uncontrolled from its initial state when omitted', but the prop doc says 'Controlled only — there is no uncontrolled mode'. I followed the prop doc: no default-open property, the element never flips `open` itself.
- Dialog: the behavior scenario `initial-focus-lands-on-the-close-button` expects focus on the closeButton part, but on Lit that part is a non-focusable wrapper around ds-button; the test asserts focus rests inside the wrapper.
