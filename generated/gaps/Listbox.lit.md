# Gaps reported while generating Listbox for lit

Each entry is a place the doc made the generator guess. Fix the doc, re-run parse, regenerate.

## 2026-09-10 09:44 — round 1

- Listbox: schema requires a `DsFormField`-compatible field, but `currentValue` must be `ListboxValue` (string | string[] | null) to support `multiple`, which is outside `DsFormField`'s declared `string | boolean | null` contract. I implemented `currentValue`/`checkValidity`/`reportValidity`/form-association without formally `implements DsFormField`. More importantly, `packages/lit/src/Form.ts`'s `FIELD_TAGS`/`FIELD_SELECTOR` constants (a fixed set: ds-input, ds-checkbox, ds-switch, ds-radio-group) do not include `ds-listbox`, so `<ds-form>` will not currently discover, validate, or collect a standalone `<ds-listbox>` even though the doc says 'Inside a Form, `name` collects the value ... and `required` fails when nothing is selected.' Fixing this requires editing Form.ts, which is out of scope for this generator pass.
- Listbox: the schema has no `error`/`invalid` prop (unlike RadioGroup, Input), yet a11y.requires lists `error-identification` and the platform notes describe `required` failing submission. I surface the failure only through native ElementInternals validity (`setValidity`/`reportValidity`), with no visual error state, since inventing an `error` prop wasn't in the schema.
- Listbox: `labelledBy` is documented as 'Id of a visible element that labels the list' without specifying whether that element lives in the same shadow root or the consumer's light DOM. I implemented it as a plain `aria-labelledby` attribute on the internal `role=listbox` div (matching this package's existing pattern in Menu/Dialog/Meter, all of which only ever reference same-shadow-root ids). This only resolves when the referenced id is inside the same shadow root (e.g. a future `<ds-combobox>` composing `<ds-listbox>` and rendering its own visible label alongside it). If the id is meant to be a light-DOM id in the consumer's page, that needs cross-root `ariaLabelledByElements` reflection, which this package only wires up via `ElementInternals` on a *host* element (Form.ts, Card.ts) — not applicable here since `role=listbox` intentionally lives on an internal div, not the host, so that `list` and `option` elements can share `aria-activedescendant` in the same tree per the lit platform note.
- Listbox: the `border` style binding's description says 'Only when standalone; inside a popup the popup owns the border' but there's no prop distinguishing standalone vs. embedded use. I always render the border (standalone default); a composing component (future Combobox/Select) is expected to zero it via `overrides.borderWidth` pointing at a zero-width token, since overrides can only substitute another token reference, not remove a rule.
- Listbox: `copy.selectedCount` has no matching anatomy part — Listbox itself never renders a selection count (per Content guidelines, that's shown by 'the surrounding UI'). I exported it as `LISTBOX_COPY_SELECTED_COUNT` for a future composing component to reuse rather than inventing a count display inside Listbox's own anatomy.
- Listbox: `selectionFollowsFocus` (default `true`) is not listed under `platforms.lit.reflect` (only `multiple`, `disabled`, `required` are), but per the 'booleans that default to true' rule it still needs a negated-attribute converter so it's settable to `false` from HTML at all. I added the `no-selection-follows-focus` attribute/converter without `reflect: true`, i.e. it accepts the negated attribute on read but doesn't mirror back out to an attribute — consistent with the reflect list omitting it, but worth flagging since it's a slight deviation from how Popover/SidePanel apply the identical converter (those two do set `reflect: true`).
- Listbox: behavior scenario 'renders-maxVisible-*' and the keyboard model's PageUp/PageDown 'move by the visible row count' assume a concrete row height; I compute it in CSS from `fontSize * lineHeight + 2 × optionPaddingBlock` (an approximation — it doesn't include the option's border or any inter-row gap, since none is specified for the option list) rather than measuring the DOM, so `maxVisible` scroll height is a calculated estimate, not a pixel-exact N rows.

## 2026-09-10 18:29 — round 1

- Listbox: the `invalid` prop's description says it shows `copy.invalid`, but the schema's `copy` block only defines `empty`, `required`, `selectedCount` and `loading` — no `invalid` string. Synthesized `${label} is not valid.` as the ElementInternals validationMessage, matching the convention already used by Input.ts/Select.ts for the same gap.
- Listbox: `error`/`error-identification` require rendering error text and a11y wiring, but the component's `styles` block defines no token binding for error text color/size (unlike Input/Select's locked `errorText`) and `anatomy` has no matching part. Rendered a `role="alert"` region styled with `color-foreground-danger` (matching Input/Select's own errorText token) and exposed it as csspart `error-message`, which is not in the documented anatomy.
- Listbox: `embedded`'s prop description says the composing popup owns 'border, surface and radius', but only the `border` style binding's own description calls out the `embedded` exception explicitly; `surface` and `radius` don't mention it. Chose to suppress border, background and border-radius together on `.list` when `embedded` is set, to match the prop's prose.
- Listbox: `platforms.lit.reflect` lists only `multiple`, `disabled`, `required`, so the new `invalid`, `error`, `embedded`, `defaultActiveValue` and `loading` properties are not reflected to host attributes (no `:host([invalid])`-style selectors) — internal styling/behavior reads the properties directly instead.
- Listbox: `Select.ts` and `Combobox.ts` (existing composers, out of scope for this pass) don't currently pass the newly-added `embedded`, `loading` or `defaultActiveValue` down to their composed `<ds-listbox>` — they manage `activeValue` directly instead. Those files likely want a follow-up pass to adopt the new props now that Listbox implements them.

## 2026-09-16 08:18 — round 1

- Listbox: `form.valueType: string[]` contradicts the lit platform notes (string for single-select, FormData per value only with `multiple`) and `DsFormField.currentValue: string | boolean | null`; chose string for single, string[] for multiple, so `currentValue` is `string | string[] | null` and DsListbox does not declare `implements DsFormField`.
- Listbox: `optionSelectedCheck` says the check renders only with `multiple` and 'single-select shows selection by the row fill', but no row-fill binding exists (`optionActiveBackground` is the active state, and the Accessibility section says active and selected are never confused); single-select shows selection by `optionSelectedWeight` only.

- Listbox: the doc does not say whether PageUp/PageDown follow `selectionFollowsFocus` (Behavior lists only arrows, Home, End and typeahead); chose to follow it like the arrows.
- Listbox: `maxVisible` is 'rows × measured first-row height' in the prop but 'fontSize × lineHeight + 2 × optionPaddingBlock' in Behavior; used the formula as the CSS fallback and replace it with the measured first rendered row, plus listPadding and border so exactly N rows show.
- Listbox: no binding for the error message text (color/size), and anatomy has `errorMessage` but no composition; rendered it as `<ds-text tone="danger" size="sm">` inside a `role=alert` errorMessage div, spaced from the list with `<ds-stack gap="tight">` (gap token not in the doc).
- Listbox: the whole-list `disabled` style is unspecified (only `disabledOpacity`); applied `disabledOpacity` to the list, `tabindex=-1` and `aria-disabled`, and did not stack opacity on individually disabled options.
- Listbox: the doc does not say what ArrowUp/PageUp do when no option is active (a Combobox forwarding keys before focus); chose to start from the last enabled option.
- Listbox: the typeahead reset timeout is not a token or constant in the doc; used a module constant of 500ms.
- Listbox: `copy.selectedCount` has no place in Listbox's anatomy; exported `LISTBOX_COPY_SELECTED_COUNT` for surrounding UI and render no count.
- Listbox: `invalid` and `error` both drive the invalid state and the doc does not say whether clearing `error` clears an explicitly set `invalid`; chose to clear only the invalid that `error` implied.
- Listbox: behavior says 'Without name the list does not register with a Form', while the lit convention puts `data-ds-field` on every field; kept `data-ds-field` always (ds-form skips unnamed fields) and submit no form value without `name`.
- Listbox: Ctrl+A 'again clears': does not say whether selected disabled options survive select-all or the clear; select-all keeps them, clear empties everything.

## 2026-09-17 11:46 — round 1

- Listbox: `error` says the displayed message falls back to 'the Form's message', but Lit's ds-form never pushes a message into its fields (it only reads `validationMessage`), so there is no Form message to show; the displayed order is `error`, then copy.required/copy.invalid while invalid.
- Listbox: the export rename (ListboxOption = leaf, ListboxGroup, ListboxItem = union) swaps the meaning of two existing Lit names and drops ListboxGroupOption, which breaks Select, Combobox, Search and adopters; the doc has no lifecycle/deprecation entry for the old names. Chose a clean rename and updated the in-package consumers.
- Listbox: typeahead says 'the next option whose label starts with the typed characters' and nothing about typing the same letter again. The old Lit code cycled through options sharing that letter (the APG convention); I dropped cycling to follow the rule literally, so 'aa' matches only a label starting with 'aa'.
- Listbox: onActiveChange fires null 'when the list loses focus', but when Select/Combobox/Search drive the list with handleKey the list never has focus, so the host must clear `activeValue` itself; the doc doesn't say who fires null in that case.
- Listbox: `disabled` says keys, hover and clicks do nothing but doesn't say whether focusing a disabled list still sets an active option and fires active-change; chose not to (the active option is only set when enabled).
- Listbox: `labelledBy` gives no attribute name for Lit; chose `labelled-by` (kebab-case like `initial-active-value`, `empty-message`).
- Listbox: `invalid` must reflect (platforms.lit.reflect) but the list is also invalid while `error` is set; to keep `:host([invalid])` and the state test consistent, setting `error` sets `invalid` and clearing it resets `invalid` only if `error` was what set it. The doc doesn't say whether the reflected attribute should cover error-implied invalid.
- Listbox: the errorMessage part is a composed Text but the doc names no live-region behaviour; the old wrapper's role=alert was removed, so a newly set error is announced only through aria-describedby.
- Listbox: the Behavior row formula multiplies `fontSize × lineHeight`, which is only valid CSS if `font.lineHeight.normal` is unitless; the doc doesn't state that constraint on the token.

## 2026-09-21 12:56 — round 1

- Listbox (harness, not the component): the generated behavior test clicks the option with a Playwright role locator, which refuses aria-disabled elements, so `a-disabled-option-cannot-be-selected` can never pass — the scenario's premise (a disabled option) is exactly what the locator rejects. tools/behavior_tests.ts needs `{ force: true }` (or a dispatched click) when the scenario's `given` marks the clicked option disabled; the hand-written test does this and passes.
- Listbox: the empty/loading row is documented as living inside the list with the option padding, but a role=listbox owns only option and group children, so a visible empty row fails axe's aria-required-children. Chose to render it aria-hidden with an id and point the list's aria-describedby at it, so the still-focusable empty list announces 'No options' on focus. The doc should say which element the empty state is and how it is announced.
- Listbox: the lit platform block lists `tabindex=0` flatly while `embedded` says an embedded list is not a tab stop. Chose tabindex=-1 when embedded, 0 otherwise (including when disabled, which the doc does say stays focusable); the attribute list should carry the condition.
- Listbox: `optionWeight` (font.weight.regular) and `optionSelectedWeight` (font.weight.medium) are both unqualified bindings on part `option` with no `state`. Chose optionWeight as the base weight on every row label with the selected rule winning on specificity; the doc should give optionSelectedWeight a `state: selected`.
- Listbox: the `options` description requires that 'a previously exported ListboxGroupOption stays as a deprecated alias of ListboxOption', but the Lit package never exported that name — it already exports ListboxOption/ListboxGroup/ListboxItem. Added no alias (React made the same call); the clause should be scoped to the platforms that actually had the old name.
- Listbox: `copy.selectedCount` has no Lit surface — the doc assigns it to React Native's accessibilityValue and otherwise says 'the surrounding UI shows it'. Kept it as an exported `LISTBOX_COPY_SELECTED_COUNT(count)` helper for Select/Combobox and never rendered by the list. If the web/Lit list should announce the count, the doc must name the element.
- Listbox: `initialActiveValue` moves the active option 'without firing onActiveChange' when it changes 'while the list has no focus', but in an activedescendant composite the host (Select, Combobox, Search) holds DOM focus and still drives the list. Chose the test `shadowRoot.activeElement !== the list element`, so a host-driven list always follows the new value; the doc should state the test in those terms.
- Listbox: 'typing the same character repeatedly cycles through the options starting with it' is not reconciled with the accumulating buffer. Chose: a buffer made of one repeated letter collapses to that letter and searches from the option after the active one; any other buffer is a prefix searched from the active one. The doc should say the repeated-letter case replaces the buffer rather than extending it.
- Listbox: `typeaheadReset` is 'read at runtime from the list', but the doc does not say what to do when the custom property cannot be read (no token stylesheet). Parsed ms/s from getComputedStyle; unreadable resolves to 0, so only single-character typeahead works there.
- Listbox: PageUp/PageDown 'moves by the maxVisible row count' is ambiguous between enabled options and drawn rows (which include disabled rows and group labels — the things the maxVisible height formula counts). Chose enabled options, so a page move never lands on a disabled row or stalls.
- Listbox: Shift+Arrow says it 'adds' the reached option but not whether it can remove one — chose add-only. Ctrl+A 'deselects the enabled options' — chose to leave selected disabled options selected in both directions, which the doc does confirm.
- Listbox: `value` and `defaultValue` are typed `string | string[]` regardless of `multiple`, and the doc never says what a single-select list does with an array or a multi-select with a bare string. Chose to normalise both ways (an array's first entry is the single selection, a string becomes a one-entry array) rather than warn.
- Listbox: `disabled` is documented only as the prop, but a form-associated element is also disabled by an owning <form>/<fieldset> through formDisabledCallback, which does not set the reflected attribute. Keyed the dimming, the key/click guards and aria-disabled on the effective state and wrote the CSS against the list's aria-disabled rather than :host([disabled]); the doc should say whether ancestor-disabled counts as `disabled`.
- Listbox: 'a composed part receives exactly the listed props' cannot hold — the errorMessage Text needs the `id` that aria-describedby points at and `element="p"`, the emptyState Text needs `element="p"`, every part needs its data-part hook, and optionCheck needs the locked optionSelectedCheck colour forwarded as Icon `overrides.color`. Kept all of those.
- Listbox: `borderInvalid` is not in the doc's list of bindings an `embedded` list makes a no-op (`border`, `borderWidth`, `surface`, `radius`), but an embedded list draws no border at all, so an override of it cannot apply either. Added it to the no-op set.
- Listbox: option element ids are unspecified for Lit. The web notes let hosts build `${id}-option-${value}` from the list's `id`, but Lit's options live in a shadow root and there is no `id` prop; used an instance-scoped `ds-listbox-N-option-<index>` (index, not value, so a value containing a space still yields a valid IDREF). Select/Combobox reach in by `data-value` instead, which the doc should record as the Lit contract.
- Listbox: the `LabelledBy` story exists only for React parity — on Lit `labelledBy` is accepted and never resolved, so the story shows a caption paragraph that does not name the list. The doc should say whether the Lit story is expected to exist at all for a web-only prop.
- Listbox: React's Default story args are 5 options and Lit's previous generation used 3, so the two component pages disagreed on the same-named story. Aligned Lit to React's FRUITS/MANY_FRUITS/PEOPLE fixtures; the doc's `examples` fix only the four named example stories, not the meta args every other story inherits.
