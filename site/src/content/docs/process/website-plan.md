Decided 2026-09-12, with Tony. The site described in `vision-and-decisions.md` ("Pages site") assumed the docs half of the public site would just be the existing Starlight build. That no longer holds: Tony wants the whole website — hero, navigation, docs sidebar, every component page — built from nothing but `@design-schema/react` components, and Starlight owns too much of its own header/sidebar/TOC markup to make that true. So this is a new app, `apps/website`, sitting next to `apps/ios-gallery`. `site/` does not go away — it keeps being the contributor/spec reference (schema decisions, process pages, the MCP server doc, extending-components) — but it is no longer the adopter-facing docs. `apps/website`'s docs section reads the same markdown as its content source, so the schema stays the single source of truth; it just renders that content through our own chrome instead of Starlight's.

## Why a new app instead of reskinning Starlight

Starlight is a full theme, not a component slot machine: even where its override API lets you swap a piece (`MarkdownContent`, `Sidebar`), it still renders its own header chrome, skip links, TOC, and pagination underneath. Getting to "every pixel of UI is one of our own components" through Starlight means fighting the framework at every layer. A bare Astro app has no opinions to fight — Astro gives static generation, file-based routing, and React islands for the interactive pieces, and the page is otherwise just our components composed the way the landing-page pattern doc already imagined (`vision-and-decisions.md`: "warm-friendly, sand with black geometric-line SVG background, SegmentedControl theme switcher").

## What already exists to build on

- `generated/components.json` — the parsed schema for all 51 components (anatomy, props, events, a11y, styles), produced by `tools/parse.py` (soon `.ts`, Workstream A of the currency plan). This is the props-table data.
- `generated/keyboard/*.json` — the 58 keyboard specs, one per interactive component, for the accessibility section's keyboard table.
- `packages/react/src/*.stories.tsx` — Storybook CSF3 stories already encode "varying examples" (Default, sizes, variants, disabled, etc.) as named exports with args. These are the natural source for the docs site's example gallery instead of writing examples twice.
- `site/src/content/docs/components/*.md` — the prose body of each component doc (guidance, feel) above the frontmatter schema. `apps/website` reads this directly as its content source rather than duplicating it.
- 15 of the 51 components are generated in `packages/react/src` today (Alert, Breadcrumb, Button, Checkbox, Disclosure, Form, Heading, Input, Landmark, Link, Meter, RadioGroup, Stack, Switch, Text). The website is built to scale to all 51 but only renders live examples for components that exist; a component page for an ungenerated component shows its schema (props/a11y/keyboard) with a "not yet generated" notice instead of a live demo.

## Content pipeline

`apps/website` defines two Astro content-layer loaders (Astro 5's Content Layer API, already the version pinned in `site/package.json`):

1. **Schema loader** — reads `generated/components.json` directly (no copy).
2. **Prose loader** — globs `../../site/src/content/docs/**/*.md` for the markdown body, keyed by the same slug as the schema.

A third build step, not a content loader, produces the example gallery: `tools/docs_examples.ts` (job 507) statically *analyses* each `*.stories.tsx` — parsed with the TypeScript compiler API, never imported, since a story module pulls in React, the component and its CSS — walks its named exports, and writes `generated/examples/<Name>.json` — `{ title, args, sourceText, storyId }` per story — so the website never re-authors an example, it renders the same story Storybook does.

Nav structure (top-level: Homepage / Docs / GitHub / About, and the docs sidebar's category groups) is itself generated, not hand-maintained: `generated/nav.json` groups the 51 components by their roadmap phase (Primitives → Core → Controls → Focus → Overlays → Selection → Numeric → Rows → Grids → Streams, the same order `regen.ps1` composes in) so the sidebar and the mobile Select always match the schema.

## Global chrome

**Header (desktop).** `Landmark(role="banner")` wrapping a `Container(width="page")` wrapping a `Stack(direction="row", align="center", justify="space-between")`: the logo mark (a bespoke SVG asset — see below, not an `Icon` glyph) + wordmark on the left as a `Link` to `/`; a `Stack(direction="row", gap="normal")` of `Link`s (Homepage, Docs, About) plus GitHub (`Link` with `external`, opens in a new tab, no in-app page) on the right; a `SegmentedControl` for the theme (calm-precise / warm-friendly) at the far right, per the landing-page pattern doc's original idea.

**Header (mobile, below the new `layout.breakpoint.md` token — see Foundations gap).** The nav `Stack` and `SegmentedControl` are replaced by one icon-only `Button` (hamburger glyph, `accessibleName="Open menu"`, `aria-expanded`) that opens a `SidePanel`. This is exactly the pattern `component-roadmap.md` already settled on SidePanel for ("the APG disclosure pattern with `modal` opt-in") — the mobile nav drawer sets `modal`, so it traps focus and returns it to the hamburger button on close. The panel's content is the same nav `Link`s stacked vertically, plus the theme `SegmentedControl` at the bottom.

**Footer.** `Landmark(role="contentinfo")`, a `Divider`, then a `Stack` of `Link`s (GitHub, npm, License) and a `Text(tone="muted")` copyright line.

## Home page

`Landmark(role="main")` → hero section first: `Container(width="content")` → `Stack(direction="column", align="center", gap="loose")` holding: the logo mark at a larger size, `Heading(level=1)` reading "Design Schema: An Agentic Design System", a `Text(size="lg", tone="muted")` one-to-two-sentence statement (drawn from `vision-and-decisions.md`'s Vision paragraph: a documentation-first, schema-driven system that generates real components for web, web components, and native platforms from one set of docs), and a `Stack(direction="row", gap="normal")` of two `Button`s — primary "Read the docs" → `/docs`, secondary "View on GitHub" → the repo, `variant="outline"`.

Below the hero, a feature section: `Container(width="page")` → a wrapped `Stack` of `Card`s (one per pillar — schema-driven, every platform, zero-token theming, accessible by construction), each `Card` with a `Heading(level=3)` and a `Text`. No dedicated grid component exists yet in the 51; the wrapped `Stack` plus `layout.gap.section` is the interim answer, not a new component — flag this as a foundations question if a real CSS-grid primitive turns out to be needed once the section is built.

The hero background ("sand with black geometric-line SVG background" from the landing-page pattern note) is a decorative, `aria-hidden` SVG behind the `Container`, not a component — background art isn't a UI pattern APG governs.

**Logo.** No component in the 51 is a brand mark (`Icon` is a fixed 16×16 UI-glyph set, not a logo). The Design Schema logo is authored once as a static SVG (`apps/website/src/assets/logo.svg`), using `currentColor` / the theme's `color.foreground` custom property so it re-themes with calm-precise/warm-friendly and light/dark automatically, exactly like every generated component does. This is the one visual asset in the site that is not generated — worth saying explicitly since everything else on the page is.

**What building it changed (job 504, 2026-09-12).** Two things above did not survive contact with the schema, and both are logged in `generated/gaps/` rather than worked around in the page:

- *The calls to action are `Link`s, not `Button`s.* `components/button.md`'s own "Do not" section rules out a Button for navigation and points at "a Link (or a Link styled as a button)" — and a Button has no destination to give, so on a static page it could only navigate from script, leaving the hero's two actions dead without JavaScript. `variant="outline"` is not one of Button's variants either. The "Link styled as a button" the guidance names does not exist (Link has `tone`, no appearance prop), so the CTAs are plain Links until it does: `generated/gaps/Button.web.md`.
- *The wrapped `Stack` needs one flex rule to be a card row at all.* Its items are sized by their content, so four cards of body copy shrink toward their longest word and the row never wraps. The page supplies a preferred column width and a `layout.max-width.prose` cap in `apps/website/src/styles/home.css` — layout only, no appearance. This is the foundations question this section asked to have flagged, and the answer is a real grid primitive (`Grid(minItemWidth, gap)` over `repeat(auto-fit, minmax(…))`), which also fixes the ragged last row a flex wrap leaves: `generated/gaps/Stack.web.md`.

The section also gained a `Heading(level=2)` above the cards ("Four pillars"), so the page outline runs h1 → h2 → h3 unbroken — `heading-order` is one of the axe rules Lighthouse's accessibility score includes.

## Docs section

**Sidebar (desktop, ≥ `layout.breakpoint.md`).** A persistent left column inside the docs layout: `Landmark(role="navigation", accessibleName="Component docs")` containing one `Disclosure` per phase group from `generated/nav.json` (open by default), each holding `Link`s to `/docs/components/<slug>` for every component in that phase. Foundations and Patterns get their own top-level `Link`s above the phase groups, not nested in a `Disclosure`.

**Sidebar → Select (mobile, < `layout.breakpoint.md`).** Below the breakpoint the sidebar `Landmark` is replaced by a single `Select`, options grouped the same way (`generated/nav.json`'s phase groups as `optgroup`-equivalent sections, since `Select`'s schema already supports grouped options), each option's value the component's route. `onChange` navigates (`window.location.assign`, since this is cross-page routing, not in-page state) to the chosen component's overview page. This is a page-level layout swap driven by the breakpoint token, not a new responsive prop on `Select` itself.

**What building it changed (job 505, 2026-09-12).** Four things the prose above did not settle, and the way each was settled:

- *The nav is an island, and it is rendered twice.* Both markups are in every docs page and `apps/website/src/components/docs-sidebar.css` displays exactly one, the same arrangement the header uses — the swap is a viewport question the browser can answer before hydration. But both halves need script to be worth anything (a `Disclosure` that never collapses is a dead button; the `Select` navigates from `onChange`), so the pair is one `client:load` island, `DocsNav.tsx`. Astro still renders it at build time, so every sidebar link is in view-source and works with the island's JavaScript slow or blocked. The mobile `Select` genuinely cannot navigate without JavaScript — that is what `window.location.assign` means — which is the same bargain the header's `SidePanel` drawer already makes below the same breakpoint.
- *The `Select`'s popup is portaled into `main`, not to `<body>`.* Its default portal target is `document.body`, which is outside every landmark on the page, so an open popup puts content in no landmark at all — axe's `region` rule, one of the ones Lighthouse scores. `Select`'s own `container` prop is the answer: the popup is `position: fixed` against the viewport, so where it sits in the tree is a semantic choice rather than a layout one. No component changed.
- *Foundations and Patterns are options too, and the routes are hand-written.* `generated/nav.json` describes the 51 components; neither it nor `tools/site_nav.ts`'s top-level list has a section list, so the two section routes live in `apps/website/src/nav.ts` beside the component-route shape. They are also ungrouped options at the top of the mobile `Select`, so both renderings reach the same destinations rather than the phone losing two. The pages they point at — along with `/docs` itself and `/docs/components/<slug>` — were created here as placeholders, because a sidebar link to a 404 is the navigation's defect, not the next job's; job 506 replaces the component page's body and keeps its `getStaticPaths`.
- *No token is a sidebar width.* The scale stops at the three content measures (`layout.max-width.{prose,content,page}`), so the sidebar column is half the prose measure — a ratio of a token, the same move the home page's card row makes, and the same thing to revisit if page chrome ever earns its own widths.

**A third section, added by job 523 (2026-09-12).** `/docs/naming-demo` is the worked example for [Brand naming, and the update path](/process/customization-and-naming/) — three components rendered twice, once with Design Schema's vocabulary and once with a fictional brand's, from the renamed tree in `packages/react/demo-brand`. It sits beside Foundations and Patterns in `apps/website/src/nav.ts`'s `DOCS_SECTIONS` (and so in the sidebar, the mobile `Select` and `tools/site_routes.ts`'s fixed routes) rather than in a phase group, because it is a page *about* the components rather than one of them — and a comparison nobody can find proves nothing, which is the entire point of that page. Two things it needed that no other page does: one `resolve.alias` in `astro.config.mjs` (the renamed components import `@demo/tokens`, a package only a real fork publishes), and the rename tables read from `packages/react/demo-brand/renames.json`, which the demo's own diff writes — so the page cannot claim a rename the tree does not have.

## Component page template

Route `/docs/components/[slug]`, same layout for all 51 regardless of generation status:

1. **Header block.** `Breadcrumb` (Docs / Components / `<Name>`), `Heading(level=1)` = the component name, `Text(tone="muted")` = the doc's `description` frontmatter field verbatim.
2. **Basic Usage.** A `Card` containing the component's default story rendered live (a React island, `client:visible`) next to its install/import snippet. Code presentation (syntax highlighting) is explicitly out of scope for "generated components only" — see Foundations gap below — and uses Astro's built-in `<Code>` (Shiki), a non-generated utility, since syntax highlighting isn't an APG interaction pattern to begin with.
3. **Props table.** `Table` (not `DataGrid` — this is static reference data, not an editable grid) built from `generated/components.json`'s `props`/`events` for that component: columns Prop, Type, Default, Description, Platforms, mirroring what `SchemaTables.astro` already renders for the internal site, just through our `Table` component instead of a raw HTML `<table>`.
4. **Examples.** `Tabs`, one tab per entry in `generated/examples/<Name>.json` (Default, Sizes, Variants, Disabled, …, whatever the stories already cover) — each tab panel is the live island plus its source snippet. This is the "varying examples" requirement, and it costs no new authoring: it is Storybook's own example set, projected.

**What building it changed (job 507, 2026-09-12).** 696 stories across all 51 components now reach the site, 674 of them as live renders. Seven things the prose above did not survive:

- *Step 2 is not built, and step 4 absorbed it.* "Basic Usage" was a `Card` holding the default story next to an install snippet — which is the first tab of step 4's `Tabs` with a different snippet beside it. The examples section is what the page has; an install/import snippet is a *package* fact rather than a *story* fact, has no story to trace back to, and so belongs with job 508's other snippet rather than being hand-written into a section here.
- *The extractor needs an evaluator, not a reader.* A story's `args` are frequently not literals: they name a module-level `const` (`columns: COLUMNS`), hold JSX (`children: panels`), narrow their own data (`tabs: TABS.slice(0, 3)`), or set a key to `undefined` to unset one the meta supplies. `tools/docs_examples.ts` resolves all four from the AST — identifiers into their declarations, JSX into `{ $element, props, children }` descriptors the website rebuilds with `createElement`, and a small set of *pure* array calls and arithmetic — because the alternative is a JSON file that silently says the example is something simpler than it is.
- *What is genuinely code is kept, not dropped.* 126 args across the 696 are callbacks (`render`, `formatValue`, `validate`) or calls that cannot be evaluated (`Feed`'s `minutesAgo(3)`). Each is written as `{ "$unsupported": "<source>" }` and dropped at render, which is exactly what the component sees when a consumer omits an optional prop — a `Table` column renders its raw value rather than a formatted one — and the source slice beside it still shows the reader the real story. `pnpm docs:examples --report` lists them.
- *Whether an example renders is answered by rendering it.* A CSF story can define its own `render` and build a demo around the component (all five of ActionSheet's do), and then there are no args to mount anything with. Guessing from the schema's required-prop list gets the partial cases wrong — `Feed`'s `items` is present, it is the timestamp *inside* each item that is missing — and a guess that is wrong is a failed static build, because SSR has no error boundary. So `apps/website/src/example-probe.ts` renders every example once in the page's frontmatter and asks whether it threw. 674 of 696 render; the rest show their source and their Storybook link.
- *The source snippets cannot go through Astro's `<Code>`.* They live inside a React island (the `Tabs`), and Astro can only pass markup into an island through a **statically named** slot — while the number of snippets on a page is the number of stories the component has. A dynamic `slot={`code${i}`}` compiles to a slots object keyed by an identifier that is not in scope, which is a build error, not a degraded page. `apps/website/src/highlight.ts` calls the same Shiki `<Code>` calls, from the frontmatter, and hands the island finished HTML. This is job 508's spot for the example half of its work; its other half, the install snippet, is still a plain Astro `<Code>` when it lands.
- *`pnpm check` now depends on a Storybook build.* The story ids are Storybook's, read from `packages/react/storybook-static/index.json`, which is gitignored build output — so a fresh clone has to run `pnpm --filter @design-schema/react build-storybook` once before `pnpm check` will pass. Deriving the ids here instead would remove that dependency and reintroduce the thing this step exists to avoid: a deep link that breaks quietly when Storybook changes its algorithm. The tool names the command in the error rather than guessing.
- *Breadcrumb's page has two breadcrumbs.* Job 506's gate located the page's own crumb with a page-wide `getByRole('navigation', { name: 'Breadcrumb' })`, which is now ambiguous on exactly one of the 51 pages — the one whose live example is a `Breadcrumb`. It is scoped to the first. Every component page is now a page that contains instances of the component it documents, which is worth remembering the next time a gate reaches for a page-wide locator.
5. **Accessibility.** An `Accordion` with sections "Role & structure" (the doc's `a11y.role` and anatomy, prose from a11y.requires), "Keyboard support" (a `Table` from `generated/keyboard/<Name>.json` — Key / Action columns), and "Contrast & motion" (the doc's contrast pairs and any `reduced-motion` requirement). An `Alert(tone="info")` above the accordion calls out anything that needs a deliberate consumer choice (e.g., "supply an accessible name via `label` or `aria-labelledby`").

For the 36 components not yet generated in `packages/react`, step 2 and the live islands in step 4 are replaced by an `Alert(tone="neutral")`: "Not yet generated — schema and accessibility contract below are final; a live example ships once `packages/react` regenerates this component." Steps 3 and 5 render unconditionally, since the schema and a11y contract exist for all 51 today.

**What building it changed (job 506, 2026-09-12).** Steps 1, 3 and 5 are built; step 2 and step 4 are one marked slot waiting for job 507. Six things the prose above did not survive, and how each was settled:

- *There are no 36.* The count above was written when 15 of the 51 components existed in `packages/react/src`; all 51 do now, and all 51 are exported by `@design-schema/react`, so the "not yet generated" branch renders on **no** page today. It is built and exercised anyway, and neither the page nor its gate carries a list: the page asks the package whether it exports the component, the gate re-reads `packages/react/src` and compares. The same two numbers in "What already exists to build on" above — "15 of the 51", "36 components" — are history; read them as the state on 2026-09-12 morning, not as the count.
- *There is no `neutral` Alert tone.* `tone` is `info | success | warning | danger`, and each says something about urgency that "this is not generated yet" does not mean. The notice is `info` until the schema has a tone for a statement of fact: `generated/gaps/Alert.web.md`.
- *Every `Table` on a page costs one axe rule.* `Table` renders its caption as a composed `Heading` — `anatomy.caption`'s composition says to — and also sets an explicit `role="table"`, which stops axe applying the native-table allowances and makes the heading an owned child the `table` role does not permit (`aria-required-children`). `hideCaption` does not help; nothing a consumer passes does. The website's axe gates hold every other rule to zero and let that one through by name, narrowed to `Table`'s own element (`tests/website/axe.ts`), and the fix is the doc's: `generated/gaps/Table.web.md`.
- *The "Components" crumb is text, not a link.* There is no `/docs/components` index route — the sidebar reaches a component directly — and `Breadcrumb`'s own schema renders an ancestor without `href` as plain text, which is the component's answer to exactly this. If a components index is ever worth having, the crumb becomes a link and nothing else changes.
- *`a11y.requires` is a list of slugs, and a docs page owes the reader a sentence.* `focus-restore` and `no-hover-only` are contract identifiers, not prose. `apps/website/src/component-page.ts` holds one sentence per requirement, keyed by the schema's own closed enum so a new requirement is a typecheck error rather than a slug shown to a reader — and marks the subset that is a *consumer* decision rather than the component's own contract, which is what the `Alert(tone="info")` above the accordion lists, alongside the required props the doc annotates with an a11y note.
- *Events get their own `Table`.* Step 3 names one table over "props/events", but an event has no type and no default, so folding them together means a column that is a dash for half the page — and it stops "the props table" being the doc's prop count, which is the gate. Two tables: Prop / Type / Default / Description / Platforms, then Event / Type / Description / Platforms.

Only the accessibility accordion is an island (`client:visible` — it is below the fold, and its sections are open and mounted at build time, so the whole contract is in view-source and folding is what hydration adds). The props tables, the breadcrumb and the header block are static `@design-schema/react` output and ship no JavaScript at all.

**What building it changed (job 508, 2026-09-12).** The scoped exception step 2 names is now wired, and step 2 itself exists again — as a snippet section, not the `Card` the prose describes. Four things:

- *The exception is two spots, and the second one is the one that needed a reason.* The Basic Usage snippets are a literal `<Code>`; the example sources go through `apps/website/src/highlight.ts`, for the statically-named-slot reason job 507 found. Both call the same Shiki with the same theme, so "two spots" is a fact about the page rather than about the implementation, and the comment that says so is at the top of one file. Everything else on the site that looks like code is a `Mono` — a `Text` at `font.family.mono` — which is a generated component doing a generated component's job.
- *Shiki is themed from the tokens, not from a preset.* `highlight.ts` builds a Shiki **CSS-variables** theme, so every colour it emits is `var(--ds-code-…)`, and `apps/website/src/components/code.css` binds those names to the active theme's own colour tokens. No `github-light`/`github-dark` ships at all, and a code block re-themes on the same two switches every generated component does. The mapping re-uses the system's existing colour vocabulary — danger for keywords, success for strings, warning for constants, brand for names that point somewhere — rather than inventing a code palette.
- *The block's surface is `color.background`, and `color.status.info.*` is unused.* Both are warm-friendly's doing, and both are worth knowing before retuning a theme: on its sand `color.background-subtle`, `color.status.success.foreground` is 4.47:1 — just under AA — and clears at 4.71:1 on the page background; and its `info` ramp is the same warm orange as its `warning`, so a palette using both would have two roles a reader could not tell apart. The corollary is the honest one: warm-friendly's `color.link` *is* its foreground, so function names read as plain identifiers there. A low-chroma theme gets a low-chroma code block, which is what "re-themes like every other component" has to mean.
- *Step 2 is a snippet section, and it derives its snippets.* The live render stays in step 4 where job 507 put it — the default story is that section's first tab. What Basic Usage owes a reader is the install command and the import lines, and those come from `packages/react/package.json` (its name, and the `.css` export it publishes because `sideEffects: false` means a consumer has to import the stylesheet themselves) rather than being written into the page. It renders only when the package exports the component, which today is all 51.

## Linking to Storybook

Decided 2026-09-12. The docs page's example `Tabs` (above) render each example's live component directly from its story's `args` — a self-contained React island with no network dependency on Storybook at all. That matters because it means the docs site's core content (props tables, a11y contracts, and the examples themselves) works whether or not any Storybook instance is reachable; a "storybook is down" incident degrades one link, not the docs site.

The one thing that does need a real Storybook instance is a deep link next to each example — "Open in Storybook ↗" — for anyone who wants the full toolbar (viewport sizing, the accessibility addon panel, controls) rather than the static embed. Rather than self-host that instance on GitHub Pages bundled into the same deploy as the docs site (the original assumption in `vision-and-decisions.md` #3, and a real single-point-of-failure: one Storybook failing to build could previously fail the whole Pages artifact, including the working docs site), each package's Storybook publishes independently to **Chromatic** — a hosted service built specifically for this job. Each of `packages/{react,lit,rn}` gets its own Chromatic project with a permanent, versioned URL that doesn't depend on the other two packages or the main site building successfully (job 510). It's free for a public/open-source repo, and it comes with visual regression testing as a later option at no extra integration cost.

The deep link itself: `tools/docs_examples.ts` (job 507) cross-references each story export against Storybook's own generated `index.json` (rather than re-deriving Storybook's ID-generation algorithm by hand) to capture the real `storyId`, and links to `{chromaticUrl}/?path=/story/{storyId}` — the same URL scheme Storybook's own router uses, so the link works identically whether Chromatic is serving it or a future self-hosted mirror is.

**What building it changed (job 510, 2026-09-12).** The workflow is written and staged; the three projects are not created, and cannot be from here. Four things:

- *Half of this job is not code, and the repository now says where the other half lives.* Creating a Chromatic project is an OAuth flow against a GitHub account, and storing a project token is a repository-settings action; this checkout has no git remote and no `gh`. So the job stops at a written procedure — `jobs/510-chromatic-storybooks.md`, "Log" — the same honest outcome the SwiftUI gate jobs reached, rather than a gate reported as passing on a hosted repository nobody here can see.
- *`generated/chromatic.json` exists with empty strings, and that is a value rather than a placeholder.* `apps/website/src/examples.ts` already reads an empty or absent URL as *omit the "Open in Storybook ↗" link*, which is what this plan asked for before job 510 lands. Writing the file with its three keys and `""` means the site is correct today, the resume step is three strings, and the shape is checked before the URLs are. It is also the one file in `generated/` that is typed by hand and never regenerated — a wrong slug costs a link per example and announces nothing — so `tools/chromatic.ts` (`pnpm chromatic:check`, `--fetch` for the "URLs 200" criterion) is what makes that loud. It rejects a `<branch>--<slug>` preview URL by name, because that is the plausible wrong thing to paste: it is what the CLI prints after a build, and it moves with the branch.
- *GitHub has no per-job `paths:` filter, and the gate is a per-job statement.* "A PR touching only `packages/react` triggers only the react Chromatic job" needs one small `changes` job computing the diff, with each package job gated on its output. That is a shared `needs:` edge, but not a shared *build*: the three publishes still cannot fail each other, which is the independence the plan is actually buying. The filter treats the token pipeline, `storybook/shared/`, the lockfile and the workflow itself as inputs to all three, since all three previews import `@design-schema/tokens/<theme>/css`.
- *Building the Storybook twice per package is not worth the flag the job named.* Chromatic's `--build-script-name` makes the CLI run the build script itself, so pairing it with an explicit build step builds each Storybook twice. The workflow keeps the explicit step — a Storybook that does not build and a publish that failed deserve to be different red steps — and passes `--storybook-build-dir` instead, which also keeps the build inside pnpm's workspace resolution rather than whatever package manager the CLI infers from a package directory.

## Foundations gap: a breakpoint token

Every component's own responsiveness so far is container-query-driven (Splitter's collapse rule is the precedent: "container query by ResizeObserver"), because a component doesn't know what viewport it's in. Page-level chrome is different — the header's nav-vs-hamburger switch and the docs sidebar-vs-select switch are viewport decisions, not container ones, so they need an actual breakpoint. `foundations/layout.md` gains `layout.breakpoint.{sm,md,lg}` (640/768/1024px, the conventional content-visible tier) as a new token group, consumed only by page chrome — `Header`, the docs layout, and nothing inside `packages/react/src` itself, so it does not touch the "no literals" rule that governs components. Job 502 lands this before the header and sidebar jobs, since both depend on it.

## About and GitHub

**About** is a plain content page — `Container(width="prose")` → `Stack` of `Heading`/`Text`, adapted from `vision-and-decisions.md`'s "Who it is for" (Adopter / Owner) and `guides/two-ways-in.md` — no new component needs.

**GitHub** in the top nav is an external `Link`, not a route: it goes straight to the repo (`https://github.com/design-schema/design-schema` once job's org/repo step in `vision-and-decisions.md` #1 has run) and opens in a new tab.

**What building it changed (job 509, 2026-09-12).** The About page, the footer and the deploy are built. Four things:

- *One of the two named sources does not exist.* The About page is "adapted from `vision-and-decisions.md`'s 'Who it is for' (Adopter / Owner) and `guides/two-ways-in.md`", and `vision-and-decisions.md` has never been a file in this repository — the same thing job 504 found when it went for the Vision paragraph, and the reason step 5 of this job could not edit §3. `two-ways-in.md` carries that same split heading for heading, so it is the whole source; the correction §3 was to receive is in `process/publishing.md`, "The Pages site", where a reader of this repository can find it.
- *The footer's three destinations are all derived.* The repository comes from `generated/nav.json` (the entry the header and the hero already share), the npm organisation from `packages/react/package.json`'s own scope — so renaming the scope, which `customization-and-naming.md` is entirely about, moves the link with it — and the copyright line is read out of `LICENSE` at build time rather than retyped with a year in it. A footer is exactly the kind of surface where a hand-typed URL rots unnoticed.
- *The footer is the reason `body` is a flex column.* `contentinfo` is a sibling of `main`, not a region inside it (a `footer` descended from `main` is not a landmark at all), and as a sibling it sits wherever the content ends — which on the two section placeholders is a third of the way down the screen. One `min-block-size: 100vh` column in `Layout.astro` is the whole fix.
- *The deploy gate needed a tool.* "The deployed site serves `/`, `/about`, and all 51 `/docs/components/<slug>` routes" is not something `astro build` answers: a `getStaticPaths` that returns one path fewer still exits 0, and the route is simply absent from `dist/`. `tools/site_routes.ts` (`pnpm site:routes`) reads the route list from `generated/nav.json` — so the 51 is never written down a second time — and fails the build when a page is missing or empty. `pnpm gates:website` and the deploy workflow both run it.

The workflow itself is staged in `.github/workflows-pending/`, not installed: both this job and job 510 call their workflow "hand-delivered", on the authority of a protected-files note in the document that is not in the repository, so the constraint could not be checked and was honoured. That directory's README says how to install it.

## Where this lands relative to the existing Pages plan

`vision-and-decisions.md`'s publishing section (#3) said "landing page at `/`, docs at `/docs` (Astro build), Storybooks at `/storybook/{react,lit,rn}`." Two things changed from that original assumption: "docs at `/docs`" now means `apps/website`'s docs section (this plan), not a Starlight build — `site/` is not part of the public Pages deploy at all going forward; it stays a repo-local reference for contributors and for Claude Code sessions like this one — and the Storybooks are no longer folded into the Pages artifact at `/storybook/*`; they publish independently to Chromatic (see "Linking to Storybook" above). The Pages deploy is now just `apps/website`, which also means it's simpler and has one fewer way to fail.

Job 509 landed that deploy, and since `vision-and-decisions.md` is not a file here, the corrected §3 is written down in [Publishing](/process/publishing/), "The Pages site" — which is also where the workflow's shape and its one residual Storybook dependency are described.
