- SidePanel: the notes describe toggling the native `hidden` attribute on the panel once the exit transition ends; instead followed this package's established BottomSheet/Popover pattern of conditionally mounting/unmounting the panel, which gives the same accessibility-tree result but not the literal mechanism described.

- SidePanel: added a `container?: HTMLElement` portal-target prop; it isn't in the component's own schema prop list but matches the existing convention on every other portal-based overlay in this package (Popover, BottomSheet).

## 2026-09-16 07:34 — round 1

- SidePanel: DOM placement contradicts itself — the web platform note says the panel is portaled 'so Tab from the trigger does not walk into it by document order' with a Popover-style seam, while the Guidance body says the next Tab enters the panel 'because it sits right after the trigger in the document' and the Web platform-notes prose says 'directly after the trigger'. Chose the portal (schema note + overlay rule) and added handlers so Tab from the trigger enters the panel, Shift+Tab from the first control returns to the trigger, and Tab from the last control goes to the next tabbable element after the trigger.
- SidePanel: the keyboard section says Tab 'from the trigger, moves into the open panel', but the platform note implies it does not by DOM order; implemented the keyboard rule explicitly (Tab keydown on the trigger wrapper focuses the panel's first tabbable).

- SidePanel: dismissible:false + Escape in uncontrolled mode — 'reports, the consumer decides' is ambiguous about whether local state changes. Chose: fire onOpenChange(false, 'escape') without closing the uncontrolled panel.
- SidePanel: whether `dismissible:false` blocks `navigation`/`trigger`/`action` is not stated. Chose: only close-button, scrim/outside and swipe are gated; the trigger toggle and Link navigation always close.
- SidePanel: 'the switch must not lose content state' can't be kept for a modal panel, whose presentation changes from <dialog> to the non-modal element at the breakpoint (the tree root type changes). - SidePanel: the root is ambiguous — platforms.web.element is `aside`, but the note says Landmark (which renders the aside/nav) takes no className/style/ref and SidePanel's own positioned element carries them. Chose: `data-ds`, classes, hooks and ref on SidePanel's wrapper (a display:contents div holding scrim + fixed surface; the <dialog> in modal). `id`/aria-controls target is the surface div, not the landmark itself.

- SidePanel: persistent-mode layout is underspecified ('page grid beside the content', 'grid column of the width token') — no rule for where the sidebar goes relative to the trigger, and no statement on whether the close button shows. - SidePanel: modal initial focus — the note says 'first control', the guidance 'first control (or the title)', and the guidance also says `autoFocus={modal ? - SidePanel: the `trigger` prop is `content` (ReactNode) in the schema but 'exactly one element, typed as such' in the web note. Typed as ReactElement; hiding it in persistent mode uses a display:contents wrapper span (data-part='trigger') so the Button itself is never restyled.

## 2026-09-17 11:13 — round 1

- SidePanel: 'the ref is null while closed' conflicts with 'the `hidden` attribute when closed'. The non-modal surface stays mounted with `hidden` (the renders and has-accessible-name scenarios need it in the DOM), and the ref reports null whenever the panel is closed and not persistent.
- SidePanel: the `partGap` binding names part `focusScope`, but FocusScope always overwrites `data-part` with `scope` and accepts no className/style, so no `data-part="focusScope"` element exists and the gap cannot be put on it. - SidePanel: the closeButton composition lists only `variant: ghost` and `iconOnly: true`, but an icon-only Button needs a `label` (copy.closeLabel) and the `close` Icon as `leadingIcon`. I passed both although they are not in the listed props.
- SidePanel: the body Box is `inset: lg` with `inset` forwarded to `paddingBlock`, and the doc says the header and footer get 'the same padding'. I gave the header inline + block-start inset and the footer inline + block-end inset, and left the doubling in place; the doc should say whether the gap or the padding wins.
- SidePanel: Heading has its own `marginBlockEnd` (space.sm), which unbalances vertical centering against the close button in the header. There is no forward for it and restyling the child is not allowed, so it is left as is.
