# Gaps reported while generating Switch for web

Each entry is a place the doc made the generator guess. Fix the doc, re-run parse, regenerate.

## 2026-09-10 01:43 — round 1

- Switch already had a Switch.tsx/css/stories/test set that predated the overrides/data-ds/data-part conventions (visible in Checkbox); I brought it up to that convention — added `SwitchOverridableBinding`, `overrides` prop, per-instance CSS hooks for every listed binding (locked bindings get hooks too, just excluded from the TS union), `data-ds="Switch"` on the root, and `data-part="description"` on the description Text — without touching the existing behavior logic, which already matched the schema's behavior scenarios and passed all 16 existing tests unchanged.
- The schema doesn't say whether the description's helper text size/color should be enforced by a local CSS rule or left to Text's own `size="sm" tone="muted"` props; followed Checkbox's precedent of setting both (Text props for the semantic class and a local rule reading the `--ds-switch-helper-size`/`--ds-switch-description-text` hooks) so the override hooks actually take effect.

## 2026-09-10 17:40 — round 1

- Switch: the package convention doc says form-field components carry data-ds-field for Form to discover them, but Form.tsx actually discovers fields via context registration (useFormContext().register), not DOM query — data-ds-field is only present on Checkbox and Input among 13 form-registering components (RadioGroup, Select, Combobox, etc. also omit it). Left Switch consistent with the majority pattern rather than adding the attribute unilaterally; this is a system-wide convention/implementation mismatch worth resolving once, not per-component.
- Switch: guidance mentions 'Inside a Fieldset the field reads FieldsetContext: disabled from the group applies as if set on the field,' but no FieldsetContext exists anywhere in the package (Checkbox, the closest sibling, doesn't implement it either) — Switch only inherits disabled from FormContext, not from a Fieldset group. Not implemented, since inventing that cross-cutting context for one component would be inconsistent with how its neighbors currently behave.

## 2026-09-16 04:49 — round 1

- Switch: Guidance says 'Inside a Fieldset the field reads FieldsetContext' but no FieldsetContext exists in @design-schema/react; chose FormContext's `disabled` only.
- Switch: `helperSize`, `fontFamily` and `lineHeight` have no `part` and the description is composed Text; which child binding each forwards to is not declared. Chose Text `fontSize`/`fontFamily`/`lineHeight`, following Checkbox.
- Switch: the thumb is a part in the anatomy with `thumb`/`thumbSize`/`thumbInset` bound to it, but the web notes draw it on the input itself (a pseudo-element), so it has no data-part hook; the doc does not say this is intentional for web.
- Switch: `form` does not say whether a disabled Switch is still submitted; registered it with `isDisabled` like Checkbox, so the Form's disabled-field rule applies.
- Switch: `disabledOpacity` has no part; chose to dim the track, label and description, even though `labelColor`/`descriptionText` are locked contrast pairs.
- Switch: the `transition` description says travel is 'instant under reduced motion' but does not say whether the track colour change is also removed; chose to remove both.
- Switch: `minTarget` is 'minimum row height; the whole row toggles', but the row is full width and `a11y.requires` lists target-24px while the prose cites the 44px comfortable target; used size.target.comfortable as min-block-size on the row and let the gap between the label and the track forward clicks.
- Switch: `controls.state: checked` together with the explicit `aria-checked` requirement makes a fully component-controlled input tempting, but with React 19 plus jsdom a component-held `checked` combined with preventDefault on a disabled click leaves the DOM checked; the doc should say the uncontrolled input keeps native state and aria-checked is mirrored.

## 2026-09-17 05:03 — round 1

- Switch: the spec wants a full-width row with min-block-size minTarget and no padding, and the track 'at the top of the row, centred on the label's first line'. With a one-line label that row is 44px tall with the content in the top line-height (24px), leaving empty space below. Checkbox, which the spec calls 'as Checkbox', centres its row. I followed the Switch spec (align-items: flex-start plus a track wrapper one label line tall). The doc should say whether a one-line row centres vertically.
- Switch: the web notes say the input stays uncontrolled for its native checked state, but don't say how a controlled switch keeps the DOM `checked` in step when the prop doesn't change. I reset `event.target.checked` to the prop in the change handler and sync the DOM property in an effect whenever the held state changes. The markup uses defaultChecked from the current state.
- Switch: there's no rule for 'a press that asks for the current value (next equals checked) fires nothing' on web, where every native click flips the value. I added a `next === isChecked` guard that can't be reached in practice.
- Switch: the track and thumb styles key off the component state, either `:checked` or `[aria-checked='true']`. I used `[aria-checked='true']` so the look follows the component state, including in controlled mode.
- Switch: 'disabledOpacity dims the track, the label and the description', but the description is a composed Text that must not be restyled. I put the opacity on the wrapper around the label and description, not on the Text.
- Switch: RTL thumb travel is required ('Mirror the thumb travel under [dir=rtl]'), but no selector is given. I used the ancestor selector `[dir='rtl'] …`, which misses a `dir` inherited only from the user agent. `:dir(rtl)` would be more exact.
- Switch: `name` is optional here but FormContext registration needs one, so a Switch without `name` inside a Form doesn't register. Its DOM id then comes from useId rather than form.idBase. The doc doesn't say whether a nameless switch should register.

## 2026-09-20 22:31 — round 1

- Switch: the row cannot be one flex box. `platforms.web.notes` says "The row is a full-width flex row with min-block-size minTarget and no padding", while labelSize says the track slot is "aligned with the top of the text column" AND "The row centres its content (track slot plus text column) on the cross axis". A single flex container cannot both centre its items in minTarget and top-align the slot against a taller text column. I split it: the root is a column flex that centres an inner unhooked `.ds-switch__row` content box, which top-aligns the slot. Checkbox solves the same problem with symmetric padding-block, which this doc explicitly forbids ("The row has no vertical padding"). Say which box carries min-block-size.
- Switch: two contradictory mechanisms for the disabled-field rule. `FormFieldRegistration.isDisabled()` already exists and is documented as "Disabled fields are skipped by validation and omitted from values" — that is how Checkbox satisfies the identical rule — but props.disabled tells web to "not register while disabled (it unregisters when it becomes disabled and registers again when re-enabled)". I did both (skip registration while disabled, and still supply isDisabled), which is belt-and-braces. Two fields on the same Form now use different mechanisms for one rule; pick one and state it in the Form contract.
- Switch: thumbInset's block-axis meaning is ambiguous. The description says "Gap between the thumb and the track edge; split evenly on the short axis", which reads either as (a) the block inset is derived from the geometry, (trackHeight - thumbSize)/2, or (b) thumbInset itself is the block gap. With the default tokens both give 2px (space.6 24 - space.5 20)/2 = 2, space.1 = 4 on the inline axis only, so the defaults hide the difference. I chose (a). An override of thumbInset or trackHeight makes the readings diverge visibly, so this needs stating.
- Switch: the track wrapper span has no name. platforms.web.notes requires the thumb be "stacked over the input in a track wrapper span (as Checkbox's indicator)", but the anatomy is track/thumb/label/description with no entry for that wrapper, so it gets no data-part. I named it `.ds-switch__track-wrap`. The "as Checkbox's indicator" pointer also does not carry over technically: Checkbox stacks with inline-grid + place-items:center, which would centre the thumb, whereas the Switch thumb needs an inline-start inset plus a travel transform, so I used position:relative on the wrapper and absolute on the thumb.
- Switch: the off-state value of aria-checked is unspecified. The doc says to set aria-checked "explicitly to mirror the checked state" because some screen readers do not derive it from a checkbox carrying role=switch, but never says whether the off state is aria-checked="false" or the attribute omitted. Checkbox omits it except for mixed. I render "true"/"false" always, since an omitted attribute would defeat the stated reason for setting it. Behavior scenario `disabled-does-not-toggle` only asserts aria-disabled, so nothing pins this down.
- Switch: whether a native <form> submits a disabled or nameless web Switch is unstated. platforms.web.attributes lists `name`, so I forward it to the input and a native <form> submits "on" when checked — including while disabled, where props.disabled says the Form contributes no key. The Lit notes resolve exactly this (setFormValue(null) while disabled) but the web notes do not, leaving the native-form path and the Form-context path asymmetric on web. Decide whether web should also set the input's native `disabled`, or drop `name` while disabled, or accept the asymmetry and say so.
- Switch: the events entry reads as two rules in tension on web. onChange's description says the event does not fire "for a press that asks for the current value (next equals checked)", then says the guard is written only on RN/SwiftUI and "on web and Lit every native toggle flips the value, so no guard is written there". I followed the latter and removed the guard. The consequence, which the doc does not state: a controlled Switch whose `checked` prop never changes fires onChange(!checked) on every click indefinitely. That is correct per the contract but is the case the first sentence sounds like it is excluding.

## 2026-09-23 14:52 — round 1

- Switch: the conventions say to put `ref` on the root, but the web notes treat the input as the track, the thing the user interacts with. I followed Checkbox: `ref` is typed `Ref<HTMLInputElement>` and resolves to the input through `useImperativeHandle`, while the root is the full-width div. The spec doesn't say which element the ref should reach.
- Switch: the general rule says locked bindings keep a --ds-<name>-* hook, and the spec also says a binding carried by a composed child declares none. `descriptionText` is both locked and realised by the composed Text. I declared no --ds-switch-description-text hook, per the helperSize/descriptionText note. Checkbox does the opposite for its description and error text colors, so the two components disagree.
- Switch: the web notes say a click on the root itself or on the description is forwarded to the input. Clicks on the row's gap, the text column and the track slot land on inner wrappers, not the root. I forward every click outside the input and the label, as Checkbox does. The spec's list of forwarded targets is narrower than the hit area it describes.
- Switch: the spec doesn't say whether a Form's own `disabled` state counts as the switch being disabled. I made it count: it drops `name`, blocks toggling and makes the Form skip the switch, the same as Checkbox.
