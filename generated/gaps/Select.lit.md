# Gaps reported while generating Select for lit

Each entry is a place the doc made the generator guess. Fix the doc, re-run parse, regenerate.

## 2026-09-10 09:56 — round 1

- Select: the schema has no controlled `open`/`defaultOpen` prop (unlike sibling overlays Menu/Popover/Dialog, which all have one for exactly this purpose), so the Keyboard story can't declaratively render pre-opened; I used a `play` function that clicks the trigger's shadow-DOM button instead of inventing an `open` prop.
- Select: `aria-activedescendant` on the trigger's `role=combobox` button cannot correctly reference the active option, because the option lives inside `<ds-listbox>`'s own separate shadow root — plain ID refs don't cross shadow boundaries, and `ElementInternals.ariaActiveDescendantElement` only reflects for the internals-owning element itself, not into a composed child's shadow tree. I left it unset; the active option is only conveyed via focus staying on the trigger plus Listbox's own visual highlight, which is a real screen-reader gap for this exact composition (docstring hints it should 'work' but the platform doesn't support it as described).
- Select: `aria-controls` on the trigger points at Select's own `<div id="popup">` wrapper (same shadow root), not at the `role="listbox"` element itself, which is one shadow level deeper inside `<ds-listbox>` and unreachable by ID from the trigger's root — an approximation of the spec's `aria-controls={listboxId}`.
- Select: `<ds-listbox>` is itself `formAssociated = true`; composed inside `<ds-select>`'s shadow root it may independently try to associate with an ancestor `<form>` and call its own (empty-named) `setFormValue`. I left its `name` unset to minimize the chance of a stray form entry, but a real fix needs a 'not form-participating' composition mode on Listbox that isn't in its schema.
- Select: `<ds-form>`'s hardcoded `FIELD_SELECTOR`/`FIELD_TAGS` (Form.ts) don't include `ds-select`, so `<ds-form>` won't auto-collect/validate it even though it implements `DsFormField` — same known limitation already true of `<ds-listbox>`.
- Select: `DsFormField.currentValue` is typed `string | boolean | null`, but `multiple` makes Select's `currentValue` a `string[]` — same documented mismatch as Listbox; `<ds-form>` can't type-check this today.
- Select: the overridable `labelWeight`/`helperSize` hooks are exposed on the host per the contract, but they target the composed `<ds-text>` label/description, whose own `overrides` prop expects `TokenRef` token-path strings rather than resolved CSS-var strings — I couldn't bridge a hook's runtime value into that prop without inventing an unverified mapping, so these two hooks are currently inert (the label/description keep ds-text's own defaults) rather than restyling the child's shadow tree.
- Select: `popupSurface`/`popupBorder`/`popupShadow`/`popupRadius` style Select's own `.popup` wrapper, but the composed `<ds-listbox>` also draws its own border/background/radius inside it (Listbox has no borderless/surfaceless mode), producing minor nested 'double chrome' around the option list; not fixed via restyling the child, which the conventions disallow.
- Select: keyboard-model rows' `from: first`/`from: inside`/`from: trigger` fields have no defined semantics in the schema beyond grouping context; treated as descriptive metadata, not additional behavior to implement.

## 2026-09-10 18:35 — round 1

- Select: the schema lists `size` as a prop with a `fontSize: font.size.{size}` binding and sm-specific `triggerPaddingBlockSm`/`minTargetSm` bindings, but `platforms.lit.reflect` omits `size` — reflected it anyway (`reflect: true`) since an attribute selector is required to apply the per-size CSS, matching the established pattern for `size` on Button and Input in this same package.
- Select: `copy.selectedCount`, `copy.done`, `copy.required`, `copy.invalid` and `copy.requiredIndicator` are all defined, but the guidance's 'Behavior' section says the phone/tablet sheet footer button uses `copy.done` — that switch is React Native-only per the platform notes (BottomSheet), so `copy.done` is unused on this Lit build; left unreferenced rather than invented into an unspecified UI element.
- Select: the previously generated file's trigger used `aria-labelledby="label value"`, which pulled the placeholder/value text into the accessible name (e.g. 'Country Select…' instead of 'Country'), failing the schema's own `has-accessible-name` behavior scenario. Fixed to `aria-labelledby="label"` only, matching the native-`<select>` fallback branch, which already only referenced `label`; the current value is still conveyed visually and via the trigger's text content, just not folded into the accessible name.

## 2026-09-16 08:33 — round 1

- Select: platforms.lit.notes say DsFormField.currentValue is `string | boolean | string[] | null`, but Form.ts still declares `string | boolean | null`. Select returns `string | string[] | null` without `implements DsFormField`, as Listbox does. Form.ts's interface needs the doc's widening.
- Select: form.valueType is `string[]`, but single-select submits a string and `onChange` sends `string | string[]`. I submit a string for single and a FormData with one entry per value for multiple.
- Select: the Parts section says the listbox part receives exactly `options`, but the Behavior prose also requires `embedded`, `selectionFollowsFocus: false`, `defaultActiveValue` and `labelledBy`, and showing the selection needs `value`. I pass all of these, plus `multiple` and `disabled`, and bind Listbox's public `activeValue`. The composition block should list them.
- Select: label and description are composed `Text` with no props listed, yet Text needs `element`, `weight`, `size` and `tone` to match the bindings. I pass label `element=span weight=medium size={size}`, description `element=p size=sm tone=muted`, and error `tone=danger size=sm`.
- Select: the conventions say a field label is a native `<label for>`, while composition says label is Text. I render `<label for=trigger>` wrapping `<ds-text>`. Clicking the label focuses the trigger without opening the popup, which the doc doesn't specify.
- Select: labelWeight and helperSize must be forwarded to ds-text's `overrides` rather than written as CSS, so their `--ds-select-label-weight` and `--ds-select-helper-size` hooks exist on :host but setting them from document CSS has no effect. Only the `overrides` property reaches the Text.
- Select: errorMessage is listed as a plain element, but errorText (color.foreground.danger) and helperSize style it. I render a `role=alert` div containing a danger `ds-text`. When `invalid` is set without `error`, it shows `copy.invalid`; the doc doesn't say whether the invalid copy is visible or only the validation message.
- Select: the fontWeight binding is described as the weight of trigger and option text, but Listbox has no weight binding to forward it to, so it only reaches the trigger. fontFamily, fontSize and lineHeight are also not forwarded to the Listbox, since no forwards are declared.
- Select: placeholderColor, partGap, helperSize, errorText, layer, fontFamily, fontSize, fontWeight, lineHeight, minTarget, minTargetSm, focusRingWidth, disabledOpacity and enter have no `part`. I applied them to the trigger, the field group, the popup and the Text children as their descriptions suggest.
- Select: disabledOpacity has no part; following Input, the whole field group (label included) dims.
- Select: the popup border width has no binding (only the popupBorder color), so I used border.width.thin directly.
- Select: the Keyboard section lists only Escape and Tab as gated rules. I also implemented Enter, Space and the arrows on the trigger to open; Enter to commit (toggle with multiple); Space committing and closing for single-select; and forwarding arrows, Home, End and a-z to Listbox, as the full keyboard block and prose describe. Whether Space closes a single-select popup is not stated; I close it, like a click on an option.
- Select: with `open` controlled, Tab reports `open-change` but the popup stays shown until the property changes, so focus can move into the Listbox's tabindex=0 list. The contract (show new state only once the property changes) conflicts with 'Tab closes; focus moves on'.
- Select: `native: always` is meant for 'forms that must work without JavaScript', which a custom element cannot do. The native <select> lives in the shadow root and submits through ElementInternals like the popup mode. The value part has no element in that mode, and the chevron is overlaid only for single-select.
- Select: web notes use aria-labelledby = label + value, so the accessible name includes the placeholder or selected text ("Country (required) Select…"). I followed this, but it doubles the value that a combobox already exposes.
- Select: the lit notes call the active-option element 'live'. I used aria-live=polite on a visually hidden span that is also referenced by aria-describedby. Whether both are wanted, and which politeness level, is unstated.
- Select: `onChange` fires 'when the value changes'. Re-selecting the current option fires no `change`, but the popup still closes.
- Select: the doc names no outside-dismiss or close event beyond 'clicking outside closes' and web's 'focusout to outside'. I close on pointerdown outside and on focusout to a known outside target. There is no form/overlay `dismiss` block, so neither `collision` nor `placement` is declared; I flip above at the viewport edge.
- Select: the `enter` binding is 'popup fade' with no easing named. I used motion.easing.standard with @starting-style opacity, and removed the old chevron rotation and trigger border transitions, which the doc doesn't mention.

## 2026-09-17 11:53 — round 1

- Select: fontSize is `font.size.{size}` but the composed label and value Text take only `weight`/`tone`/`element` props, so following `size` needs the forward to carry a default. Chose to always forward `overrides.fontSize = overrides.fontSize ?? font.size.<size>`; the doc should say the forward carries the resolved default, not only a consumer override.
- Select: the composition lists the Listbox props as exactly options, multiple, value, embedded, selectionFollowsFocus, but the Behavior prose adds initialActiveValue and labelledBy, and the lit notes add setting `activeValue` on open. Passed all three and dropped `disabled` (a disabled Select never opens); the composition's props list should include them.
- Select: ds-listbox warns in development without `label` (it is always the list's aria-label, even with labelledBy), but the Select composition gives the Listbox no label. Left it unset, so an open Select logs the Listbox warning in dev; the doc should forward `label` or Listbox should accept labelledBy alone.
- Select: errorMessage is a Text part, but the doc also calls it a `role=alert` region. Put `role=alert` on a wrapper div (id `error`, the aria-describedby target) and `data-part=errorMessage` on the ds-text inside it; the doc should say which element carries the part.
- Select: popupOffset 'on the side the popup opens' is implemented as the popup's block margin (both sides), so the side away from the trigger also gets the margin; this only matters against the viewport edge in the flip test, which reads the resolved margin.
- Select: the value Text truncating a long label with an ellipsis cannot be done from the parent without restyling the child's shadow tree (text-overflow does not cross the shadow boundary). The value host is clipped (overflow hidden, nowrap) without an ellipsis; Text would need a truncate prop for this.
- Select: the `enter` binding asks for an opacity fade, but the Popover API top layer has no exit transition unless display/overlay are transitioned too. Implemented entry only (@starting-style), and closing is instant; the doc says 'enter', which this satisfies, but it does not say whether an exit fade is expected.
- Select: triggerBorderFocus says the danger border stays when invalid and focused, which the code does, but with focusRingWidth replacing triggerBorderWidth the padding calc() can go negative if a consumer overrides triggerBorderWidth above border.width.focus; the doc says 'clamped at zero' and CSS max() on a calc() of custom properties does the clamp, but the existing calc is unclamped. Left unclamped; flag for the doc to give the exact computed expression.

## 2026-09-21 13:32 — round 1

- Select: the composition block for `listbox` lists only the static props; `label`, `labelledBy`, `initialActiveValue` and the change/active handlers appear only in prose. Worse, on Lit `labelledBy` is inert — an IDREF cannot cross into ds-listbox's shadow root, and ds-listbox never renders the attribute anyway. I pass both, and the list is really named by `label`. The doc should either drop `labelledBy` for Lit or say it is parity-only.
- Select: `chevronReserve` is described as '`native: always` on web only', but Lit has the same native mode and the same chevron. I applied it on Lit for single selects and omitted it for `multiple`; the doc should widen the description or say the binding is a no-op on Lit.
- Select: the `keyboard` block has no rule for Space while the popup is open, yet the guidance says Space commits (single) or toggles (multiple) through Listbox's model. I forward Space to the Listbox and close for single — behavior that no keyboard rule or gate covers.
- Select: Enter with `multiple` is documented as 'Select toggles the active option' without saying where the toggled value lands in the array. I reproduced Listbox's `orderValues` (option order, unknown values appended) so Enter, Space and a click all produce the same array.
- Select: `disabled` wins over a controlled `open`, but the doc does not say what `aria-expanded` reports then. I report `false` and never show the popup, so the trigger never announces an expansion the user cannot see.
- Select: nothing in the doc says how a Lit story should own a controlled `open`. The Keyboard story must be open, but with `open` controlled the popup can never close, and focus stays on the trigger by design so the generated gate's `focusAt` finds zero focusables and presses keys at document.body — both keyboard rules failed. I made the story write `open-change` back onto the element (as React's story does with useState) and added a `play` that focuses the trigger.
- Select: 'Every forward carries the resolved token … not only a consumer override' means a document-level `--ds-select-font-family` / `--ds-select-helper-size` / `--ds-select-line-height` hook no longer reaches the composed Text, since the forward writes the child's own hook directly. I followed the doc; the root hooks still drive the trigger, the native `<select>` and the popup. Worth stating explicitly, because it makes the CSS escape hatch partial for those four bindings.
- Select: `copy.done` is declared and never rendered on Lit, per the notes. It sits in the COPY table unused — flagged here so a future reader does not 'fix' it.
- Select: `aria-controls` is 'present only while open' in the web notes but unqualified in the Lit notes, where the popup wrapper is always in the shadow root. I keep it always present; the two platform notes should agree.
- Select: `form.valueType` is `string[]`, but the guidance says a single select submits a string. setFormValue gets a string for single, a FormData for multiple and null when empty or disabled — the single `valueType` field cannot express that split.
- Select: the Lit notes require the long value to be clipped on the value host with no ellipsis, but no style binding covers the clipping. I wrote `overflow: hidden; white-space: nowrap` on the value part with no hook, so it is not overridable.
- Select: `focusRingWidth` specifies `max(0px, calc(...))`, which forces a `0px` literal past the literal gate (needs a `literal-ok` comment). Input's identical focus-ring rule has no clamp, so the two fields now differ; one of the two docs should change.
