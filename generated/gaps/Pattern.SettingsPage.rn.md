# Gaps reported while generating Pattern.SettingsPage for rn

Each entry is a place the doc made the generator guess. Fix the doc, re-run parse, regenerate.

## 2026-09-10 20:35 — round 1

- Appearance tab: SegmentedControl 'Color mode' and RadioGroup 'Layout density' are documented as changing the live theme mode/density, but the page rules forbid `useTheme()` and any theme/mode branching in the page itself, and RN's `ThemeProvider` exposes no mode setter through context (mode is only set by the prop from an ancestor, e.g. Storybook's `withTheme` decorator) — there is also no `density` concept anywhere in the `Theme`/`Tokens` type. Both controls are implemented as presentational, locally-stated controls with no actual effect; this is the page's biggest seam and needs either a theme-mode-setter API or a documented 'demo only' caveat.
- Delete-account Card: spec wrote `tone=danger?` as an open question against a Card prop that does not exist on `CardProps` (only `surface`/`inset`/`heading`/`headingLevel`/etc.) — left off per the 'leave it out' rule for open questions.
- AlertDialog: spec says 'whose cancel is the initial focus', but `AlertDialog` has no `initialFocus` prop (unlike `Dialog`'s `DialogInitialFocus`) and always moves initial accessibility focus to the title/heading once the enter animation completes; Cancel only precedes Confirm in reading order. Implemented as-is (title receives initial focus) since there's no supported way to focus Cancel first.
- AlertDialog's exact heading/description/confirm copy for the delete flow wasn't specified verbatim by the structure (only the trigger button and the fact that confirm is danger-toned) — used 'Delete account?' / 'This will permanently delete your account and everything in it. This cannot be undone.' / 'Delete account'.
- Toast 'region (bottom-end)': RN's `ToastProvider` renders one fixed, centered, bottom-of-screen region with no positioning options (no 'end' alignment) — the region is also an absolute overlay appended by the provider, not literally a sibling inside the page's own Stack as the structure diagram suggests. Mounted `ToastProvider` at the top of `SettingsPage` and call `toast()` from a child instead.
- Existing RN demo pages (ProfileSettings, Preferences, SignIn) all wrap their screen in a raw `View` styled via `useTheme()` for the page background — this pattern's rules explicitly forbid both `useTheme()` and any styled `View`/`style` prop in the page, so `SettingsPage` has no explicit background layer of its own; it relies on `withTheme()`'s decorator frame (or an app's own background) painting `colorBackground` behind it.
- Input has no built-in type-format validation (email/url) — only `required`/`invalid`/`error` precedence — so 'validates on submit (the Form contract: required, then type)' is only partially implemented: required-field validation fires, but no format check exists to fire for a malformed email/url without reimplementing validation logic outside the component (out of scope as business logic).
- Form's default `errorSummary` is `true`, which focuses the error summary rather than the first invalid field; set `errorSummary={false}` on the Profile form so it matches the spec's 'focuses the first invalid field' behavior exactly.

## 2026-09-16 13:14 — round 1

- Toast: the spec says the provider owns the region and no region is authored in the page, but on React Native `toast()` does nothing (it warns and never resolves) unless a `ToastProvider` is mounted, and the package's `withTheme()` decorator does not mount one. I left the provider out of the page (adopters have one at their app root) and added it as a story decorator inside `withTheme()`, which goes beyond 'the package's withTheme() decorator' alone. The pattern doc should say where the provider comes from on native, or withTheme should mount one.
- Card: the structure puts Text + Button (and Alert + Button) straight under Card, but RN Card's body View has no gap, so siblings would touch. I wrapped each body in `Stack gap=normal align=start`; the structure should name that Stack and its gap (the web page does the same thing). align=start keeps the Button from stretching to full width; the doc doesn't say whether actions in a Card body should stretch.
- TabPanel Notifications / Appearance / Account: each panel holds two sibling Fieldsets or Cards with no container named in the structure. I used `Stack gap=loose` to match the Profile form's field stack; the structure should name it.
- Appearance: the behaviors say 'the page says so' (the controls are presentational) but give no copy or component. I used Fieldset `description` with 'A preview only: the app sets the color mode, and System means no override.' and 'A preview only: the theme has no density setting yet.', the same copy as the React page. The spec should fix the copy.
- Form: the RN Form requires a `name`/`label` that the structure doesn't give. I set `name="profile"` and left out `label`, since there is only one form on the screen. Field `name`s (name, email, displayName, website, productUpdates, securityAlerts, tips, pushFrequency, density) are my choice; the structure gives none.
- Cancel: 'resets the form to its saved values' could also mean clearing validation errors. RN Form has no reset API, so Cancel only restores the controlled Input values; any error message already showing stays until the next validation.
- Checkbox / Switch / RadioGroup on the Notifications and Appearance tabs are outside any Form, so they are not saved or reset. The spec gives them no save path; I left them as local, uncontrolled or page-state controls.
- AlertDialog: the structure doesn't place it. It is a sibling after Container inside the main Landmark. Confirm only closes the dialog; the spec gives no follow-up (e.g. a Toast or navigation) for a confirmed delete, so none is faked.
- Landmark main + ScrollView: the only primitive allowed is ScrollView around the page, so it wraps the Landmark rather than the reverse. On native the Landmark is inside the scroll content, not the scroll container.

## 2026-09-17 16:56 — round 1

- Form: the structure lists Cancel before "Save changes" in the actions row, but Form's own `actions` contract says "at least one Button with type: submit, primary first (Form's action-order rule)". Followed the structure (Cancel first, Save second) and left the contract contradicted — the pattern doc and Form's `actions` prose need to agree on which wins for a settings form.
- RadioGroup/SegmentedControl: the spec gives option labels only (Immediately | Daily digest | Weekly digest, System | Light | Dark, Comfortable | Compact) and writes `defaultValue=Immediately`, but every option needs a `value`. Chose lowercase slugs ('immediately', 'daily', 'weekly', 'system', 'light', 'dark', 'comfortable', 'compact') matching the React and Lit pages, so `defaultValue="immediately"` is the slug, not the label.
- Tabs: the structure nests the tab labels on the panels (`TabPanel "Profile"`), but the RN API takes a `tabs: TabsItem[]` array of {id,label} plus one `TabPanel id=` per tab. Hoisted the four labels into a module-level SETTINGS_TABS constant and kept the ids the spec names. `fit` and `activation` are unspecified and left at their defaults, so on a phone the four tabs pack at the start rather than filling the width — `fit="fill"` is the likelier intent for a 4-tab settings screen and the doc should say.
- Switch: the spec says "controlled, so it can disable the RadioGroup" but names no event. RN's Switch fires `onValueChange` (web/React uses `onChange`), so the page reads differently from its React sibling; the pattern doc should name the behavior rather than a prop.
- ScrollView: "a ScrollView around the page" does not say whether the Landmark or the ScrollView is outermost, nor whether the AlertDialog (a sibling after Container, inside Landmark main) ends up inside the scroller. Put ScrollView outermost with Landmark main inside it; the AlertDialog is a Modal so being inside the scroller is inert, but on web/Lit the same tree means the dialog is a scroll child.
- Toast: the page raises `toast()` and the spec says the provider owns the region, but not who mounts `ToastProvider`. Mounted it in the story decorator (standing in for the app root) rather than in the page, since a pattern page an adopter copies should not create a second provider.
- Checkbox/RadioGroup names outside the Form: the Notifications and Appearance controls carry `name` props (productUpdates, securityAlerts, tips, pushFrequency, density) but sit outside any Form, and RN Form collection is the only consumer of `name`. They are inert here — kept for cross-platform parity with the spec, worth a note that a name outside a Form does nothing.
- Testability hook: the conventions require `testID="<Name>"` on a component root, but say nothing about pattern pages in `demo/`, and none of the existing RN demos carry one. Left the page without a testID; a pattern-level convention would make the axe/behavior gates able to target the screen.
- Alert inside the danger Card: `live` is unspecified. Left the default, since the alert is present when the panel mounts rather than appearing in response to an action — but the spec's own guidance ("off for alerts already present when the view loads") suggests `live="off"` is the correct value here.
- Fieldset gap: Fieldset renders its own Stack and takes a `gap`, which the structure never sets for any of the five Fieldsets, so all of them use the default. This is exactly one of the seams the Guidance asks about (legend vs. Card heading weight); the doc should state the intended Fieldset gap for a settings form instead of leaving it implicit.
