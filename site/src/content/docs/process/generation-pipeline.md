The first two tiers were generated by hand-spawned agents and a person triaging gap lists. `tools/generate.ts` makes that loop a command. The design principle is the one that made the manual runs work: the model is allowed to be creative in one place, writing the component, and everything after it is a hostile, deterministic check that either passes or hands the model a precise complaint.

## The loop

```
doc (site/src/content/docs/components/<name>.md)
  └─ tools/parse.ts ──► generated/prompts/<Name>.<platform>.md      (deterministic; sha256 = identity of the spec)
       └─ tools/generate.ts
            round 1: model writes packages/<pkg>/src/<Name>.*  (+ index.ts export)  and reports gaps as JSON
            gates:   tools/checks.ts → parse · contrast · literals · typecheck
            round 2..N: only if a gate failed — the model gets the failing output verbatim, nothing else
            └─ generated/generate.lock.json   hash, files, rounds, gate results, cost
               generated/gaps/<Name>.<platform>.md   every guess the model had to make
```

`generate.ts --check` lists targets whose prompt hash no longer matches the lockfile. `--stale` regenerates them. `--adopt` records hashes for code that already exists (how Tiers 0 and 1 were brought under the lockfile). The default runner drives Claude Code headless (`claude -p`, tools on, edits auto-accepted, cwd = the repo) so the model can read the package's conventions itself; `--runner api` calls the Messages API with the convention files inlined and parses files back out of the reply, for environments without the CLI.

## Why generation is not part of the build

Model output is not reproducible. A `pnpm build` that regenerated components would ship different code on every deploy and nobody could review it. So generation is a code-mod: run it when a doc changes, look at the diff, commit the result. The deploy build (`pnpm build`) never calls a model; it runs `pnpm check`, the token build, `lint:literals`, `generate:check` — which fails the build when a doc changed and its code was not regenerated — and the site build. The lockfile is what connects the two halves: a doc edit makes a target stale, CI refuses to ship until someone regenerates and commits, and the commit carries the hash that satisfied CI.

This also keeps humans in the loop in the right place. Generated files are ordinary source: Claude Code or a person can patch one by hand, and the next doc change will regenerate it (and the patch had better have been reflected in the doc, or the gap list will say so). The lockfile records `hash: null` for a target whose last run failed its gates, so it stays stale and visible rather than silently claiming success.

## The gates

Each gate is a process that exits 0 or does not; the model never sees the gate's code, only its output. Today:

**`parse`** — the docs still validate. A generator is told not to touch docs; this is how we know.
**`contrast`** — every declared pair, every theme and mode. Doc-level, but cheap, and it catches a regenerated theme.
**`literals`** — `tools/lint_literals.ts`: no hex, rgb, px, ms or font-stack literals in `packages/*/src`, no bare numbers on size properties in React Native styles, and no bare numbers inside the SwiftUI modifiers that take a dimension, color, duration or depth (`.padding(`, `.frame(`, `Color(`, `.font(.system(size:` and the rest) in `packages/swiftui/Sources/DesignSchema`. The visually-hidden clip pattern and `color-mix` of tokens are exempt; anything else needs a `literal-ok: <reason>` mark, which is a code-review flag by design.
**`typecheck`** — the package's real TypeScript typings (`pnpm --filter <pkg> typecheck`). Skippable with `--skip typecheck` where `node_modules` is not available.
**`swift-build` / `swift-test` / `swift-audit`** (`swiftui` only) — the same three things, run where SwiftUI compiles. `tools/swiftui_gate.ts` puts the generated file on a `gen/swiftui/<Name>` branch, dispatches `.github/workflows/swiftui-gates.yml` on a macOS runner and reads back `gates/<Name>.swiftui.json`; the failures reach the model as an ordinary fix round. Because a round trip is minutes, `--platform swiftui` generates a whole phase as one batch: every component's branch is pushed, then all of the runs are waited on together. See [iOS platform](/process/ios-platform/).

**`keyboard`** (opt-in, `--with keyboard`) — `tools/keyboard_tests.ts` reads every component's `keyboard` block and writes one Playwright spec per component and web platform into `generated/keyboard/`. A rule like `{ keys: [Tab], from: last, expect: focus-wraps-to-first }` becomes a test that opens the component's `Keyboard` story, puts focus where `from` says, presses the key, and asserts the `expect` — the root disappears, focus moved to the index it should, the trigger is focused, an aria state flipped. Rules marked `expect: manual` appear as skipped tests so coverage is visible. The walker crosses shadow roots, so Lit elements are tested the same way. Nobody writes a keyboard test per component; the doc is the test.
**`axe`** (opt-in, `--with axe`) — `tests/gates/axe.spec.ts` loads every story from each Storybook's `index.json` in light and dark mode and runs axe-core with the WCAG 2.2 AA tag set. A missing accessible name or a contrast failure axe can see fails here rather than in review.

Both browser gates need `pnpm install` (Playwright and `@axe-core/playwright` are dev dependencies) and `pnpm exec playwright install chromium` once; Playwright starts the three Storybooks itself or reuses running ones. Run them on committed code with `pnpm gates:keyboard` / `pnpm gates:axe`, or during generation with `pnpm generate --component Dialog --with keyboard --with axe`.

Still planned: a `package.json` diff that fails on a new dependency, and a visual diff of each story in both modes against the last committed run, so a regeneration that changes the look is a reviewed change rather than a surprise.

## What the model is told

The task prompt is short: a one-page conventions digest for the platform (`prompts/conventions/<platform>.md`, inlined — reading the package's exemplar files every run was about 40% of a generation's tokens, so the digest replaces them and the model may open at most `index.ts` and one component), then generate from the spec, add the export, compose existing components rather than re-implement them, and end with a JSON block listing files written and every gap. The spec is the generated prompt from `tools/parse.ts` — schema YAML, platform notes, guidance, the platform template's rules — unchanged, and only the judgment sections of the theme's feel skill follow it (the resolved token table is on disk and the literal gate enforces names). Fix rounds send only the failing gate output plus a reminder that the spec wins over the gate if they disagree (and that such a disagreement is a gap to report, because it means a check is wrong).

The gap list is still the most valuable output. `generated/gaps/` accumulates them per target and per round; the doc pass reads them, fixes the doc, re-parses, and the target is stale again — which is the loop closing.

## Running it

```
pnpm generate --component Icon                               # web, lit and rn
pnpm generate --component Icon --platform web
pnpm generate --component Button,Icon --platform swiftui     # iOS: one branch each, one CI round trip (needs gh)
pnpm generate --stale                                        # everything whose doc changed
pnpm generate:check                                          # CI mode: exit 1 if anything is stale
pnpm gates                                                   # run the gates on committed code, no model
```

`pnpm generate` runs `tools/parse.ts` first, so the prompts are fresh from the docs before any target is compared with the lockfile. On Windows, `generate.ps1 -Component/-Platform/-Stale/-Check` wraps the same commands and logs to `logs\generate.log`.

`DS_MODEL` or `--model` picks the model. The default is `sonnet`: a precise spec plus hard gates is the case where a cheaper model is enough, and the gates catch what it misses; use `--model fable` for the overlay components with the heaviest keyboard models. Measured on the first Icon run at Fable rates: $1.8–2.8 per target with one or two rounds; the digest and Sonnet together should bring that to roughly a fifth — a projection until the next run confirms it, which is why cost is in the lockfile. `--max-rounds` (default 3) bounds the fix loop; `--max-turns` bounds each round's agent. Cost per target is written to the lockfile so the price of a regeneration is visible in the diff.

## Full regeneration

`pnpm regen` regenerates the whole suite from the docs in composition order — Primitives → Core → Controls → Focus → Overlays → Selection → Numeric → Rows → Grids → Streams — so every component is generated after everything it composes. The order lives in `tools/regen-phases.json`. After each phase it commits, writes `generated/gaps/SUMMARY.md` (classified by `tools/gap_digest.ts`: DOC gaps first, with the doc they belong in), and stops with exit code 3. Fold the DOC gaps into the docs, run `pnpm parse`, and resume with `--from <next phase>`; only the components whose prompts changed are regenerated, so folding is cheap. `--phase <name>` runs exactly one phase. `--no-pause` runs straight through for a second pass. `--auto-fold` has Claude Code fold the gaps between phases instead of pausing, and exits 4 if the fold leaves the docs unparseable. `--dry-run` prints the plan and every command without calling anything. `--platform web|lit|rn|swiftui` runs one platform, and separate windows run the platforms in parallel once the lockfile is per platform (job 100); `--platform swiftui` spends CI wall-clock rather than dollars per round, one round trip per phase. On Windows, `regen.ps1` is the equivalent, with the same flags in PowerShell form (`-From`, `-Phase`, `-NoPause`, `-AutoFold`, `-DryRun`, `-Platform`). The per-phase commits go through `tools/commit.ts` and carry no attribution unless `DS_COMMIT_TRAILERS` or `git config ds.commitTrailer` sets trailer lines. A full first pass is roughly 150 targets, in the region of $150–250 on Sonnet, and 7 hours in parallel or 20 sequential; a second pass after folding costs a fraction because current targets are skipped by prompt hash and stale ones start from existing files.

Extensions (see [Extending components](/process/extending-components/)) are part of the prompt and the hash, so a regeneration after an owner adds custom props or modules is exactly as safe as one after a doc fix: the merged schema is the input, hand-written modules under `src/custom/` are never touched, and the `modules` gate proves they are wired.
