# Gaps reported while generating Pattern.SettingsPage for lit

Each entry is a place the doc made the generator guess. Fix the doc, re-run parse, regenerate.

## 2026-09-10 20:31 — round 1

- Card: schema has no `tone` prop (spec wrote `tone=danger?` as an open question), so I left it off the Delete-account Card and relied on the Alert already inside it to carry the danger signal.
- AlertDialog copy (heading/description/confirmLabel) was never given verbatim — the structure only said '→ AlertDialog'. I wrote on-brand copy: heading 'Delete your account?', description 'This permanently deletes your account and everything in it. This cannot be undone.', confirmLabel 'Delete account'.
- Toast tone for 'Changes saved' was unspecified; used the component default (neutral) rather than guessing 'success'.
- Density control: no token/attribute exists anywhere in the system for layout density (only color data-mode is documented). The Density RadioGroup is real and controlled but drives nothing — matching the guidance doc's own open question about layout.rhythm.
- 'System' color mode: the documented mechanism is only an explicit data-mode="dark"|(absent) toggle on <html>, no tri-state. Selecting System just removes the override, resolving to the documented light default rather than following the OS preference.
- Cancel/'reset to saved values': <ds-form> has no reset() and its internal shadow-root <form> does not own the slotted light-DOM fields (per Form.ts's own docs), so there is no native form.reset() to call as the React version used. I reset by hand: on Cancel, every <ds-input> under the profile <ds-form> has its `.value` set back to `undefined`. Since the spec gave no seed data, that returns fields to the same empty state they started in.
- The structure nested 'Stack horizontal gap=tight justify=end (Form's action row)' as a child of Form, but Form's real API takes the action row via a named `actions` slot, so I used `<ds-stack slot="actions">` instead of a trailing default-slot child.
- Set Form's `errorSummary` property to `false` (overriding the component default of `true`) so submission behavior matches the spec's literal wording 'focuses the first invalid field' rather than the default error-summary-gets-focus behavior.
- The structure's 'Toast region (bottom-end)' node is not rendered explicitly: Toast.ts documents `<ds-toast-region>` as auto-created in `document.body` by the `toast()` function and 'not meant to be authored directly', so the page just calls `toast({...})` on successful submit instead of composing a region element.

## 2026-09-16 13:12 — round 1

- Pattern.SettingsPage structure: the Notifications, Appearance and Account TabPanels each hold two siblings (Fieldset, Fieldset / Card, Card) with no Stack, but the Profile panel has an explicit `Stack gap=loose`. ds-tab-panel is display:block, so on Lit these siblings sit with no gap between them. I followed the structure exactly (no Stack). The doc should add `Stack gap=loose` to those three panels, or Tabs should own a gap between panel children.
- Pattern.SettingsPage / Card: each Card's body is Text + Button with no Stack. Card lays out body children as flex column items with `partGap` (layout.gap.loose) and stretch alignment, so the Button probably fills the width and sits a loose gap below the Text. I followed the structure. The doc should say whether a Card body needs its own `Stack gap=normal align=start`, or whether Card should align body children to start.
- Pattern.SettingsPage / Form: Form has no reset() and no reset event. Slotted ds-inputs are not associated with a native <form>, so formResetCallback never runs, and setting `value = undefined` does not clear an uncontrolled edit. To make Cancel 'reset to saved values' I made the four Inputs controlled (page state holds a saved copy and a draft). Form also keeps its internal `errors` after Cancel. The Form doc should define reset (a method or a `type=reset` Button).
- Pattern.SettingsPage / Input names: the structure gives no `name` on the Inputs, but Form keys values and errors by field name (empty names collide). I used name, email, displayName, website.
- Pattern.SettingsPage / Form: the structure writes `Form onSubmit` with no `name` or `label`. Form's doc says a label is required only when a page has more than one form. There is one here, so I set neither; the form landmark is unnamed.
- Pattern.SettingsPage Appearance: 'the page says so' (the controls drive nothing) has no visible copy in the structure. I said so only in a code comment. Add Fieldset `description` copy to the doc if it should be visible.
- Pattern.SettingsPage initial values: no default is given for Frequency, Color mode or Layout density. Frequency is left unselected, Color mode starts at 'system' (no override), and Layout density starts at 'comfortable'.
- Pattern.SettingsPage AlertDialog: the spec does not say what confirm does, so both confirm and cancel just close the dialog (no fake delete). AlertDialog is used but is not in the 'Components used' list.
- Pattern.SettingsPage Checkbox/Switch: the structure gives no names for the Notifications controls. They are outside any Form, so I left them unnamed and uncontrolled, except the Switch, which is controlled so it can disable the RadioGroup.
- Pattern.SettingsPage acceptance: Guidance asks for a story titled `Patterns/Settings`, but the output rules say `title: 'Patterns/SettingsPage'`. I kept 'Patterns/SettingsPage'.

## 2026-09-17 16:53 — round 1

- SettingsPage: the spec gives RadioGroup/SegmentedControl choices as labels only (Immediately | Daily digest | Weekly digest, System | Light | Dark, Comfortable | Compact), but RadioGroupOption/SegmentedControlOption require a distinct `value`. Chose slugged values (immediately/daily/weekly, system/light/dark, comfortable/compact); `defaultValue=Immediately` is written as a label, so it became `default-value="immediately"`. The doc should state option values, not just labels.
- SettingsPage: the frequency RadioGroup is specified `defaultValue=Immediately` (uncontrolled) while the Appearance controls are specified 'value starts at X' plus 'real, controlled inputs'. Read that literally: frequency uses `default-value` with no page state, Appearance uses controlled `.value` + change handlers. If all three were meant to be the same kind of control the doc should say so once.
- Switch: the spec asks for a controlled Switch ('controlled, so it can disable the RadioGroup'), but Lit's Switch has no controlled-value contract like Input's `value`/`defaultValue` pair — only `defaultChecked` plus a native-like live `checked` getter/setter. The element toggles itself first and then the page re-binds `.checked`, so it is synchronised, not controlled. A `checked`/`defaultChecked` pair matching Input's would remove the difference.
- Form: `<ds-form>` sets `role="form"` unconditionally, and the spec says this Form takes no label because it is the page's only form. That leaves a `role="form"` element with no accessible name in the a11y tree. Left it unlabelled per the spec, but the Form doc should say whether `role="form"` is dropped when there is no label/labelledBy.
- Tabs: the page sets `keep-mounted` as the spec requires, but on Lit the attribute is a no-op — Tabs never detaches panels, it only toggles `hidden`, so unsaved panel state is preserved with or without it. Kept for cross-platform parity; the doc should note that it is meaningless on Lit rather than a behaviour the page relies on.
- AlertDialog: no cancel label is given in the spec, so `cancel-label` is left off and the element's own default copy applies. The confirm label is specified verbatim; the cancel label should be too, or the doc should state that the default is intended.
- SettingsPage: the structure tree lists `Toast "Changes saved"` as a node inside the Tabs subtree, while the parenthetical says it is raised with `toast()` and no region is authored. Followed the parenthetical — nothing Toast-related appears in `render()`. The tree should not show Toast as a child at all, since it misreads as an authored element.
- SettingsPage: the three Notifications Checkboxes are given `name` (productUpdates, securityAlerts, tips) but sit outside any `<ds-form>`, so the names are inert — Form collects by `data-ds-field` within its own subtree. Set them anyway as specified; the doc should say whether those names are decorative or whether these controls were meant to be in a second Form.

## 2026-09-22 00:26 — round 1

- Pattern.SettingsPage: the "Components used" list omits Toast, but "Behaviors the page must show" requires a Toast "Changes saved" on submit. I added `import '../src/Toast.js'` and the `toast()` helper; the list should name Toast so a generator does not have to infer the import.
- Pattern.SettingsPage: the action row is specified as Button primary "Save changes" then Button secondary "Cancel" inside `Stack direction=horizontal justify=end`, which places the primary action to the LEFT of Cancel at the right edge — the opposite of the usual web order. I followed the doc verbatim (it matches the React file), but since this fixes both visual order and tab order it should be an explicit decision in the doc rather than an ordering that reads like an accident.
- Pattern.SettingsPage: the two RadioGroups are inconsistent and the doc gives no reason. pushFrequency is uncontrolled (`defaultValue=immediately`) while density is controlled page state ("value starts at comfortable"), even though both are page state that is never saved. I implemented both as written; the doc should either justify the split or make them the same.
- Pattern.SettingsPage: the doc names only the React prop for suppressing the error summary (`errorSummary={false}`). On Lit that prop defaults true, so it is the negated attribute `no-error-summary` — the doc should give the Lit spelling, since a generator that writes `error-summary="false"` gets a truthy boolean attribute and silently keeps the summary, defeating the "focus the first invalid field" behavior.
- Pattern.SettingsPage: `gap=normal` on all four Fieldsets is already Fieldset's default on Lit, so the structure's explicit value is a no-op. Harmless, but the doc should say whether it is deliberate emphasis or whether a Fieldset inside a TabPanel is meant to differ from the default.
- Pattern.SettingsPage: the doc does not say what `data-ds` a pattern page carries. The conventions fix `data-ds="<Name>"` for components; I kept the existing `data-ds="Pattern.SettingsPage"`, which matches the DS_GATE_COMPONENT target name the axe gate uses, but this should be stated so the three platforms agree.
- Pattern.SettingsPage: Cancel is specified to leave already-showing error messages until the next submit, but on Lit the Inputs own their error state and the page (which only restores the four controlled values) has no contract to clear it. The behavior falls out of the missing Form reset contract rather than being chosen; worth stating as a known consequence, or worth giving Form a reset.
