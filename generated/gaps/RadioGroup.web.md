## 2026-09-21 02:42 — round 1

- RadioGroup: the transition binding says the selected border color animates but 'invalid and focus border changes switch instantly' — on web the focus ring IS the border (focusRing replaces controlBorder), so one border-color transition cannot be both. CSS picks the transition from the destination state, so I cleared it on :focus-visible and --invalid: entering focus/invalid is instant as specified, but LEAVING focus fades the border color over `transition`. Unfixable in CSS without giving the focus ring its own element, which the binding forbids.
- RadioGroup: indicatorInset is listed as overridable with part: radioIndicator, but the web platform note says radioIndicator is a ::before pseudo-element with no node and therefore no hook. Overrides are defined as root hooks, so I put --ds-radio-group-indicator-inset on the root and had the ::before rule read it. Confirm that is the intended resolution for an overridable binding whose part is a pseudo-element.
- RadioGroup: a11y.requires lists arrow-navigation and roving-tabindex, which read as code to write, but the web platform note says native radios sharing a name already implement both and 'do not reimplement it'. I followed the platform note and wrote no key handling for arrows/Space/Tab, so the entire keyboard block is native on web. The two sections should agree, or a11y.requires should be marked platform-conditional.
- RadioGroup: the generator rule says a component with a keyboard block ships a Keyboard story with 'at least three focusable children', but a radio group is by definition ONE tab stop — only the selected (or first) radio is tabbable. The existing Keyboard story renders three radios, which is the most the pattern allows; the rule cannot be satisfied literally for radiogroup.
- RadioGroup: the spec says a disabled group puts preventDefault guards 'on the fieldset' for click, change and the arrow/Space keys. I kept the key guard on the fieldset but left the click guard on each input and the change guard in the option's own change handler — same effect and more precise (a fieldset-level click guard would also cancel clicks on unrelated content). Note that preventDefault on a bubbled `change` is inert anyway, since change is not cancelable and the state has already flipped; the early return is what actually suppresses onChange.
- RadioGroup: the spec says the whole option row is the hit area and that the row wrapper is not an anatomy part, but never says whether clicking an option's radioDescription selects that option. I chose yes (the row forwards clicks to the radio, skipping the input and its label, which already select natively). Worth stating explicitly since the description is a composed Text.
- RadioGroup: option ids are specified as `${groupId}-${value}`, but outside a Form the group id falls back to React's useId, which contains colons (`ds-radio-group:r1:`). Those ids are valid HTML5 and work in aria-describedby/label-for, but need escaping in querySelector/CSS. This matches Checkbox's existing house convention, so I left it; flagging in case the doc wants a colon-free id base.
