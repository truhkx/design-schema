# Gaps reported while generating Toolbar for lit

Each entry is a place the doc made the generator guess. Fix the doc, re-run parse, regenerate.

## 2026-09-10 12:53 — round 1

- Toolbar: anatomy lists `overflowButton` and `overflowMenu` as separate parts, but composition maps them both to Menu (which already composes its own Button trigger internally). I rendered a single composed `<ds-menu part="overflow">` that fulfills both anatomy entries — there is no separate CSS part for just the trigger button.
- Toolbar: the roving-tabindex/overflow candidate list is defined as every descendant carrying `data-ds` that is a direct child of the toolbar or one level inside a `<ds-toolbar-group>` (leaf controls are never descended into further). The doc's 'assigned elements' phrasing doesn't specify this recursion depth or how to avoid accidentally picking up a control's own slotted decorative children (e.g. an icon in a leading-icon slot); I chose 'stop descending at the first data-ds element' to avoid that.
- Toolbar: 'a control with its own arrow-key model keeps it — the toolbar hands the key to them when focus is inside' is only partly implemented. I skip the toolbar's own arrow handling entirely whenever focus is inside a SegmentedControl/RadioGroup or an open Menu, rather than detecting when focus is at that widget's edge pointing outward (which would require reaching into the composed child's internal state). So arrow keys never escape those widgets back into toolbar-level roving focus.
- Toolbar: `overflow: menu`'s collapse granularity operates on individual top-level controls (flattened across `ds-toolbar-group` wrappers), not whole groups as a unit — the doc's 'each control must provide overflowLabel' language doesn't say whether a group collapses atomically or its members collapse individually; I chose per-control so a partially-collapsed group is possible.
- Toolbar: the reserved width/height set aside for the overflow trigger before it's known to be needed is approximated from the `--size-target-min` token read via `getComputedStyle`, since the trigger isn't rendered yet at that point and there's no schema-specified reservation amount.
- Toolbar: `groupGap` ('either side of a separator') is forwarded to the auto-inserted Divider's own `--ds-divider-spacing` hook, which adds *additional* margin around it on top of the uniform flex `itemGap`/`itemGapCompact` already applied by the container — so the true visual gap around a separator is itemGap+groupGap, not exactly groupGap, since flexbox `gap` can't isolate one pair of children.
- Toolbar: `size` is documented as 'passed to the child controls that accept it' with no propagation algorithm given. I implemented it as a one-time default (a control without its own `size` attribute is given the toolbar's, once, when first observed) rather than a continuous sync, and later changes to the toolbar's `size` prop do not revisit already-defaulted children.
- Toolbar: `focusRing`/`focusRingWidth` are locked style bindings in the schema, but in this implementation the host itself is never given a tabindex (real focus always lands on a slotted control, each with its own focus ring) — added a defensive `:host(:focus-visible)` rule using these tokens that should never actually trigger in normal use.
- Toolbar: `ToolbarGroup` (`<ds-toolbar-group>`) is named only in the Lit platform notes, not as its own schema component with documented props/styles, so its layout (gap forwarding, `data-vertical` for orientation) is inferred rather than specified.

## 2026-09-10 18:56 — round 1

- Toolbar: overflow='menu' width budget reserves space for the 'More' trigger via a CSS var `--size-target-min` that doesn't exist in the tokens package, so it always resolves to 0; correctness is preserved by the ResizeObserver re-running recalcOverflow once the trigger becomes visible and shrinks .container, but this causes an extra reflow/possible one-frame overflow instead of reserving space up front. Spec doesn't define a token for 'reserve room for the overflow trigger', so left as-is rather than guessing one.
- Toolbar: overflowLabel is documented per-child-control but isn't a Toolbar prop itself; implementation reads a `overflow-label` attribute (falling back to `label` then textContent) off each collapsed child at runtime, which matches the platform note's intent but isn't spelled out as a contract in the schema.

## 2026-09-16 10:44 — round 1

- Toolbar: the web notes say collapsed controls are 'removed from the DOM, not just hidden', but the Lit notes say menu items call click() on the original slotted element; removing a consumer's light-DOM children would break frameworks that own them, so Lit hides them with `hidden` (marked data-ds-toolbar-collapsed) and leaves them out of the roving list.
- Toolbar: the overflow prop says collapsing 'takes whole entries from the end', but Guidance says 'Only Buttons collapse… collapses Buttons from the end first'. Chose: walk entries from the end and collapse an entry (a bare control or a whole group) only if all its controls are Buttons; fixed entries are skipped and stay, even when a Button entry before them collapses.
- Toolbar: `ToolbarGroup` is named as part of the API ('label for the group's accessible name, children') but has no props, anatomy detail or platform tag contract in the schema beyond the Lit note naming <ds-toolbar-group>; added a `label` property (aria-label, and the Menu group heading when collapsed). An unlabelled group becomes separator-delimited Menu items.
- Toolbar: 'a Divider is drawn between groups' doesn't say whether one goes between a group and a bare control; only adjacent ToolbarGroups get a separator.
- Toolbar: groupGap 'replaces itemGap' either side of a separator, but Divider has no toolbar-facing length or spacing contract; the separator length is set on the Divider host's block-size, and its spacing hook `--ds-divider-spacing` (with spacing=tight) becomes calc(groupGap - itemGap), which goes negative if an override makes groupGap smaller than itemGap.
- Toolbar: overflowButton is composed inside ds-menu (Menu renders its own trigger Button), so Toolbar cannot put data-part=overflowButton on it; only overflowMenu carries a data-part.
- Toolbar: the keyboard rules defer to a control that handles the arrow itself (defaultPrevented), and Guidance says the toolbar takes the arrow 'when focus is on the control's edge and the arrow points out'; ds-segmented-control calls preventDefault on every arrow, so focus can never leave a SegmentedControl by arrow key. SegmentedControl's doc needs an in-toolbar edge rule.
- Toolbar: the keyboard table doesn't say whether ArrowLeft/Right/Home/End are taken from a text-entry control (a Search or input in the toolbar, where they move the caret); the toolbar takes them unless the control prevented default.
- Toolbar: the overflow item label needs `overflow-label` ('must provide'), but there is no fallback rule; falls back to the `label` attribute, then text content, with a dev warning.
- Toolbar: the size doc says 'a child's own size wins', but ds-button/ds-select reflect their default size, so a child that rendered before the toolbar looked at it can't be told apart from one sized in markup; the toolbar only defaults children that have no size attribute when it discovers them.
- Toolbar: `focusRing`/`focusRingWidth` are locked and applied nowhere (per Guidance); hooks are declared on :host for consumer CSS only, and the old :host(:focus-visible) outline was removed since the host never takes focus.
- Toolbar: `children` in examples is a prose description ('Bold, Italic and Underline buttons'), not something a story arg can render; the stories take it as a `children` arg naming a preset template so each example's given is exactly its args.
- Toolbar: behavior scenarios horizontal-is-the-reported-orientation, vertical-toolbar-reports-its-orientation and the-toolbar-is-one-tab-stop are marked web-only, so they are not in Lit's scenario list and have no Lit test, though the Lit element sets aria-orientation and never takes focus itself.
- Toolbar: the scroll fade is a static mask on both edges; the doc doesn't say whether an edge fades only when there is content past it.

## 2026-09-17 13:22 — round 1

- Toolbar: styles.groupGap declares `part: group`, but its description applies it as padding on the separator wrapper (groupGap − itemGap); the declared part and where the binding takes effect disagree. Chose the description: the separator part carries it and ToolbarGroup does not read it.
- Toolbar: styles.separatorLength says the separator wrapper 'carries the part hook' but does not name the wrapper element or how Lit styles a light-DOM wrapper it inserts. Chose a light-DOM `<div data-ds-toolbar-separator data-part="separator">` styled from the toolbar's shadow root with `::slotted(...)`, with no `part` attribute.
- Toolbar: the fadeWidth description says 'a gradient from the toolbar background to transparent', while the web notes say 'masked edges' (mask-image). Chose a mask-image gradient: it fades the content into whatever is behind it without a second painted layer.
- Toolbar: fadeWidth describes horizontal scrolling only, but overflow says a vertical toolbar treats `menu` as `scroll`. Chose vertical scrolling for vertical `scroll`/`menu`, with the fades on the top and bottom edges.
- Toolbar: the compact-actions-with-overflow example says 'each with the same overflowLabel', which reads as either one shared string or an overflowLabel equal to each button's label. Chose overflow-label equal to each button's own label.
- Toolbar: the text-entry rule (an input, textarea or Search keeps ArrowLeft/ArrowRight/Home/End) does not list which input types count as text entry. Chose every input type except button, checkbox, color, file, hidden, image, radio, range, reset and submit, plus textarea and contenteditable, judged by the event's innermost composed-path target.
- Toolbar: the Lit notes say the roving list is 'rebuilt on slotchange', but a control added inside an existing ToolbarGroup is assigned to the group's slot and the toolbar's slotchange never fires. Kept a childList-only subtree MutationObserver instead.
- Toolbar: the Keyboard story needs at least three focusable children, but the spec does not say what Default's `children` are (only the examples have them). Default and Keyboard use two labelled groups of three ghost Buttons, so a separator shows.

## 2026-09-21 18:35 — round 1

- Toolbar: the lit notes require per-entry slots *and* that the toolbar 'never inserts nodes into the consumer's markup', but not how children reach those slots. Chose named slots plus a `slot="ds-toolbar-entry-<i>"` attribute written onto each top-level child — the only write into consumer markup left. Imperative assignment (`slotAssignment: 'manual'` + `slot.assign()`) would avoid even that; the doc should say which, since the attribute is visible in the consumer's DOM and manual assignment makes any unassigned child invisible.
- Toolbar: `container` is in the anatomy, but the root carries background/border/radius/padding while a separate inner element must be the scrollable, masked row. Two elements can claim the name; put the bindings on the host and `part/data-part="container"` on the inner row. The doc should say which one the part names.
- Toolbar: `generated/behavior/Toolbar.lit.test.ts` resolves its target with `deep(el.shadowRoot, '[role=toolbar]') ?? [part=container] ?? [data-part=container]`, so it asserts `aria-orientation` and the accessible name against a shadow element — but the Lit convention puts `role`/`aria-label`/`aria-orientation` on the host. Those 3 scenarios cannot pass without duplicating the role or adding attributes AT ignores; left them red (identical on HEAD's implementation) rather than gaming the matcher.
- Toolbar: 'the toolbar is one tab stop' is unreachable on Lit for anything but Buttons. Only `ds-button` mirrors its host `tabindex` to its inner control; `ds-select`, `ds-segmented-control`, `ds-search` and the overflow `ds-menu` trigger stay tab stops of their own whatever the toolbar writes, and reaching into their shadow roots is forbidden. Either those schemas grow a forwarded tabindex or the doc should state that Lit's roving model is arrow-navigation only for them.
- Toolbar: 'a child counts as sized when it has a `size` attribute at the moment the toolbar discovers it' collides with Lit's own reflection — every sized control reflects `size` with a default of `md`, so whether a child looks pre-sized depends on whether its first render beat the toolbar's discovery pass. Kept the doc's rule with a `data-ds-toolbar-size` ownership marker taken on first sight; it holds in practice but is a microtask-ordering race the doc does not acknowledge.
- Toolbar: `size` says only that Search has no `sm`. Encoded a per-tag accepted-size table (ds-button/ds-segmented-control/ds-select: sm+md; ds-search: md) rather than probing; a control that already has a toolbar-set size it no longer accepts has that attribute removed. Adding a `lg` toolbar size later needs this table edited by hand.
- Toolbar: 'any other wrapper makes what it holds one bare control' does not say what gets focus or what collapses. Chose the wrapper's first focusable descendant as the roving target, and made a wrapper never collapsible (only a bare `ds-button` or a group of them collapses), so a wrapper full of Buttons stays visible where the same Buttons unwrapped would fold.
- Toolbar: the overflow Menu needs an `id` per item, which the doc never defines, and the once-per-control missing-`overflow-label` warning is keyed 'by its entry, and its index inside a group'. Used `entry-<i>` / `entry-<i>-<j>` for both. That identity moves if the consumer reorders entries, so a reordered toolbar can warn twice about the same control.
- Toolbar: `groupGap − itemGap` 'clamped at 0' needs a zero-length literal in CSS. Used `max(0px, calc(…))`. Same wording as the web generator hit — the doc should either bless the zero literal or say to rely on the browser discarding a negative padding.
- Toolbar: reserving `size.target.min` for the More trigger 'before it is rendered' needs something measurable that is not the Menu. Rendered an invisible `span.target-probe` sized from `--size-target-min`, which is not in the anatomy and has no part; the doc should confirm structural elements outside the anatomy are allowed.
- Toolbar: nothing says what happens when collapsing cannot free enough width because a non-Button entry blocks the walk from the end. Chose to stop collapsing and let the row overflow the host rather than collapse a non-Button entry or fall back to scroll.
- Toolbar: none of the 13 behavior scenarios touches the separator, the collapse into the Menu, the edge fades or the roving focus — they are all attribute and render checks, so the whole distinctive half of this component ships untested by the doc's own suite. I verified those in a throwaway browser suite and deleted it; the doc should add scenarios for 'a separator is drawn between two adjacent groups', 'a narrow toolbar folds trailing Buttons into More' and 'arrows move, Home/End jump, neither wraps'.
- Toolbar: `focusRing` and `focusRingWidth` are locked bindings the guidance says Toolbar applies nowhere. Declared them as hooks on `:host` so the consumer-CSS escape hatch exists with no rule behind them — the overrides contract should state that a locked binding may have no rule.
- Toolbar: the Keyboard story's `overflow` is unspecified and the schema default `menu` can remove controls at a narrow gate viewport, leaving fewer than three focusable children. Pinned `overflow: wrap` (as web did). The Default/Keyboard children are specified only as 'two labelled ToolbarGroups of three ghost text Buttons each' with no labels; matched React's Text style (Bold, Italic, Underline) and Insert (Link, Image, Table) for story parity.
