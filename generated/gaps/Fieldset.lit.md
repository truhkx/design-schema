# Gaps reported while generating Fieldset for lit

Each entry is a place the doc made the generator guess. Fix the doc, re-run parse, regenerate.

## 2026-09-10 02:07 — round 1

- Fieldset: composition maps legend/description to Text and fields to Stack, but every existing Lit field composite (RadioGroup, Checkbox, Input) renders raw <legend>/<p> styled to the same tokens instead of instantiating ds-text, and the platform notes require fields to stay in the light DOM (ruling out wrapping them in a shadow ds-stack). Followed that precedent: raw elements for legend/description, and a plain flex '.fields' wrapper (gap from fieldsGap) around the default <slot> instead of a shadow <ds-stack>.
- Fieldset: the schema has no `required` prop, only a copy.requiredIndicator and the behavior note 'appended to the legend when every field inside is required'. Implemented as a computed getter that queries slotted ds-input/ds-checkbox/ds-switch/ds-radio-group and checks their `required` property at render time; it only recomputes on property changes and on the default slot's `slotchange`, not on ad-hoc mutation of a field's `required` property after connection (mirrors the same limitation ds-form's disabled-sync already accepts).
- Fieldset: `disabled` propagation targets ds-input, ds-checkbox, ds-switch and ds-radio-group (same set ds-form uses for its own fields), since the spec says 'every field inside' without enumerating tags; nested ds-fieldset was not included as a target since the spec doesn't mention fieldset-in-fieldset (and Related explicitly says RadioGroup already is a fieldset, implying no nesting).
- Fieldset: added `aria-disabled` on the shadow `<fieldset>` when `disabled` is set, matching the React/Web platform note ('disabled uses aria-disabled on the fieldset') even though the lit platform note doesn't repeat it and a11y.requires doesn't list a disabled-state item — kept for parity with Checkbox/RadioGroup's own aria-disabled pattern on their controls.
- Fieldset: the error region is always rendered (empty when unset, hidden via `.error:empty`) rather than conditionally, matching Checkbox/RadioGroup's pattern so a role=alert element persists in the DOM for screen readers to announce a later change — the schema doesn't specify which approach to use.

## 2026-09-10 20:58 — round 1

- Fieldset: the `gap` prop's own description says 'Fieldset renders the Stack itself; children are the raw fields,' and the `fieldsGap` binding says an override is 'forwarded to the Stack's own overrides.gap' — read literally, this means the fields wrapper must be an actual composed `<ds-stack>`, not a styled div. I composed `<ds-stack part="fields" gap=${this.gap} .overrides=${this.stackOverrides}>` around Fieldset's own `<slot>`, so the real slotted field elements flatten through into the Stack's flex container (verified in a real browser: assignedNodes({flatten:true}) resolves to the actual ds-input elements, and they lay out top-to-bottom via Stack's gap). This relies on a nested-slot flattening pattern with no existing precedent elsewhere in this package (Stack's shadow root uses slotAssignment:'manual', and its light-DOM child here is Fieldset's own passthrough `<slot>` rather than real content) — spec-compliant and verified, but worth a second look given it's a new composition shape for this codebase.
- Fieldset: legend/description compose plain native `<legend>`/`<p>` rather than `<ds-text>`, even though the schema's `composition` block maps `legend`/`description` to Text. The Lit-specific platform notes only describe a shadow `<fieldset><legend>` and never mention composing Text, and the only binding with an explicit forwarding instruction is `fieldsGap`→Stack, so I treated Text composition as optional there (matching how Alert.ts also renders its heading/body as plain elements rather than `<ds-text>`). If Text composition is actually required for legend/description too, `legendSize`/`legendWeight`/`helperSize` would need their own override-forwarding scheme, which the doc doesn't specify.

## 2026-09-16 05:31 — round 1

## 2026-09-21 04:04 — round 1

- Fieldset: the doc defines "a field" differently per platform without reconciling it. Web counts "any component element or a native input, select, textarea, button or fieldset", but the lit notes scope both `disabled` and the required indicator to direct children carrying `data-ds-field`. A slotted native `<input required>` therefore counts on web and does not on Lit, so the same markup shows the required indicator on one platform and not the other. I followed the lit note (data-ds-field only) and report the divergence.
- Fieldset: the `swiftui.props`/notes name a `legendLevel` prop ("Heading or Text per legendLevel") that does not exist in `props`. Nothing to implement on Lit — the legend is always a native <legend> — but the contradiction should be resolved in the doc (drop it, or add the prop for every platform).
- Fieldset: the doc names no state stories, so React invented `RequiredIndicator`, `WithError` and `Disabled` while the previous Lit generation used `AllFieldsRequired`, `ErrorSet` and `DisabledTrue` — a silent parity break that only the story-parity rule catches. I renamed Lit to match React. The doc should list the non-example stories it expects, as it lists the examples.
- Fieldset: the examples' `children` are prose ("An Input name=street label=Street and an Input name=city label=City"), not markup, so a story cannot pass them verbatim as args and also render real fields. I kept the prose string as the `children` arg and mapped it to a template fragment, which means arg parity with React (where `children` is a ReactNode array) is by name only. A `childrenMarkup`-style field, or slots declared per example, would let both platforms carry identical args.
- Fieldset: React's `NotificationPreferences` story uses `name=notifyEmail/notifySms/notifyPush` while the doc example says `name=email/sms/push`. I followed the doc, so the two platforms' notification example differs in field names.
- Fieldset: the doc says the error is "announced (inserting the role=alert region announces it)", which covers unset→set. It does not say what happens when `error` changes from one string to another: the wrapper already exists, so Lit re-renders the text in place and a screen reader may not re-announce. I left it as a plain re-render. If a second announcement is wanted, the doc should say the region is re-created on every change.
- Fieldset: the behavior scenario `a-disabled-group-is-marked-disabled` asserts `state: disabled is true` without naming the node. On Lit the host reflects the `disabled` attribute and the shadow `<fieldset>` carries `aria-disabled="true"`; I asserted it on the `group` part, matching the web note. Worth stating explicitly, since the host and the group part are different elements on Lit only.
- Fieldset: the platform rules say to set `delegatesFocus: true` on anything focusable, but Fieldset's shadow root contains nothing focusable — the fields are slotted light DOM, which `delegatesFocus` does not reach. Enabling it would make the host a focus target with no delegate, so I omitted it and Fieldset defines no `focus()`. `a11y.requires` lists no `focus-visible`, so I read this as intended; confirm the group is never meant to be a focus target.
- Fieldset: `gap` is listed under `platforms.lit.reflect`, but `fieldsGap` reaches the Stack only through `overrides.gap` and Fieldset itself has no rule keyed on `[gap=...]`. The reflected attribute styles nothing inside the component; it is useful only as an external selector. Harmless, but the reflect list usually implies an attribute selector exists.
