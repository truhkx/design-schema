# Gaps reported while generating Icon for rn

Each entry is a place the doc made the generator guess. Fix the doc, re-run parse, regenerate.

## 2026-09-09 18:16 — round 1

- Icon: the schema's props list has no `color`, but the RN platform notes and guidance say the parent passes a `color` prop and that it is required-by-convention. I added an optional `color?: string` prop with `color.foreground` as the fallback; the schema should declare it (at least as an RN-only prop) so it is not an invented prop.
- Icon: guidance says the inline font size is 'read from a TextNestingContext if present', but TextNestingContext is a boolean that only says whether the icon is nested, not what size the parent is. I rely on React Native's own nested-Text style inheritance instead: when `inline` and nested, no fontSize/fontFamily/color is set so the glyph inherits. When `inline` but not nested in a system Text (for example inside Button, whose icons sit in Views), there is nothing to inherit; I fall back to `font.size.md`. The spec should say what inline means outside running text.
- Icon: `color` fallback when nested. The spec says `color.foreground` is the fallback 'only when the icon has no colored ancestor'. On RN, a nested Text inherits color, so I apply the fallback only when not inheriting; otherwise a decorative check inside a colored Text would wrongly override the parent's color. Confirm this is the intended reading.
- Icon: the `strokeWidth` binding (`border.width.focus`) cannot be applied to a Text glyph. I did not approximate it with fontWeight, and documented the limit in the JSDoc. The schema should mark this binding as web/Lit-only or state the RN substitute.
- Icon: the `size` binding says 'width and height'. For a Text glyph I set fontSize, lineHeight, width and height to the token, with textAlign center and includeFontPadding false so the box is square and lines up in rows. Wide glyphs at small sizes may overflow the box; the spec does not say whether a square box or a natural text box is wanted.
- Icon: the Unicode table maps both `check` and `success` to ✓, so the 'four different status shapes' promise (circle-check for success) does not hold on RN. I used the table verbatim; the spec should either accept that or supply a distinct character (for example ✔ or ☑).
- Icon: `danger` is documented as octagon-x but the table gives ⨂ (circled times, U+2A02), and `search` is ⌕ (U+2315, telephone recorder), and the chevrons ⌄/⌃ are U+2304/U+2303 technical symbols. The guidance asserts all exist in the default iOS and Android system fonts, but I could not verify that; if any is missing on Android it will render as a tofu box. Consider documenting a verified fallback per glyph.
- Icon: `importantForAccessibility` for labelled icons is unspecified. I use `"auto"` when labelled and `"no"` when decorative, matching Button's decorative wrappers.
- Icon: `label=""` (empty string) is treated as no label, i.e. decorative. The spec does not say whether an empty label should be an error or decorative.
- Icon: the stories rule says one story per enum value plus Default. For the boolean `inline` and string `label` I added one story each (`Inline`, nested in Text; `Label`), since the naming rule only covers enums.
- Icon: `allowFontScaling` is not mentioned. I left it on so icons scale with the text they sit beside; Button's stories previously used `allowFontScaling={false}` for their placeholder glyphs, so the two disagree until Button is regenerated to use Icon.

## 2026-09-10 00:43 — round 1

- Icon: the schema's `platforms.rn.notes` (decision 2026-09-10) says the RN paths table must be 'byte-identical to the web table', but web's Icon.tsx has no `calendar` entry even though `calendar` is in the shared enum — no reference path exists on any platform yet. I invented a 16-grid line-glyph calendar (body rect + two hanger ticks + header divider) in packages/rn/src/paths.ts; web/Lit will draw a different shape unless regenerated from this same data, breaking the 'visually neutral swap' goal until then.
- Icon: `color`/size inheritance when `inline` is nested inside a system `Text` can't be implemented as literally as the doc implies. `TextNestingContext` (packages/rn/src/Text.tsx) is a plain boolean — it signals nesting but carries no font-size or color value — and Icon now renders `Svg`/`Path` (not `Text`), so there is no native Text-in-Text cascade to ride the way the retired Unicode-glyph implementation did. I fall back to `font.size.md`/`color.foreground` for inline icons whether or not they're nested in Text, same as the non-nested inline case. A true fix would mean threading the resolved size/color through `TextNestingContext` (or a new context) in Text.tsx, which is out of scope for this generation.
- Icon: `platforms.rn.props` lists only width/height/viewBox/fill/stroke/accessibility*, omitting `strokeWidth`, `fillRule`, `vectorEffect`, and `testID` even though the `styles.strokeWidth` binding, the filled-glyph fillRule note, and the package's testability-hook rule all require them. Treated the detailed prose notes as authoritative over the abbreviated props list and included all four.
- Icon: the `has-accessible-name` scenario has no `given` block, but Icon's default (from Icon.stories.tsx `Default`/`meta.args`) has no `label` and is therefore decorative with no accessible name — the generic derived scenario assumes a component always exposes one. Wrote the test with an explicit `label` (`'Warning: over quota'`, matching the existing `Label` story) instead of default args, since testing the true default would assert the opposite of the scenario's name.
- Icon: `react-native-svg` was already listed as a peer/dev dependency in packages/rn/package.json before this generation (no package.json change needed), even though the existing packages/rn/src/Icon.tsx being replaced still used a Unicode-glyph fallback with no SVG — the dependency addition and the component's actual adoption of it appear to have landed separately.

## 2026-09-16 01:41 — round 1

- Icon: `strokeWidth` is now locked, but packages/rn/src/Checkbox.tsx forwarded its own `indicatorStroke` override into Icon's `strokeWidth` — on RN there is no cascade to route it through as on web, so I removed the forward and Checkbox's `indicatorStroke` is now inert on this platform while staying in `CheckboxOverridableBinding`. Either the Checkbox doc drops `indicatorStroke` or Icon's `strokeWidth` has to unlock; Checkbox needs regenerating either way.
- Icon: the `color` prop description says the fallback to `color.foreground` is skipped whenever the icon is nested in a Text, while the `styles.color` description says the parent Text's TextStyleContext supplies the color only `when inline`. I followed the prop: nesting alone makes the glyph take the Text's color (an explicit `color` prop still wins, then `overrides.color`); `inline` only governs the size.
- Icon: `platforms.rn.props` lists `vectorEffect`, and `styles.strokeWidth` asks for a constant screen-pixel stroke at every size, but react-native-svg honors `vector-effect` only under react-native-web. Passing the raw token everywhere would make native strokes scale with the box (thin at xs, thick at xl), so I branch on `Platform.OS`: web gets the raw `border.width.focus` plus `vectorEffect`, native gets `borderWidthFocus * 16 / dimension` in grid units. The doc should state which platform does the scaling rather than leaving it to `where the platform honors it`.
- Icon: with `inline` and no enclosing Text the spec gives no size — the schema says `1em of the surrounding text` and the RN note says `otherwise font.size.md`. I used `font.size.md`, ignoring `size`, so `inline` stays a no-op for `size` in both cases; worth saying in the schema, since `inline` with `size="xl"` outside a Text silently renders md.
- Icon: the schema's rn props list has no `ref` and the platform conventions require any component exposing its root to declare one. Icon's root is react-native-svg's `Svg`, whose ref is a class-component instance rather than a `ViewInstance`, so I left `ref` off. If callers need to measure a glyph, the doc has to name the instance type to declare.
- Icon: the unknown-`name` fallback (empty Svg plus a `__DEV__` warning) is specified only in `platforms.web.notes`. I implemented it on RN too, since `name` is unvalidated at runtime for JS callers; the note belongs in the shared prose or in each platform's notes.
- Icon: the rn notes say inline icons `read the parent Text size through TextNestingContext`, but the package's Text exports `TextStyleContext` (resolved `fontSize`/`color`/`nested`) and the conventions call the same thing `TextNestingContext`. I used the real export; one of the two names should be corrected so the next regeneration does not invent a second context.
- Icon: the doc calls for baseline alignment for `inline` (web `vertical-align: -0.125em`, SwiftUI `.baselineOffset`) but names no RN mechanism. An `Svg` nested in RN `Text` is centered by the text renderer with no baseline control, so `inline` on this platform only matches the size and color — the glyph sits slightly higher than on web. Unimplementable as written; the doc should record it as a platform limit.
- Icon: `behavior.label-makes-the-icon-meaningful` asserts `role: img` and `aria-hidden: null` for web/lit only, leaving the rn expectation as just the accessible name. I also assert `accessibilityRole="image"` and `accessibilityElementsHidden === false` so the platform's half of `the aria-hidden of the decorative case is gone` is actually covered; the scenario should list an rn-platform `then`.
- Icon: `size` is declared `enumRef: size` with values xs–xl, and the `overrides` contract lets `overrides.size` be any `TokenRef` — including a non-numeric token. I cast the resolved value to `number` (as every other component in the package does); nothing in the schema constrains an override's token to the binding's own type.
