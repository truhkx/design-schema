Fix Dialog's broken behavior, reported by Tony 2026-09-15 ("did not work as expected"). Likely root cause found by source review of `Dialog.tsx` + `FocusScope.tsx` (not yet confirmed live — this repo's test runner was unreachable from the session that diagnosed it; run `pnpm --filter @design-schema/react test -- Dialog FocusScope` first to confirm before and after, and manually open/close a Dialog example to check focus visibly returns to its trigger).

**The mismatch.** `Dialog.tsx` moves focus into the dialog itself (first focusable element, or the title, or the close button per `initialFocus`) inside a `useLayoutEffect`. `FocusScope.tsx` (which `Dialog` renders as `<FocusScope trapped autoFocus="none" restoreFocus>`) records "the opener to restore focus to on close" — `document.activeElement` at mount — inside a plain `useEffect`.

React fires all of a tree's `useLayoutEffect`s (children before parents) before any of its `useEffect`s (also children before parents) fire. `Dialog`'s layout effect and `FocusScope`'s passive effect are not siblings — `FocusScope` is Dialog's child — but effect *type* orders across the whole tree, so Dialog's `useLayoutEffect` still fires before FocusScope's `useEffect`, regardless of the parent/child relationship, because layout effects (of every component) always run before passive effects (of every component). So by the time `FocusScope` reads `document.activeElement` to record the opener, Dialog has already moved focus *into* the dialog — `FocusScope` records an element inside itself as "the opener," not the real trigger button outside the dialog that the user actually clicked. On close, `restoreFocus` tries to refocus that wrong, likely-already-unmounted element, so focus does not return to the trigger — this is very plausibly what read as "broken."

**Fix:** move `FocusScope`'s opener-recording (and marker-insertion) logic from its `useEffect` into a `useLayoutEffect`. Because `FocusScope` is the child in every one of its composites (Dialog, AlertDialog, BottomSheet, ActionSheet, SidePanel, Menu, Popover — anywhere it's used), a child's layout effects fire before its parent's, so this ordering change guarantees `FocusScope` captures `document.activeElement` before the parent's own layout effect (Dialog's initial-focus move, or any composite's own layout-effect-driven focus change) has a chance to run. Keep everything else in that effect (the marker comment, the `autoFocus` handling) together in the same effect — only the effect type changes from `useEffect` to `useLayoutEffect`.

**Audit the other composites.** Every component that renders `<FocusScope restoreFocus ...>` and also does its own layout-effect-driven initial focus move (check AlertDialog, BottomSheet, ActionSheet, SidePanel at minimum) has the identical bug for the identical reason — this is a `FocusScope` fix, not a Dialog-only one, so nothing else needs a separate patch, but confirm each of those composites actually restores focus correctly after this change (test or manual check per component).
Gate: `pnpm --filter @design-schema/react test -- Dialog FocusScope AlertDialog BottomSheet ActionSheet SidePanel` passes; manually opening a Dialog example from a button and closing it (Escape, the close button, and a scrim click) returns focus to that exact button each time, not to the dialog's own contents or nowhere. Do not modify `packages/react/src/Dialog.tsx` for this — the bug and the fix both live in `FocusScope.tsx`, which is shared; changing Dialog itself is not needed and would leave the same bug in every other composite.
