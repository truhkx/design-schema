# Gaps reported while generating Dialog for web

Each entry is a place the doc made the generator guess. Fix the doc, re-run parse, regenerate.

## 2026-09-09 22:57 — round 1

- Dialog: the schema's composition names `footer: Stack`, but Stack's `gap` prop is a fixed `space.*` preset enum with no override hook, while the schema's `footerGap` binding is `layout.gap.tight` and is listed as overridable. There's no way to make an overridden `footerGap` actually reach Stack's internal gap without restyling it (disallowed). Chose `gap="1"` (space.1, 4px in calm-precise) as the closest visual match to the default token and declared the `--ds-dialog-footer-gap` hook on the root for override-surface completeness, but `overrides.footerGap` has no visible effect on the rendered footer today. Stack would need its own token/override escape hatch to close this gap.
- Dialog: composition doesn't name a component for `header` (only focusScope/title/description/closeButton/body/footer), so it's rendered as a plain div with its own `--ds-dialog-header-gap`/`--ds-dialog-inset` hooks, matching the Card precedent for uncomposed anatomy parts.
- Dialog: `inset` (padding of header, body, footer) is expressed three ways for consistency — header/footer read `--ds-dialog-inset` directly in CSS, body forwards the same override value into Box's own `overrides.paddingBlock/paddingInline` (Box already exposes exactly this hook). All three share the same default (`layout.inset.lg`) and the same override input, but through two different technical paths since Box owns its own padding.
- Dialog: the gap between the title and description inside the heading-group isn't named by any binding in `styles`; used `var(--layout-gap-tight)` directly (a valid token reference, but not an overridable hook), consistent with Card's header gap having no sub-token either.
- Dialog: `focusRing`/`focusRingWidth` are declared as locked tokens, but Dialog has no directly-focusable element of its own — the ring in practice comes from the composed Button (close button) and, for `initialFocus="title"`, a dedicated `:focus-visible` rule was added on the title heading since it's the one focus target Dialog itself introduces.
- Dialog: jsdom (used by the `tests` gate) implements the `open` IDL property on `HTMLDialogElement` but not `showModal()`/`close()` or the `cancel` event. The component calls the real methods via optional chaining (so nothing throws) and also assigns `dialog.open = true/false` as a fallback so the element isn't hidden by the UA `dialog:not([open])` rule under engines that lack `showModal()`; this assignment is a no-op in real browsers since `showModal()`/`close()` already reflect `open` themselves.
- Dialog: `container` (portal target) isn't in the schema's `props` table but is implied by the keyboard/overlay rule ("a `container` prop may override" the portal target) and needed for testability/embedding; added it as an optional prop defaulting to `document.body`.

## 2026-09-16 06:22 — round 1

- Dialog: the Controlled state section says `open` is uncontrolled when omitted, but the schema marks `open` required and says the consumer owns it; I kept it required and controlled only.
- Dialog: the derived scenarios `renders`, `renders-size-*` and `renders-initial-focus-*` give no `open` and expect `renders: true`, so the Default story must be open. I set `open: true` in meta.args, which means every story opens on load. The doc should say whether Default is open.
- Dialog: BottomSheet (wide mode) passes `className` and `style` into Dialog, but the package convention says the root never forwards them. Dialog keeps both in its prop type so BottomSheet still compiles, but ignores them. BottomSheet needs a pass to stop passing them.
- Dialog: `inset` (padding of header, body and footer) has no declared forward to the body Box, and the rules forbid adding forwards. The body Box gets no inset, and a Dialog-owned scroll wrapper around it reads `--ds-dialog-inset`. The doc should say whether `inset` forwards to Box `paddingBlock`/`paddingInline`.
- Dialog: the footerGap binding and the `--ds-dialog-footer-gap` hook don't agree. The value only reaches the Stack through `overrides.footerGap`, so setting the root hook from consumer CSS has no effect on the footer gap. The same goes for descriptionGap if the description ever moves into a composed Stack.
- Dialog: Heading, Button and Stack overwrite `data-part` with their own value (`text`/`container`), so the heading, closeButton and footer parts are Dialog-owned wrapper elements around those components (the heading wrapper also does the visual hiding and the focus ring via `:has(:focus-visible)`). - Dialog: `initialFocus: first` doesn't say what happens when the body has no focusable control. I fall back to the close button, then the heading; footer actions are never the initial target. Where the fallback lands on the heading, it gets tabindex -1 at that moment.
- Dialog: the web notes say to call `preventDefault()` on `cancel` 'when not dismissible', but the Guidance web section says 'always'. I always prevent it, since the consumer owns `open`. jsdom doesn't turn Escape into `cancel`, so Escape is handled on keydown, and a flag makes the browser's `cancel` for that same key report only once.

- Dialog: the `onOpened` 'after the open transition ends' rule has no case for when there is no transition (reduced motion, or no stylesheet as in jsdom). I fire it on the next frame when the surface's computed transition-duration is 0.
- Dialog: the example `given` values for children/footer are prose descriptions ('An email Input and a role Select'), not args, so the stories render my own content for them (field labels, plan names, the reading-dialog paragraphs). That text isn't from the doc's copy.
- Dialog: the md/lg widths are 'derived by the generator' from layout.maxWidth.content, but the doc gives no formula beyond '3/4'. I wrote `calc(var(--layout-max-width-content) * 3 / 4)`. Neither md nor lg has a hook, so only sm can be overridden.
