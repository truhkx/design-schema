# Gaps reported while generating Select for lit

Each entry is a place the doc made the generator guess. Fix the doc, re-run parse, regenerate.

## 2026-09-10 09:56 — round 1

- Select: the schema has no controlled `open`/`defaultOpen` prop (unlike sibling overlays Menu/Popover/Dialog, which all have one for exactly this purpose), so the Keyboard story can't declaratively render pre-opened; I used a `play` function that clicks the trigger's shadow-DOM button instead of inventing an `open` prop.
- Select: `aria-activedescendant` on the trigger's `role=combobox` button cannot correctly reference the active option, because the option lives inside `<ds-listbox>`'s own separate shadow root — plain ID refs don't cross shadow boundaries, and `ElementInternals.ariaActiveDescendantElement` only reflects for the internals-owning element itself, not into a composed child's shadow tree. I left it unset; the active option is only conveyed via focus staying on the trigger plus Listbox's own visual highlight, which is a real screen-reader gap for this exact composition (docstring hints it should 'work' but the platform doesn't support it as described).
- Select: `aria-controls` on the trigger points at Select's own `<div id="popup">` wrapper (same shadow root), not at the `role="listbox"` element itself, which is one shadow level deeper inside `<ds-listbox>` and unreachable by ID from the trigger's root — an approximation of the spec's `aria-controls={listboxId}`.
- Select: `<ds-listbox>` is itself `formAssociated = true`; composed inside `<ds-select>`'s shadow root it may independently try to associate with an ancestor `<form>` and call its own (empty-named) `setFormValue`. I left its `name` unset to minimize the chance of a stray form entry, but a real fix needs a 'not form-participating' composition mode on Listbox that isn't in its schema.
- Select: `<ds-form>`'s hardcoded `FIELD_SELECTOR`/`FIELD_TAGS` (Form.ts) don't include `ds-select`, so `<ds-form>` won't auto-collect/validate it even though it implements `DsFormField` — same known limitation already true of `<ds-listbox>`.
- Select: `DsFormField.currentValue` is typed `string | boolean | null`, but `multiple` makes Select's `currentValue` a `string[]` — same documented mismatch as Listbox; `<ds-form>` can't type-check this today.
- Select: the overridable `labelWeight`/`helperSize` hooks are exposed on the host per the contract, but they target the composed `<ds-text>` label/description, whose own `overrides` prop expects `TokenRef` token-path strings rather than resolved CSS-var strings — I couldn't bridge a hook's runtime value into that prop without inventing an unverified mapping, so these two hooks are currently inert (the label/description keep ds-text's own defaults) rather than restyling the child's shadow tree.
- Select: `popupSurface`/`popupBorder`/`popupShadow`/`popupRadius` style Select's own `.popup` wrapper, but the composed `<ds-listbox>` also draws its own border/background/radius inside it (Listbox has no borderless/surfaceless mode), producing minor nested 'double chrome' around the option list; not fixed via restyling the child, which the conventions disallow.
- Select: keyboard-model rows' `from: first`/`from: inside`/`from: trigger` fields have no defined semantics in the schema beyond grouping context; treated as descriptive metadata, not additional behavior to implement.
