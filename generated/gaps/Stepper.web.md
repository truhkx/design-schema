# Gaps reported while generating Stepper for web

Each entry is a place the doc made the generator guess. Fix the doc, re-run parse, regenerate.

## 2026-09-10 11:21 — round 1

- Button's API (`label: string`, no `children`, no `aria-label` override) can't host an indicator + label + description bundle or a visible label that differs from the accessible name. Resolved by: keeping the indicator outside the control entirely (it's aria-hidden anyway); using Button's `label` prop as both the visible text and accessible-name base for navigable steps; and putting the description and the visually-hidden status word as siblings after the control (inside a shared `.ds-stepper__content` wrapper) referenced from the Button via `aria-describedby`, instead of literally nesting them inside the control as the platform notes describe. Non-navigable steps (a plain `<div>`) do get the label nested directly, since a div has no such restriction — so the two branches aren't structurally identical, only equivalent in exposed accessible information.
- Web platform notes only mention a visually-hidden *status word* (copy.complete/current/error), not copy.stepLabel — unlike the RN notes, which build accessibilityLabel from copy.stepLabel. Since the web markup is a native `<ol>/<li>`, list position ('item 2 of 5') is already announced by the browser/AT for free, so copy.stepLabel is unused on this platform; only complete/current/error are rendered as hidden text.
- No style binding covers the indicator's default text color (current/upcoming states show a plain number) — only the complete/error foreground colors are bound. Used `color.foreground` directly (matches the a11y contrast pair for foreground/background) rather than inventing an unbound hook.
- labelColor/labelUpcomingColor/descriptionColor are locked bindings, but the label/description are rendered via the composed Text component, which owns its own color (`--ds-text-color`) via its `tone` prop. Rather than a real (but functionally inert) `--ds-stepper-label-color` root hook, tone is set directly (`default`/`muted`) to match those exact tokens — the same pattern ProgressBar uses for its composed Text colors. No root CSS hook exists for these three bindings.
- focusRing/focusRingWidth/minTarget are locked bindings satisfied entirely by the composed Button's own focus-visible outline and minimum target size; Stepper defines the corresponding root CSS variables for escape-hatch parity but doesn't apply them anywhere itself (the non-navigable `<div>` control does use minTarget directly since it has no Button to inherit sizing from).
- The `compact` prop and the auto container-query compacting hide non-current steps' label/description/control with the standard visually-hidden clip pattern (not `display:none`), so they stay screen-reader-reachable and keyboard-focusable even though visually clipped to 1px — a deliberate accessibility-over-visual-cleanliness choice the spec doesn't make explicit.

## 2026-09-10 19:01 — round 1

- Stepper (web): the spec contradicts itself on navigable steps — platforms.web.notes and the Guidance 'Platform notes > Web' both say the label/description are 'wrapped in a Button variant="ghost"', but the Behavior section says a navigable step is 'its own native <button> ... not the Button component, whose single-label API cannot hold an indicator, label and description'. Checked Button.tsx: it takes only `label: string`, no children slot, confirming the literal instruction is technically impossible. Resolved per the Behavior section — built a native `<button type="button">` (styled with the stepHover/stepRadius/focusRing bindings) wrapping indicator+label+description, matching the same own-native-button pattern Tabs.tsx already uses for its multi-part tab control.
- Stepper (web): copy.stepLabel ('Step {n}: {label}') plus the status word is used as `aria-label` only for navigable steps, per the Behavior section's specific wording. The doc doesn't say whether non-navigable (inert) steps get the same numbered prefix or should rely on the native <ol> ordinal announced by screen readers. Chose the latter for non-navigable steps (visible label + visually-hidden status word only) to avoid double-announcing the position.
- Stepper (web): 'compact applies to horizontal steppers only' (Behavior section) is enforced only via CSS scoping (`.ds-stepper--horizontal.ds-stepper--compact`); the `ds-stepper--compact` class is still applied when `orientation="vertical"` even though it has no visual effect there. The doc doesn't say whether the class itself should be suppressed in that case.
- Stepper (web): the previous generation of this file was missing the `stepHover` and `stepRadius` overridable bindings (present in the Overrides contract) and used `color: var(--color-foreground)` directly on the indicator instead of a dedicated `indicatorColor` hook; both are now added as CSS custom-property hooks per the styles/overrides sections.

## 2026-09-16 09:43 — round 1

- Stepper: the accessible name conflicts. Behavior says 'accessible name from copy.stepLabel plus the status word set as aria-label', then says web/Lit show the plain label and add only the status word as visually hidden text (native uses stepLabel). I followed the platform-specific sentence: no aria-label and no copy.stepLabel on web. So copy.stepLabel is unused on web, which conflicts with 'use every copy.* string'.

- Stepper: the Web section says label/description Texts are 'wrapped in a Button variant="ghost"', while Behavior and the navigable prop say a native <button> owned by Stepper, not Button. I used the native <button>.
- Stepper: the orientation description says 'Vertical shows descriptions under each label', which implies horizontal hides them. I render descriptions (and aria-describedby) only when vertical. The doc should say whether horizontal drops or clips them.
- Stepper: the doc never says when a connector counts as complete. I colour the connector after step i with connectorComplete when i is before current by position, ignoring explicit statuses.
- Stepper: the button needs inline padding and a gap to show the stepHover background, and no binding covers step padding. I reused partGap for both the indicator–label gap and the control's padding (plus block padding in vertical).
- Stepper: the indicator is a circle, but no binding names its radius. I used var(--radius-full) directly, which bypasses the hook rule.
- Stepper: labelColor, labelUpcomingColor, descriptionColor, labelWeight, labelCurrentWeight, labelSize and descriptionSize are bindings on composed Text parts. 'Rules always read the hook' can't apply without restyling Text, so they are Text tone/size/weight/overrides and have no --ds-stepper-* hook. - Stepper: `compact` is described as horizontal-only, but the doc doesn't place the 'Step n of m' text. The compact-shows-the-step-count scenario only checks text, so jsdom can't verify the container query.
- Stepper: when `current` matches no step id, nothing is current or navigable under `completed` and the count reads 'Step 1 of n'. The doc doesn't cover this case.
- Stepper: the Keyboard contract excludes the Tab rule, which is covered natively because non-navigable steps render as <div>. The Keyboard story uses navigable: all for four focusable steps; no `given` URL args were needed.

## 2026-09-21 16:31 — round 1

- Stepper: the doc says a vertical step's description `is aria-hidden there and referenced by the control's aria-describedby`, but a non-navigable step's control is a plain <div>, where aria-describedby is not exposed to AT and aria-hidden would drop the description from the accessibility tree entirely. Chose to hide-and-reference only inside the navigable <button> (whose accessible name is computed from content, which is the double-read the rule exists to prevent) and to leave the description exposed as ordinary text inside the <div>.
- Stepper: the connector centring formula `calc(stepPadding + (indicatorSize - connectorWidth) / 2)` from the step's edge contradicts stepPadding being `Inline padding of a step control (block padding too when vertical)` — in a horizontal stepper the cross-axis padding is 0, so the literal formula pushes the connector stepPadding below the indicator's centre line. Chose the cross-axis reading: `calc((indicatorSize - connectorWidth) / 2)` as margin-block-start horizontally, the full formula as margin-inline-start vertically.
- Stepper: `The count follows the list, stepGap after it` conflicts with the count being display:none outside compact, and with the rule that sibling spacing is never a margin. Chose to make the root a flex column with `gap: var(--ds-stepper-step-gap)`, so the gap collapses with the hidden count instead of leaving stepGap of dead space under every non-compact stepper.
- Stepper: minTarget's `part` is `step` (the <li>) but its description says `Minimum block and inline size of a navigable step control`, and stepPadding's note says minTarget styles `the control inside it`. Applied it to the navigable control only, so a display-only <div> no longer carries a 24px floor it is not a target for.
- Stepper: the generated behavior gate asserts `onStepSelect("shipping", expect.anything())`, a trailing event argument that events.onStepSelect.payload (only `id: string`) and the `exactly the listed arguments` contract forbid. Kept the single-argument call, so generated/behavior/Stepper.web.test.tsx fails 1/13. This is repo-wide, not Stepper-specific: Checkbox (6/16), Slider, Switch, Input, RadioGroup, SegmentedControl and Button fail the same assertion against single-argument handlers. Either web payloads should declare the originating event or tools/behavior_tests.ts should stop appending expect.anything().
- Stepper: `a11y.role: none` contradicts `platforms.web.element: nav` (role navigation), so the generated has-accessible-name test is skipped with `role 'none' cannot be queried; name the landmark/text role in the doc`. The hand-written test queries role navigation instead. The doc should name the landmark role.
- Stepper: with an explicit status the doc gives the status word to `status` and the selected state to position, so a step that is both the id match and `status: "upcoming"` renders aria-current="step" with no status word at all. Implemented literally; the doc only spells out the error + current combination.
- Stepper: when `current` matches no step nothing is selected, and the compact rule clips every non-selected step's content — so a compact stepper with an unmatched `current` shows the indicators and "Step 1 of m" but no visible label anywhere. The doc does not say which label compact reveals when nothing matches; left as the literal result.
- Stepper: indicatorFontSize is described as the check/danger Icons' `size` override while the composition also fixes `size="sm"` on them. The override token always wins over the prop, so `size="sm"` is decorative on those two Icons. Passed both as written.

## 2026-09-23 16:13 — round 2

- Stepper: labelColor, labelUpcomingColor, descriptionColor and countColor say 'no --ds-stepper-* hook' (realised by the composed Text's tone), but tools/check_hooks.ts only exempts bindings listed under composition forwards, not tone-realised ones, so it requires a hook for all four.
