# Gaps reported while generating Combobox for web

Each entry is a place the doc made the generator guess. Fix the doc, re-run parse, regenerate.

## 2026-09-10 10:13 — round 1

- Combobox: keyboard spec is internally contradictory — the Home/End entry's action text says 'Alt+ArrowDown/Up jump the list to first/last', but there's also a dedicated Alt+ArrowDown entry saying it 'opens the list without moving the active option'. Implemented the dedicated entry literally (Alt+ArrowDown just opens); did not implement an Alt+ArrowUp binding or a jump-to-first/last behavior for either, since no rule unambiguously specifies it.
- Combobox: 'keydown on the input is forwarded to the Listbox handler so DOM focus never leaves the input' is not literally achievable with Listbox's public API (no controllable active-option prop). Implemented it via dispatching a native, bubbling KeyboardEvent at the mounted Listbox root's DOM node (queued until mount if the popup just opened) — this drives Listbox's own internal active/selection logic exactly as a real keydown would, without moving DOM focus. Verified via type-check only, not manually in a browser.
- Combobox: 'opens the list with no active option' after each filtering keystroke is enforced by remounting the Listbox (via a `key` bump) on every keystroke for `filter` in startsWith/contains/async, since Listbox has no external reset hook for its internal active-option state. Skipped for `filter: none` (nothing is being filtered, so nothing to reset).
- Combobox: for `filter: none`, the spec says typing should 'only move the active option' (a typeahead-style jump-to-match). Not implemented — typing under `filter: none` currently only opens the list and does not relocate the active option; only ArrowDown/ArrowUp move it.
- Combobox: 'Clicking the toggle button opens the full list' is implemented as bypassing the current typed-text filter for that one open (a `forceFullList` flag, cleared on the next keystroke) rather than clearing the typed text itself, since the spec doesn't say the toggle should also clear input text.
- Combobox: chip label truncation ('~20 chars, ellipsis') is implemented via CSS `overflow`/`text-overflow: ellipsis` with no fixed character or width cap (none of the listed style bindings provide one), so truncation only kicks in once flex-wrap/shrink constrains a chip's width, not at a fixed 20-character point.
- Combobox: the custom-entry dedup check (suppressing `copy.addCustom` when typed text already matches an existing option) compares the trimmed, normalized text against both option `value` and `label`; the spec doesn't specify which field(s) to compare against.
- Combobox: initial `inputValue` text for an uncontrolled single-select with a `defaultValue`/`value` is derived by looking up the label from `options`; the schema doesn't say whether the input should show the label on mount versus staying empty until interaction.

## 2026-09-16 08:44 — round 1

- Combobox: the component rules say the ref goes on the root, but platforms.web.element is `input`; the ref is typed Ref<HTMLInputElement> and attached to the input, while data-ds sits on the wrapper div.
- Combobox: the web notes say to forward the input's keydown to `useListbox`'s handler, but the Listbox exports no hook and no controlled active-option prop. The active option is set by remounting Listbox with `initialActiveValue` plus a synthetic focusin, and ArrowUp/ArrowDown are re-dispatched as native keydown on the Listbox root. The Listbox schema could use a controlled `activeValue`.
- Combobox: the composed Button forces data-part="container", so the chipRemove/clearButton/toggleButton anatomy names live on a wrapping <span>, and the scenarios `click: chipRemove|clearButton|toggleButton` must target `[data-part=…] button`.
- Combobox: the scenario enter-commits-the-active-option (given only open: true, no typing) needs an active option, but the Behavior section only says typing opens with no active option. Chosen: typing opens with none; the toggle, an input click, the `open` prop and ArrowDown open with the selected option active, else the first; ArrowUp uses the selected option, else the last; Alt+ArrowDown uses the selected option or none.
- Combobox: `async` + `loading` with options present (the async-results example) — Listbox shows copy.loading only when it has no rows, and the RN notes route loading through the empty-message seam. Web passes an empty option list to Listbox while loading, so stale results are hidden and the loading row shows; the custom row is also hidden while loading.
- Combobox: the ',' key rule says a comma commits and clears the input, but after a single-select commit the input shows the label. With single + allowCustom, a comma commits like Enter: the input shows the committed text and the list closes.
- Combobox: onInputChange `fires: user` says every keystroke; it also fires when a commit, Escape or the clear button changes the text (so async consumers can reset), but not when a controlled value change rewrites the label.
- Combobox: copy.done (RN sheet footer) and copy.activeOption (SwiftUI announcement) have no web use; web relies on aria-activedescendant, so neither string is rendered.
- Combobox: the toggle button's tab order is not specified; it is tabIndex=-1 (APG: the input is the single tab stop), while the clear and chip-remove buttons stay tabbable. Keyboard story focusables are the options via activedescendant, as in Select.
- Combobox: labelWeight and helperSize have no part or have a Text part; they are forwarded to the label Text's `fontWeight` and to the description/error Text's `fontSize` overrides rather than written as root CSS hooks.
- Combobox: the web guidance says the field focus ring uses `:focus-within`, which would also light up while a chip-remove or clear button (with its own ring) has focus; used `:has(.ds-combobox__input:focus-visible)` so the field ring tracks the input only.
- Combobox: the `enter` binding (motion.duration.fast) has no description; it drives the popup's opacity fade-in (via @starting-style) and the field's border-color transition, both removed under reduced motion. The popup border width has no binding and uses border.width.thin directly.
- Combobox: the keyboard block marks Escape `when: list open`, but its action also describes the closed case; both are implemented (closed + clearable clears the text only, not the value).
- Combobox: pressing the already-selected option in single mode produces no Listbox onChange (Listbox skips same-value commits), so the popup detects that click itself to restore the label and close.
- Combobox: status copy for count 0 with the allowCustom row visible is unspecified; it announces copy.empty (the count excludes the synthetic row).

## 2026-09-17 11:56 — round 1

- Combobox: constant `statusDebounce` must come from the theme's standard `motion.duration.base`, 'never from a reduced-motion override that zeroes the token', but web has no way to read the non-reduced value at run time other than getComputedStyle of `--motion-duration-base`, which a reduced-motion media query would zero; kept the computed-style read (falls back to 0 when unreadable) — the doc should name a source for the unreduced value (a JS token export or a separate custom property).
- Combobox: allowCustom says text matching an option commits that option's value, but does not say what happens when the matching option is disabled; chose to commit nothing (no custom string, no option).
- Combobox: allowCustom + multiple where the typed text matches an already-selected option — Enter/comma is 'commit', not 'toggle'; chose to keep it selected (no onChange) and clear the text, unlike Enter on an active row, which toggles.
- Combobox: onInputChange fires for 'the text a commit, Escape-to-clear or the clear button leaves behind', but the doc does not say whether it fires when that text equals the text already in the input; chose to fire only on an actual change.
- Combobox: the `popupOffset` binding has no platform mechanism named for a position: fixed popup; applied as margin-block on the side the popup opened, which the 'spacing is never a margin' convention otherwise forbids.
- Combobox: `iconColor` is locked and 'forwarded to each composed Icon's own color override', but Icon's color override type needs a TokenRef cast from the binding's token; the locked binding therefore has no root hook and is written as the literal token path color.foreground.muted at each Icon.

## 2026-09-21 13:47 — round 1

- Combobox: the doc says a scenario `click` on chipRemove/clearButton/toggleButton 'presses the Button inside' but not how, and the generated harness clicks the wrapper <span> while the hand-written test clicks the <button>. Chose to put the handler on the wrapper span so both paths fire once (a disabled ds Button stops its own click, so `disabled` still blocks). This affects every component whose part wraps a composed Button, so it belongs in the shared web conventions, not just this doc.
- Combobox: the doc lists `aria-controls` unconditionally, but the popup only exists while open, so a closed combobox points at an id that is not in the DOM. Chose to always render it (APG); note that Select renders it only while open, so the two docs disagree. axe treats a dangling aria-controls IDREF as 'incomplete' rather than a violation, so neither choice fails the gate.
- Combobox: the doc never says whether an empty-string `error` means 'invalid with no message'. Chose Input's rule (empty message is not a message; a Form entry still marks the field) because the doc says validation is 'as Input'. The package is split on this today — Input/Select/Listbox/DatePicker/NumberInput treat '' as absent, Checkbox/RadioGroup/Slider do not — so the convention should be stated once rather than per component.
- Combobox: the Keyboard story is required to have 'at least three focusable children', but the APG model makes options non-focusable (activedescendant) and puts the toggle at tabIndex=-1. With `defaultValue: apple` the focusable children are the input, the clear Button and the tabIndex=-1 toggle Button. Whether the gate counts a tabIndex=-1 element, and whether activedescendant options are meant to count, is unstated.
- Combobox: with `filter: none`, the doc says typing does not filter and is type-ahead, and separately describes `copy.addCustom` as a synthetic first row, but never says whether that row appears when nothing is being filtered. Chose to show it — suppression depends only on the text matching an existing option, independent of `filter`.
- Combobox: the doc says 'the toggle button opens the full, unfiltered list for that opening' and separately lists 'a click in the input' among the openings that activate the selected option, else the first — but does not say whether a click in the input also drops the current filter. Chose to show the full list, matching the toggle.
- Combobox: `statusDebounce` says 'when it cannot be read (jsdom) there is no debounce'. Chose setTimeout(…, 0) rather than a synchronous update, so the announcement stays asynchronous and a test cannot observe it mid-render; 'no debounce' could also mean an immediate write.
- Combobox: Alt+ArrowDown 'does nothing while the list is already open', but the doc does not say whether the key's default action is still suppressed. Chose to preventDefault unconditionally on ArrowDown/ArrowUp so the caret never jumps, which means the key is not strictly a no-op when open.

## 2026-09-21 13:51 — round 2

- Combobox: the keyboard harness cannot focus this component. It takes `root = getByRole('combobox')`, which for the APG editable combobox is the <input> itself, then walks root's element *children* to find something to focus — an input has none, so focusAt() is a no-op, keys land on document.body and every `expect: closes` rule fails no matter what the component does. The generator rule 'a Keyboard story ships at least three focusable children' is unmeetable for any activedescendant composite whose root is the focusable element: the options are non-focusable by design and the clear/toggle Buttons are descendants of the wrapper, which the harness never looks at. Either the harness should fall back to focusing the root when it is itself focusable, or the rule needs an activedescendant carve-out.
- Combobox: the doc never says whether opening the list through the `open` prop (programmatic, stories, tests) should move DOM focus into the input. It only says focus 'never leaves the input' and 'stays in the input while the list is navigated', which describes user-driven openings. Chose to claim focus on open when focus is not already inside the field — required for aria-activedescendant to announce at all — but never stealing it from the clear or chip-remove Button. A consumer who opens the list programmatically without wanting focus moved has no way to opt out.
