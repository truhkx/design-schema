# Gaps reported while generating Toolbar for web

Each entry is a place the doc made the generator guess. Fix the doc, re-run parse, regenerate.

## 2026-09-10 12:56 — round 1

- overflow:menu says every control 'must provide overflowLabel', but no existing composed component (Button, SegmentedControl, Select, Switch) declares that prop, so it can't be passed without a TS error. actionFromElement() reads props.overflowLabel defensively at runtime and falls back to aria-label → label → string children → a generated id — works today only because Button/SegmentedControl expose `label`.
- Collapsed controls only regain real behavior in the overflow Menu if they expose onClick (e.g. Button). SegmentedControl/Select/Switch use onChange with a value argument Toolbar can't reconstruct, so if one of those overflows into the Menu, its row renders but activating it is a silent no-op. There's no guidance in the schema on how (or whether) stateful controls should overflow at all.
- Arrow-key hand-off to composite controls (SegmentedControl/RadioGroup) is implemented generically via `event.defaultPrevented` (Toolbar defers whenever an inner control already handled the key) rather than true edge-detection. In practice this means the whole Left/Right axis is permanently owned by a nested SegmentedControl (it never reaches an 'edge' since it wraps internally) — only the orthogonal Up/Down bubble to the Toolbar. Matches 'keep their own inner arrow keys' but not the more precise 'only when pointing out' wording.
- `size` is documented as 'passed to the child controls that accept it', but children are opaque ReactNode built by the consumer. Toolbar has no safe way to detect which child components accept `size` without importing every related component for identity checks, so it isn't forwarded — I only added a `ds-toolbar--size-{sm,md}` class (no current visual effect, since the schema's styles don't vary by size). Consumers must pass `size` to each child themselves.
- `ToolbarGroup` exists only in prose/notes, not in the schema's own anatomy/props. I invented its API (`label?`, `children`) as an exported sibling (mirroring `TabPanel`/`Tabs`); `label` doubles as its aria-label and its heading when it collapses into the overflow Menu — a guess with no schema backing.
- The `overflowButton` anatomy part has no dedicated data-part hook: it's Menu's own internal trigger Button, rendered by composition rather than by Toolbar directly. Only `overflowMenu` (the Menu root) carries a part hook.
- `focusRing`/`focusRingWidth` (locked) have no selector reading them in Toolbar.css — every focusable element belongs to a composed child that already owns its own focus ring, and restyling it would violate 'never restyle a child'. The hooks are declared on the root purely for the documented external-CSS escape hatch.
- overflow:menu measurement is a two-pass 'show everything, measure, then collapse' technique that fully remeasures on every resize (rather than incrementally); this can show a brief flash of all controls mid drag-resize in a real browser (usually invisible since React settles before paint). jsdom has no ResizeObserver, so tests only exercise the one-shot initial measurement — live resize reaction is unverified by the test suite.
- Density's itemGap/itemGapCompact only applies between controls inside a ToolbarGroup; a bare (ungrouped) top-level control is spaced from neighbors by groupGap instead, since the schema doesn't specify how grouped vs. ungrouped spacing should mix.
- Vertical-orientation behavior (Up/Down arrows, vertical scroll+mask direction) mirrors the horizontal implementation by construction but hasn't been visually verified in a real browser.

## 2026-09-10 19:09 — round 1

- Toolbar already existed complete and committed from a prior generation pass — no changes were needed; gaps below are carried over from inspecting that existing implementation.
- overflow: menu measurement: the spec says a ResizeObserver measures children and moves trailing ones into the Menu, but doesn't specify what happens when a group (not just a Button) would need to partially collapse — the implementation collapses whole trailing entries (controls or entire groups) rather than splitting a group, since 'Only Buttons collapse' but groups mix Buttons with non-collapsible controls; chose whole-entry-at-a-time collapsing from the end.
- overflowLabel is used for the Menu label lookup, but SegmentedControl/Select/Switch never collapse per spec — the code doesn't special-case those types, it relies on them being measured as fixed-width and naturally landing before the collapse boundary; if a toolbar is narrow enough that a non-Button control itself doesn't fit, there's no documented fallback, so it's left visible and may overflow the container.
- orientation: vertical with overflow: menu is not addressed by the spec (menu overflow implies a fixed cross-axis, wrap/scroll make more sense vertically) — implemented generically but not verified against a specific vertical+menu scenario in the doc.
- 'roving-tabindex'/'arrow-navigation' interaction with composite children (SegmentedControl) relies on the child calling preventDefault() on arrow keys it handles itself; this is an assumption about SegmentedControl's existing implementation rather than something re-verified here.

## 2026-09-16 10:38 — round 1

- Toolbar: `size` is 'applied by cloning direct children', but controls usually sit inside ToolbarGroup, which would leave them unsized; chose to also clone into ToolbarGroup's children. React cannot tell whether a component 'has a size prop', so size goes to every non-host element child without its own size (host elements are skipped).
- Toolbar: Guidance says a composite control keeps its arrows only until focus is on its edge and the arrow points out, but also says the toolbar acts only when the control did not preventDefault. SegmentedControl wraps and always prevents arrows/Home/End, so arrows can never leave it; followed the defaultPrevented rule and flag the mismatch.
- Toolbar: overflow menu items should 'reuse each control's overflowLabel/onPress', but React Button's handler is onClick(event: MouseEvent) and the collapsed button is gone from the DOM; the menu calls onClick(undefined), so a handler that reads the event will break. The label falls back to `label` when overflowLabel is missing, with no warning (the spec says 'must' but asks for no warning).
- Toolbar: anatomy lists overflowButton (Button) and overflowMenu (Menu) as separate parts, but Menu draws its own trigger Button; used Menu's trigger (ghost, iconOnly, triggerIcon ellipsis, label copy.more), so no element carries data-part="overflowButton" and Menu has no size prop to take the toolbar's size.
- Toolbar: groupGap is declared `part: group`, but its description puts it either side of a separator. Chose to set the hook on the root and apply it as padding on the separator part equal to groupGap minus itemGap (a negative result clamps to 0, so a groupGap smaller than itemGap has no effect).
- Toolbar: no Divider length prop or forwarded binding for separatorLength; applied it as the block-size (inline-size when vertical) of the separator wrapper with Divider stretching inside it.
- Toolbar: unlabelled ToolbarGroups that collapse have no Menu group heading (MenuGroup needs a string); they are separated from earlier items with a Menu separator.
- Toolbar: the roving list selector in Guidance ('button, [role=radio][aria-checked=true], select, input, [tabindex]') would drop tabindex-only controls once they are set to -1 and would include every native radio; narrowed it (checked native radio only, no hidden inputs, textarea added, [tabindex] only for non-native elements).
- Toolbar: behavior scenario `the-toolbar-is-one-tab-stop` asserts `focusable: false` on the root; the test also checks that exactly one descendant has tabIndex 0.
- Toolbar: example `given.children` are prose ('Bold, Italic and Underline buttons', 'A SegmentedControl and two Selects'); rendered them as ghost text Buttons (no bold/italic glyphs exist in icon-paths.json) and a SegmentedControl plus two Selects with invented option lists.

## 2026-09-17 13:18 — round 1

- Toolbar: the overflowLabel fallback chain ends in 'the Button's text content', but React Button has no children (label is required), so the chain stops at `label`.
- Toolbar: 'warn once per control' has no stable control identity in React (elements are recreated each render); keyed the warning by the toolbar entry key (group key + index for grouped Buttons), stored per Toolbar instance.
- Toolbar: example compact-actions-with-overflow says 'each with the same overflowLabel' — read as each Button's overflowLabel equal to its own label (identical labels on all four would make the Menu unusable).
- Toolbar: 'focusing a control scrolls it into view' is left to the browser's native focus scrolling; no explicit scrollIntoView call.
- Toolbar: edge-fade direction under RTL is not specified; the mask uses `to right` / `to bottom` and measures Math.abs(scrollLeft), so the start fade is drawn on the physical left in RTL.
- Toolbar: text-entry controls keep ArrowLeft/ArrowRight/Home/End, but the doc is silent on ArrowUp/ArrowDown from an input in a vertical toolbar; the toolbar still moves focus on those.
- Toolbar: which input types count as 'text-entry' is not listed; treated every input except button, checkbox, color, file, image, radio, range, reset and submit (plus textarea and contenteditable) as text entry.
- Toolbar: the overflowMenu hook — passed data-part="overflowMenu" through Menu's rest props, which land on Menu's root wrapper rather than its portaled popup; the doc does not say which Menu element carries the part.

## 2026-09-21 18:17 — round 1

- Toolbar: the overflowLabel fallback chain is specified as overflowLabel → Button label → text content, but on web Button's `label` is required and its children are not part of its API, so the chain cannot reach text content. Chose to end at `label`, with the internal entry id as a last resort that can only appear if a non-Button somehow enters the menu.
- Toolbar: `size` says Search has no `sm` but the doc never states which control identities accept which sizes. Encoded a per-component accepted-size table (Button/SegmentedControl/Select: sm+md; Search: md only) rather than probing props; adding a `lg` toolbar size later would need this table updated by hand.
- Toolbar: the doc does not say what happens when collapsing cannot free enough width because a non-Button entry blocks the walk from the end. Chose to stop collapsing and let the row clip (`overflow: hidden`) rather than collapse a non-Button entry or fall back to scroll.
- Toolbar: `groupGap` says the separator padding is `groupGap − itemGap` "clamped at 0", but a CSS clamp needs a zero-length literal. Used `max(0px, calc(…))` with a `literal-ok` comment; if the gate should instead rely on the browser discarding a negative padding, the doc should say so.
- Toolbar: the `Keyboard` story's `overflow` is unspecified, and the schema default `menu` can remove controls from the DOM at a narrow gate viewport, which would leave the keyboard gate with fewer than three focusable children. Pinned `overflow: wrap` on Keyboard while keeping the specified children.
- Toolbar: `overflow: menu` needs a per-entry measurement wrapper element and an invisible width probe for the reserved More trigger, neither of which is in the anatomy. Rendered them as `span.ds-toolbar__entry` and `span.ds-toolbar__reserve` with no `data-part`; the doc should confirm that extra structural elements outside the anatomy are allowed in this mode (the DOM shape then differs between `menu` and the other two overflow modes).
- Toolbar: focus is specified to enter on "the last-focused control, initially the first", but not what happens when that control is later removed — collapsed into the Menu, or unmounted by the consumer. Chose to fall back to the first non-disabled control.
- Toolbar: `focusRing` and `focusRingWidth` are locked bindings that the guidance says Toolbar applies nowhere. Declared them as hooks on the root so the consumer-CSS escape hatch exists, but no rule reads them — worth stating in the overrides contract that a locked binding may have no rule behind it.
- Toolbar: the overflow Menu needs an `id` per MenuAction, which the doc never defines. Derived ids from the entry key plus the index inside a group; these are also the identity used for the once-per-control missing-overflowLabel warning, which matches "its entry, and its index inside a group".
- Toolbar: the scroll fades are specified as re-checked "on scroll and on size changes", but jsdom has no ResizeObserver, so under Vitest the check only runs once on mount. No behavior scenario covers the fades, so this is untested on this platform — a browser repro would be needed to prove the edges toggle correctly.

## 2026-09-23 13:41 — round 1

- Toolbar: the fade must sit 'inside the toolbar's padding', which needs an inner scrolling element on web. The Lit notes put `data-part="container"` on that inner row; the web notes don't say where it goes. I kept `data-part="container"` on the role=toolbar root (the anatomy's container) and made the inner `ds-toolbar__row` an unnamed structural element, so web and Lit put the container hook on different elements.
- Toolbar: 'any other wrapper makes what it holds one bare control: the roving stop is the wrapper's first focusable descendant' doesn't say what happens to the wrapper's other focusable descendants. I leave them alone, so they stay tab stops of their own and a wrapper holding two Buttons breaks the one-tab-stop rule.
- Toolbar: a ToolbarGroup nested inside a group is said to take 'no separator and no size pass', but its roving behaviour isn't stated. I treat it like any other wrapper (one stop, its first focusable descendant).
- Toolbar: the spec has overflow Menu items reuse each control's `onPress` but also calls the collapsed Button's `onClick` with no argument. React Button has only `onClick`, so I call `onClick()`.
- Toolbar: the overflow Menu's trigger isn't named as a roving stop anywhere. I include it as the last entry's stop, since it is focusable and sits in the row.
- Toolbar: no behavior scenario covers menu collapse, the `entry-<i>` ids, the missing-overflowLabel warning, text-entry key pass-through or the scroll fade, and jsdom can't measure layout. These are only reachable in a browser gate, and no scenario asks for them.
