# Gaps reported while generating Popover for web

Each entry is a place the doc made the generator guess. Fix the doc, re-run parse, regenerate.

## 2026-09-10 02:57 — round 1

- platforms.web.element is 'div' but the a11y root the tests key off (data-ds) needed to be on an always-present wrapper, not the conditionally-portaled role=dialog panel — mirrored Menu.tsx's convention (wrapper div carries data-ds='Popover' and wraps the cloned trigger + portal) so `renders`/`has-accessible-name` scenarios pass even when closed; the panel itself carries only data-part='panel'.
- Notes say 'Modal: uses a native <dialog> with showModal()' but the attributes list also asks for explicit role=dialog/aria-modal on the same element set as non-modal. Followed the codebase precedent (Dialog.tsx/AlertDialog.tsx): native <dialog> for modal (gets inert-background and focus containment from the browser's top layer for free) with explicit role='dialog' aria-modal='true' added redundantly; a plain <div role='dialog' aria-modal='false'> for non-modal.
- 'Lock body scroll while open' is listed as a generic overlay rule, but Popover's own prop doc says non-modal 'the page stays interactive.' Scroll lock is applied only when modal=true; non-modal popovers never lock page scroll. Flagging in case the intent was scroll-lock always.
- Notes call for both a document pointerdown-outside listener and a focusout-to-outside listener for non-modal dismissal. Implemented only pointerdown-outside, because the explicit Tab/Shift+Tab handlers already own the keyboard-driven 'leaves the panel' cases, and a generic focusout listener firing alongside the manual focus-move in the Tab-out handler risked double `onOpenChange` calls for one interaction. A `closingRef` guard was added regardless as a safety net.
- No `headingLevel`/level prop exists on Popover (unlike Dialog which has a fixed level too). Hardcoded the heading to level 2, matching Dialog's own default, since a11y.requires doesn't list heading-hierarchy for Popover anyway.
- Arrow placement is centered on the panel's cross-axis edge (e.g. horizontally centered under the trigger for bottom/top placements) rather than tracking the trigger's actual center, since corner placements (bottom-start/bottom-end) don't guarantee the trigger sits under the panel's midpoint. Accurate for the four non-corner placements (top/bottom/start/end); a visual approximation for the four corner ones.
- The 'start'/'end' pure-side placements resolve left/right using the trigger's computed `direction` (RTL-aware), matching Tooltip's existing precedent; the four corner placements (bottom-start, etc.) stay physical left/right with no RTL awareness, matching Menu's existing precedent. The two families of placements are therefore inconsistent with each other on RTL, but each matches an established sibling component.
- trigger is typed as `ReactElement` (not the schema's generic `content`/ReactNode) since cloning it to inject aria-expanded/aria-controls/onClick/ref requires a single element — same tightening Tooltip already makes for its identical 'exactly one focusable element' wording.

## 2026-09-16 06:54 — round 1

- Popover: overlay.dismiss lists `focus-out` and the Web guidance says a `focusout` whose relatedTarget is outside closes, but platforms.web.notes says non-modal popovers use only the pointerdown-outside listener and have 'no focusout listener'. I followed the notes: there is no focusout handler, and the Tab/Shift+Tab handlers cover the keyboard exits.
- Popover: platforms.web.notes and the guidance say `FocusScope autoFocus="first"`, but Behavior says focus goes to 'the first control (or the heading, if there are none)'. With `dismissible` the close button comes first in the DOM, so autoFocus first would land on Close. I pass autoFocus="none" and focus the first tabbable element in the body, then the close button, then the heading (tabIndex -1), then the panel. The docs should say whether the close button counts as 'the first control'.
- Popover: the guidance says `restoreFocus` on FocusScope, but restoring when the scope unmounts would pull focus back to the trigger after an outside press (where focus should go to what was clicked) and after a forward tab-out (where it should go to the element after the trigger), and it only happens after the exit transition. I pass restoreFocus={false}. The component moves focus to the trigger as soon as `open` goes false, for trigger, escape and close-button closes only.
- Popover: the reason for Shift+Tab from the first element isn't specified. The only reason that fits is `tab-out`, whose description says 'Tab moved focus past the end', which is about forward Tab. I used `tab-out` for both directions.
- Popover: Tab from the last element is supposed to move focus 'to the element after the trigger', but nothing says what happens when the trigger is the last focusable element on the page. I focus the trigger without preventDefault, so the browser continues from there (to the browser chrome).
- Popover: the root/`data-ds` element is not defined for an overlay that renders nothing but its trigger while closed. platforms.web.element is the panel `div`, so `data-ds`, `ref` and the override hooks go on the panel, which only exists while open or closing. The derived `renders-*` scenarios run on the closed Default args, so the tests assert the trigger (`aria-expanded="false"`) and that no panel exists.
- Popover: `has-accessible-name` has no `given`, but the Default story is closed, so there is no dialog to name. The test opens the popover by clicking the trigger first, then checks that the dialog is named by the trigger ('Filters'). The scenario should give `open: true`.
- Popover: Modal uses a native `<dialog>` with `showModal()`, but closing it with `close()` removes it from the top layer and hides it immediately, so the `exit` transition can't run with JS alone. I used CSS `transition-behavior: allow-discrete` on display/overlay plus `@starting-style` for `enter`. Browsers without that support show and hide instantly. The component unmounts on transitionend/transitioncancel, or after a timer based on the computed duration.
- Popover: the `offset` binding has no stated mechanism. I apply it as a CSS margin on the side facing the trigger, reading the `--ds-popover-offset` hook, and the JS flip check reads the computed margin back. That keeps the value in the token instead of a number in JS. It is a margin, which the package's 'never a margin' rule reserves for sibling spacing. This is not sibling spacing, but the docs should confirm.
- Popover: the overlay block says `layer: popover`, but the `layer` style binding and the notes say `layer.dropdown`. I used `var(--layer-dropdown)` through the `--ds-popover-layer` hook.
- Popover: the arrow is centered on the panel edge and the enter slide comes from the trigger side. Both need a physical side, so `data-side` holds the resolved physical side (top/bottom/left/right, with `start`/`end` resolved from the trigger's direction) rather than a logical one. The docs never name the attribute.
- Popover: `inset` and `partGap` don't say which element they pad. The panel owns `inset` as padding, and `partGap` is the gap in the content column and in the header row. The body Box gets no inset, so no override needs forwarding to Box.
- Popover: modal scroll lock isn't specified. The notes only say non-modal never locks. A modal popover locks page scroll like Dialog (a class on <html>), and its native ::backdrop is transparent so the page isn't dimmed. The docs don't say whether a modal popover dims the page.
- Popover: example `date-picker-panel` needs 'A DatePicker calendar', but the package's DatePicker is a form field with its own popup; there is no standalone calendar, and nesting popups is disallowed. The DatePickerPanel story uses a date Button trigger with three quick-pick Buttons as a stand-in.
- Popover: example `contextual-help` needs an 'icon-only help Button', but IconName has no help/question glyph. I used `info`.
- Popover: the Keyboard rule for Tab has `given: modal: false`, and the gate expects 'closes', but a story with `open: true` and no handler can't close. The Keyboard story renders through a small wrapper that starts from `args.open` (default true) and keeps its own state. It still accepts `modal` from the story URL.

## 2026-09-21 07:54 — round 1

- Popover: the web notes say only the `heading` part is a popover-owned wrapper, but Button writes `data-part="container"` on its own root after the prop spread, so the `closeButton` part cannot sit on the Button either. Kept it on a wrapper span (as the Lit notes require and BottomSheet/SidePanel already do) and forwarded a click landing on the wrapper to the button, since the generated behavior gate clicks the part hook, not the button.
- Popover: the doc says example stories 'start from blank args', but Storybook always merges `meta.args`, and tools/behavior_tests.ts generates `{ ...meta.args, ...given }` — so meta cannot be emptied or the derived scenarios lose the required `trigger`/`children`. Chose to write every prop out explicitly at its schema default on each of the four example stories, and to put the open-wrapper on each non-example story's `render` rather than on meta.
- Popover: the doc names the enum stories but not the boolean state stories. Chose `Modal`, `WithArrow`, `NotDismissible`; a `<Prop><Value>` reading would give `ModalTrue`/`ShowArrowTrue`/`DismissibleFalse`.
- Popover: `collision: flip-shift` with nothing about the case where neither side fits. Chose to flip only when the opposite side fits, then clamp on the cross axis only — the main axis can overflow rather than the panel being squeezed or scrolled.
- Popover: the arrow is 'centered on the panel edge... an approximation for the four corner placements', but the approximation is not specified. Chose a plain 50% of the panel edge for all eight placements, so at `bottom-start`/`bottom-end` the arrow can sit away from the trigger; the alternative (clamping it toward the trigger centre) would need a JS pass the doc does not describe.
- Popover: 'focus returns to the trigger only if it is inside the panel at that moment' does not say what counts as inside once a modal <dialog>'s close() has already moved focus to <body>. - Popover: `modal` 'locks page scroll like Dialog' with no mechanism given. Chose an `html.ds-popover-lock-scroll { overflow: hidden }` class toggled by the component, with no scrollbar-gutter compensation, so a modal popover can shift layout by the scrollbar width.
- Popover: keyboard rule 3 says a modal popover 'wraps within the panel' on Tab. Implemented as not handling Tab at all when `modal`, leaving the wrap to FocusScope's trap — the doc does not say whether Popover should wrap itself when the panel has no tabbable children (there, focus simply stays put).
- Popover: `composition.closeButton.props.leadingIcon: close` is a glyph name, but web Button's `leadingIcon` is a ReactNode. Passed `<Icon name="close" inline />`; the schema value is the glyph, not the node.
- Popover: `container` (portal target) is required by the platform conventions for every portaled overlay but appears in neither the schema props nor the overlay block; added it as a documented platform-only prop that never affects semantics.
- Popover: the web notes state the trigger is the consumer's element, so nothing carries `data-part="trigger"`. The generated behavior helper's `trigger()` therefore falls back to the dialog element — the `escape-*` scenarios still pass because the key is dispatched inside the panel, but no scenario can actually target the trigger on this platform.
