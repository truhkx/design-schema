# Gaps reported while generating Feed for web

Each entry is a place the doc made the generator guess. Fix the doc, re-run parse, regenerate.

## 2026-09-10 16:52 — round 1

- Anatomy declares a distinct `articleHeader` part, but composing Card means the heading row is entirely Card's own internal `header` part (heading text only, no room for a timestamp); Feed exposes its own `articleBody` and `articleActions` wrapper divs with those data-part hooks, but has no `articleHeader` hook of its own — mirrors the same gap already reported for the Lit generation.
- copy.position ('{index} of {total}') is rendered as a visually-hidden span reinforcing aria-posinset/aria-setsize, but only when `hasMore` is false (total/setsize known); when `hasMore` is true, aria-setsize is -1 and the position text is omitted rather than showing '{index} of -1'. Not specified either way in the doc.
- No copy.* token covers relative-time text ('3 min ago'). Used `Intl.RelativeTimeFormat('en', { numeric: 'auto' })` (matching the sibling Lit generation's locale choice) instead of inventing English strings, since the rule against un-tokenized user-facing text has no alternative here.
- Card's root always sets `data-part="surface"` (hardcoded after its own prop spread) and has no focus-visible treatment for a non-interactive root that becomes programmatically focusable. Feed's own declared `focusRing`/`focusRingWidth` bindings are applied via a CSS selector reaching into the composed Card (`[data-ds="Card"]:focus-visible`), since inline styles can't express pseudo-classes — flagged as a place Card's schema might grow a 'focusable' variant rather than Feed reaching in.
- newItemsOffset ('space above the new-items button when it appears') is implemented as padding-block-start on the button's own sticky wrapper rather than a margin, since the button is always the first child (no prior sibling to space against) and the styling rules forbid margins between siblings.
- Ctrl+End when `hasMore` only fires `onLoadMore` and does not move focus ('first triggers a load so the end is real'); the doc doesn't say whether the user must press Ctrl+End again once loading finishes and `hasMore` becomes false — implemented as 'press again after it loads', matching the Lit generation.
- With zero items there is no article to attach the load-more IntersectionObserver to, so an empty feed with `hasMore: true` never self-triggers its first load — the caller must fetch the first page independently (before rendering Feed, or via its own effect). Not specified in the doc.
- endMessage has no declared inset/padding binding of its own, so the `loadingInset` hook is reused for both the loading indicator's and the end message's surrounding padding — matches the sibling React Native generation's same choice absent a dedicated token.

## 2026-09-10 19:25 — round 1

- Feed: `newItemsOffset` is padding-block-start on the sticky button row rather than a margin, per the spacing rule (no margins between siblings) — the doc's own note confirms this choice.
- Feed: the spec gives `loadingInset` and `endMessageInset` the same token (`layout.inset.md`) but separate overridable bindings; a prior pass had collapsed them into one shared CSS hook, silently making `endMessageInset` a no-op override — split into `--ds-feed-loading-inset` and `--ds-feed-end-message-inset` so both bindings are independently overridable as the schema requires.
- Feed: 'once on mount when items is empty and not loading' (fires onLoadMore for an empty feed's first page) was missing from a prior pass — no IntersectionObserver target exists with zero articles, so this is a plain mount effect guarded by a ref so it fires once per empty-to-populated transition, not on every render.
- Feed: no `copy.*` string covers relative timestamps ('3 min ago'); used `Intl.RelativeTimeFormat` (locale 'en') rather than inventing English copy, matching the interval boundaries the schema names (minute/hour/day/week) — same choice as the existing Lit generation.
- Feed: `aria-setsize` while `hasMore` is `-1` per the platform notes; the visually-hidden `copy.position` span is rendered only once the total is known (`hasMore` false), which the schema states explicitly.

## 2026-09-16 12:57 — round 1

- Feed: Card writes its own data-part="surface" after spreading rest props, so `data-part="article"` cannot sit on the article; it is on a Feed-owned wrapper div around each Card. The articleInset binding (part: article) is forwarded to Card's paddingBlock/paddingInline overrides, since Card's `inset` is an sm|md|lg enum rather than a token hook.
- Feed: Button also writes its own data-part, so `data-part="newItemsButton"` is on the sticky row that wraps the Button; a behavior test clicking the part must click the button inside it.
- Feed: Card has no unread prop and children must not be restyled, so the locked unreadBorder/unreadBorderWidth bar is a ::before on Feed's item wrapper, laid over the Card's start edge. The doc should say where the bar is drawn, or Card should grow a start-edge accent.
- Feed: the visually-hidden "unread" and position runs are plain <span>s with Feed's clip class. The web notes ask for a visually-hidden Text, but Text has no visually-hidden option.
- Feed: the doc gives no position for the "unread" word; it comes first in articleBody, then the timestamp, then the position run, then the content.
- Feed: `timestamp` is a composed Text, but Text only renders p|span, so a <time dateTime title> (carrying data-part="timestamp" and the aria-describedby id) sits inside a Text span with tone muted, size xs; timestampSize is forwarded to that Text's fontSize.
- Feed: onLoadMore's description says "End / Ctrl+End" but the keyboard table lists only Control+End; only Ctrl+End is implemented, per 'implement every key exactly as listed and nothing else'.
- Feed: when the empty state shows is underspecified with hasMore true and loading false (the moment before the first page is requested). copy.empty shows only when items are empty, not loading and hasMore is false, so an empty feed about to fetch stays blank rather than flashing 'Nothing here yet.'
- Feed: emptyState has no style bindings (no inset, color or size), so it is a default Text with no padding; only fontFamily is forwarded to it.
- Feed: the live-region requirement names no element. The new-items row is an always-rendered role=status (so the button's count is announced when it appears) with padding only while shown; the end message and loading indicator are not live, and aria-busy covers loading.
- Feed: fontFamily is both a root hook (--ds-feed-font-family, inherited by caller content) and forwarded to the composed Text (timestamp, end message, empty state) and Button overrides, since those set their own font family.
- Feed: onItemVisible fires once per item id per mount (the observer stops watching after it fires); the doc does not say whether an item that leaves and comes back should fire again.
- Feed: relative timestamps are computed at render and do not tick over time; the doc does not say whether 'just now' should refresh. Future timestamps are clamped to 'just now', and an unparseable timestamp renders as-is with no title.
- Feed: the absolute date formats are not specified; the fallback after 7 days uses Intl.DateTimeFormat(undefined, {dateStyle: 'medium'}) and the title uses {dateStyle: 'medium', timeStyle: 'short'}.
- Feed: the sticky new-items row needs a stacking layer the doc does not name; it uses var(--layer-raised) as DataGrid/TreeGrid do.
- Feed: after onShowNew, 'moves focus to the first new article' is implemented as focusing the new first Card once the first item's id changes, then scrollIntoView (smooth, or auto under reduced motion); the doc does not say what happens if the caller prepends nothing.
- Feed: the Keyboard story's `given` args and URL are not declared for Feed, so Keyboard is Default plus newItemsCount: 2 (a new-items button plus two article Buttons and a Link as focusable children).

## 2026-09-17 16:21 — round 1

- Feed: the generated behavior harness (generated/behavior/Feed.web.test.tsx) clicks the part element itself for `when.click: newItemsButton`, but Button writes its own data-part after {...rest}, so — exactly as the web notes say — the hook has to live on Feed's sticky row, and a click on the row never reaches the Button. `pressing-show-new-asks-for-the-newer-items` therefore fails in the generated gate while passing in Feed.test.tsx (which clicks the button inside the row, as the doc's own note describes). Pre-existing, not introduced here; I did not invent a click handler on the row to make it pass. Fix belongs in tools/behavior_tests.ts (click the first interactive descendant of a part) or in the doc's click target, not in the component.
- Feed: the web notes call out that Card and Button own their data-part, but Stack does too (`data-part="container"` after {...rest}), so `articleBody` and `articleActions` cannot be the Stacks themselves. Chose Feed-owned wrapper divs with `display: contents` carrying the part hooks, with the Stack inside; articleBodyGap stays the Stack's `gap="tight"` and its override is forwarded to `overrides.gap` as the binding says.
- Feed: keyboard model vs. reachability — Card `focusable` renders `tabindex="-1"`, and nothing in the spec puts an article into the Tab order, so PageDown/PageUp/Ctrl+Home/Ctrl+End (all gated on focus being inside an article) are unreachable by keyboard alone; only a click or screen-reader browse mode can land focus on an article. APG's feed pattern normally makes articles tabbable. Implemented as specified (tabindex -1, commands gated on `[role=article]`); the doc should say whether the first article takes `tabindex="0"`.
- Feed: Ctrl+End with `hasMore` and `loading` says "does nothing" without saying whether the key is still swallowed. Chose to preventDefault and do nothing, so a feed command never falls through to the browser's scroll-to-document-end mid-load.
- Feed: "asks at most once per change of `items`, `hasMore` or `loading`" — implemented as a flag inside the observer effect keyed on [lastId, hasMore, loading]. A change to `items` that leaves the last id unchanged (the prepend from onShowNew) does not re-arm the ask; the doc does not say whether it should.
- Feed: onShowNew focus handling — "focus moves to the first article once the first item's id changes; if nothing is prepended, focus stays on the button" gives no expiry for the pending request. As written the pending flag stays armed indefinitely, so a prepend from an unrelated later source would steal focus. Kept the spec's behavior; the doc should bound it (e.g. clear on the next render where `newItemsCount` is unchanged).
- Feed: the empty-label development warning is required by the `label` description but no wording is given. Chose "Feed: `label` is the accessible name of the feed and must not be empty.", warned once per mount, treating whitespace-only as empty.
- Feed: the empty state has three style bindings but no placement or liveness rule in the anatomy or web notes. Chose a Feed-owned wrapper (mirroring endMessage) inside the items column, not a live region — only the new-items row is role="status" and aria-busy covers loading.
- Feed: onItemVisible "once per item id per mount" is implemented with a Set that is never cleared, so an id removed and later re-added does not fire again. jsdom has no IntersectionObserver and no scenario covers it, so neither this nor the load-more observer is exercised by any test on this platform.

## 2026-09-21 23:32 — round 1

- Feed: the web notes contradict themselves on which element is the role="article". Paragraph 1 gives the Card role="article"/aria-posinset/aria-setsize/aria-describedby through rest props and says "Card labels itself by its heading"; the closing paragraph says the Feed-owned wrapper carries role="article" and "the Card inside it is the presentation". Kept it on the Card: the wrapper cannot reproduce the article's accessible name (Feed cannot put an id on Card's internal heading, and the attribute list names aria-labelledby, not aria-label), and a wrapper-as-article would make Feed own the focus target, contradicting focusRing/focusRingWidth being "child-owned... Feed has no focusable element of its own". The two statements have to be fixed together.
- Feed: the doc's diagnosis "axe reports aria-required-children when a wrapper sits between them" is wrong, so the rule it states is both too strict and too loose. Verified against axe-core 4.13 (aria-required-children-evaluate): a child with no role, no global aria attribute and no tabindex is descended through (a plain wrapper div around the Card is clean), while ANY child whose role is not `article` is reported as unallowed. The real HEAD failure was the always-rendered role="status" row being a child of role="feed". Unstated consequence: the loading indicator is a role="progressbar", so it cannot be inside the feed element either, though "a loading indicator is shown after the last article" reads as inside — rendered it as a sibling after the feed element, under "any other chrome stay outside it as siblings".
- Feed: an empty feed is itself an axe violation the doc does not address — `feed` is absent from axe's `reviewEmpty` list, so a role="feed" owning no article fails aria-required-children (critical) unless aria-busy is true, which would fail the Empty story on every run. Chose: the column carries role/aria-label/aria-busy when it has at least one article OR is `loading` (aria-busy is the sanctioned way to own nothing yet); with no items and not loading it is a plain container holding copy.empty, so an empty feed has no named feed region. The doc should say whether role="feed" is unconditional (accepting the violation) or drops as implemented.
- Feed: with role="feed" on the items column the doc no longer says which element is the `container` anatomy part — the feed column, or the Feed-owned outer shell that holds the live row and the loading indicator. Put data-part="container" on the role="feed" column; data-ds="Feed", the override hooks and the keydown handler stay on the shell.
- Feed: the Keyboard story can no longer show the new-items button. The generated keyboard gate walks focusables inside getByRole('feed') and asserts the first Tab lands on index 0, but the new-items row is now a sibling outside the feed element, so its button would be the first Tab stop in the document while sitting outside the walked set — the Tab test fails whenever it is present. Dropped `newItemsCount` from Keyboard (3 focusables remain: Reply, a Link, Download). The doc should declare Keyboard's `given`, and note that Ctrl+Home's new-items target is unreachable in that fixture.
- Feed: pre-existing and still red — the generated behavior harness clicks the part element for `when.click: newItemsButton`, but Button overwrites data-part after its rest spread, so the hook must sit on Feed's row and a click on the row never reaches the button. `pressing-show-new-asks-for-the-newer-items` fails in generated/behavior/Feed.web.test.tsx while passing in Feed.test.tsx (which clicks the button inside the row, as the notes describe). I did not add a row-level click handler to force it green: that would make the row's whitespace an activation target. Fix belongs in tools/behavior_tests.ts (click a part's first interactive descendant) or in the doc's click target.
- Feed: "the pending focus request lives until the next change of `items` and no further" does not say what counts as a change, and the literal reading (array identity) breaks the feature — every caller that renders a fresh array literal, including every story, would drop the request before the prepend lands. Keyed the request on the joined item ids, so it survives re-renders and expires on the first change of ids.
- Feed: the four feed commands are still unreachable by keyboard alone (reported in the 2026-09-17 round, unresolved). Articles are tabindex=-1 and nothing puts one in the tab order, so PageUp/PageDown/Ctrl+Home/Ctrl+End — all gated on focus being inside an article — can only be reached by pointer or a screen reader's browse mode, while APG's feed pattern normally makes the articles tabbable. The doc should say whether the first article takes tabindex="0".
