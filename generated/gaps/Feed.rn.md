# Gaps reported while generating Feed for rn

Each entry is a place the doc made the generator guess. Fix the doc, re-run parse, regenerate.

## 2026-09-10 16:48 — round 1

- Feed: composition names `ProgressBar` for loadingIndicator, but @design-schema/rn has no ProgressBar yet (only web/lit have it). Built a private `FeedLoadingIndicator` (indeterminate sliding-fill track, reduced-motion aware) as a stand-in; replace it once ProgressBar ships for RN.
- Feed: platform notes say each article is 'a Card with accessible and an accessibilityLabel from heading + relative time + unread', but Card has no accessible/accessibilityLabel prop, and collapsing the article into one accessible node (as `accessible` does on RN) would hide its action Buttons and any Link in `content` from individual focus. Chose to leave articles un-collapsed (each child keeps its own accessibility) and instead add visually-hidden Text runs for 'unread' and position — so no single composed accessible name exists per article on this platform.
- Feed keyboard model (Tab/PageDown/PageUp/Ctrl+Home/Ctrl+End) has no React Native hardware-keyboard equivalent — Views/FlatList don't receive Page or Ctrl key events on phones/tablets — so none of it is implemented; screen-reader users get the platform's native swipe/browse gestures instead, with no visible-control substitute added.
- Feed: the web spec exposes the absolute timestamp via `<time title>`; there's no native equivalent surfaced here (Card doesn't forward extra accessibility props, and adding a long-press tooltip would mean growing Card's own schema), so the absolute time is not exposed to sighted users or assistive tech on RN — only the relative string is shown.
- Feed: exact relative-time wording/thresholds beyond the one example ('3 min ago') aren't specified; implemented 'just now' (<60s), '{n} min ago' (<60m), '{n} hr ago' (<24h), else '{n} d ago' — a guess.
- Feed: `aria-posinset`/`aria-setsize` have no RN prop equivalent; substituted a hidden `copy.position` text per article, rendered only when `!hasMore` (total known), mirroring the web's `-1`/unknown sentinel by omitting the hint instead of showing an unbounded total.
- Feed: `newItemsOffset` ('space above the new-items button') was applied as the button row's own top padding since nothing render above the Feed by default; unclear whether the intent was a margin the surrounding layout should contribute instead.

## 2026-09-10 20:08 — round 1

- Feed: the hand-built loading-indicator stand-in referenced 'the not-yet-generated ProgressBar' — ProgressBar now exists in the package, so I swapped the footer to render it directly (indeterminate, visible copy.loading label) instead of the ad-hoc Animated track.
- Feed: styles.endMessageInset is a distinct overridable binding from loadingInset in the schema, but the prior implementation reused loadingInset for both the loading footer and the end message; I split them so endMessageInset actually resolves and overrides independently.
- Feed: hasMore's prop description requires firing onEndReached once on mount when items is empty and not loading (FlatList has no last row to observe in that case); this was missing, so I added a mount-only effect that fires it under that condition.
- Feed: endMessage's description says it only shows 'when hasMore is false (and items is not empty)' — the prior code showed it whenever !hasMore regardless of an empty list; added the items.length > 0 guard.
- Feed: the doc's Behavior section says 'while loading with no items the loading indicator shows, not copy.empty', but FlatList renders ListEmptyComponent and ListFooterComponent simultaneously when data is empty, so both would have appeared together; now ListEmptyComponent is suppressed while loading.
- Feed: anatomy lists articleBody, articleActions and timestamp as parts, but only container/article/loadingIndicator/endMessage/newItemsButton/emptyState carried testIDs; added Feed.timestamp/Feed.articleBody/Feed.articleActions wrappers (Text/Card don't expose a testID prop, so each needed a wrapping View, matching the pattern ProgressBar itself uses for its own label/value parts).
- Feed (native constraint, not fixed): the RN platform notes ask for copy.position 'after the heading', but Card only accepts a heading string and a footer slot — there's no injection point between them — so the hidden position/unread text stays a sibling before the Card, as it was already structured; flagging since it can't literally sit after the heading without growing Card's schema.
- Feed: the keyboard block (Tab/PageDown/PageUp/Ctrl+Home/Ctrl+End) is explicitly a web-only APG feed model per the doc's own RN platform notes ('no hardware-keyboard feed model on native'), so no Keyboard-specific interaction logic was implemented on this platform — the existing Keyboard story only exercises focusable children for the axe gate, not the key bindings themselves.

## 2026-09-16 13:03 — round 1

- Feed: the Guidance's React Native section says items are `Card`s with `accessible` and a composed `accessibilityLabel`, but platforms.rn.notes says Cards stay un-collapsed (no `accessible`) so the action Buttons and Links stay focusable; I followed the platform notes (the Declared contracts section says sections win) and the Guidance paragraph should be corrected.
- Feed: the examples and scenarios give `content` as a plain string, but React Native crashes on a bare string outside `Text`; Feed wraps string/number content in the package `Text`. The schema should say whether `content` strings are wrapped or must be nodes.
- Feed: no binding covers the space between the timestamp and the content in articleBody; I used `Stack gap="tight"` (the web Guidance's value for the actions row). Add an `articleBodyGap` binding or name the gap.
- Feed: emptyState has no inset or size binding (unlike endMessage and loadingIndicator); I rendered it as a muted `Text` with no padding. The schema should declare its inset, size and tone.
- Feed: the schema doesn't say whether `fontFamily` reaches the composed children; I passed it to every Text (timestamp, end message, empty state, hidden unread/position runs, string content) and to the new-items Button's `fontFamily` override, but not to Card's heading, because Card has no fontFamily binding.
- Feed: `articleInset` is 'passed to each Card as its inset', but Card's `inset` is an enum (sm/md/lg) and a TokenRef can't map onto it; the default uses `inset="md"` and an override goes to Card's `paddingBlock` and `paddingInline`.
- Feed: the relative-time thresholds don't say whether to round or floor, or what a future timestamp shows; I floor and clamp future times to `justNow`, and the absolute date uses `Intl.DateTimeFormat(undefined, { dateStyle: 'medium' })` because the date style isn't given.
- Feed: `onItemVisible` 'when it has been substantially visible for a moment' doesn't say whether it fires again when the item scrolls out and back; I fire on each transition to viewable (from `changed`), so the caller must be idempotent.
- Feed: `onLoadMore` 'once on mount' when empty doesn't say what happens if the caller later clears `items` to empty while `hasMore` stays true; I don't fire again, and the list's own `onEndReached` is ignored while items are empty, so that feed stalls until it gets new props.
- Feed: platforms.rn.props names `accessibilityRole=list` and the web feed is `aria-busy`; I set `accessibilityState.busy` from `loading`. The loading-marks-the-feed-busy scenario is web-only, so nothing tests busy on native.
- Feed: the convention puts `testID="Feed"` on the root, while the anatomy's `container` is the feed list itself; the outer View (holding the new-items button and the list) carries `Feed` and the FlatList carries `Feed.container`.
- Feed: the `Keyboard` story rule (open with its trigger and at least three focusable children) doesn't fit a feed, which has no open state; the story shows the new-items button plus the default items' Reply button and Open ticket link.
- Feed: `newItemsOffset` is 'padding-block-start of the sticky new-items row', but React Native has no sticky header outside the list; the button sits above the FlatList (per the platform notes) with `paddingTop`, so it never scrolls away. The schema doesn't say whether it should be inside the list as a sticky header instead.

## 2026-09-17 16:36 — round 1

- Feed: `newItemsLayer` is in the overridable list and its description scopes it to "web and Lit", while the rn notes put the new-items row above the FlatList as a sibling View, where nothing overlaps. Applied it as `zIndex` on the row so the override resolves to something, but it has no visual effect on native — either drop it from the rn overridable set or say it is inert there.
- Feed: the rn notes make the new-items row itself the `accessibilityLiveRegion="polite"`, but the row only mounts when `newItemsCount > 0`. A region that mounts together with its text is not reliably announced on Android — which is exactly why the web notes keep the role="status" row always rendered and pad it only while shown. Followed the rn notes as written; the reliable form would be an always-rendered row on native too.
- Feed: `onItemVisible` says "fires once per item id per mount" in the event description, but the rn notes describe only the raw `onViewableItemsChanged` with 50%/1s, which re-fires on re-entry. Implemented the once-per-id dedupe with a Set ref (event description wins) — the rn notes should say so.
- Feed: `onShowNew` says focus moves to the first article once the first item's id changes. Not implemented on native: Card's `focusable` is a react-native-web-only capability (no container can focus a View by script on iOS/Android), and `AccessibilityInfo.setAccessibilityFocus` would need a per-Card ref the spec does not ask for. The rn notes mention `maintainVisibleContentPosition` but say nothing about focus — they should state the focus move is web-only.
- Feed: `headingLevel` has no observable effect on rn. Card renders its heading at a fixed `size="lg"` and RN has no heading levels, so all three enum values render identically and the three derived `renders-heading-level-*` scenarios cannot distinguish them. Passed the level through to Card for parity and documented it as typography-only, which is itself inaccurate here — it controls nothing.
- Feed: `unreadBorder` is specified as a bar "drawn by that wrapper over the Card's start edge". On rn a border on the Feed-owned wrapper sits beside the Card, not over it — overlaying would need a negative offset (a literal the gate rejects) or absolute positioning. Drew `borderStartWidth`/`borderStartColor` on the wrapper, which shifts the Card inward by the bar's width instead of overlapping it.
- Feed: the entire `keyboard` block (PageDown, PageUp, Ctrl+End, Ctrl+Home) is unimplementable on native — no Page or Ctrl keys reach a FlatList, and the rn notes acknowledge it. The rule "a component with a keyboard block ships a story exported as Keyboard" still applies, so the story exists for the react-native-web axe gate only; none of the four rules is testable on this platform.
- Feed: no `emptyState` behaviour is defined for `items: []` with `hasMore: true` — guidance forbids `copy.empty` there and there is no article to show, so the feed renders an empty list with no placeholder at all while the first page is requested. Left it blank as specified; a `loading` companion state would avoid the dead screen.
- Feed: `items[].timestamp` says the absolute date is shown "from seven days" but lists `daysAgo` as "under seven days", leaving day 7 exactly to interpretation, and does not say whether the relative text should update. Used `elapsed < WEEK` for `daysAgo` and compute at render only (the doc says it does not tick), so an on-screen article's time goes stale until the next render.
