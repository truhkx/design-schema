## 2026-09-10 03:40 — round 1

- SidePanel: doc prop `title` renamed to `heading` for both the JS property and the attribute (not just mapped) to avoid colliding with `HTMLElement.title`, matching the existing precedent in Dialog.ts and BottomSheet.ts rather than keeping the doc's literal attribute name.
- SidePanel: `aria-controls` from the trigger to the panel is never set — the panel lives inside the shadow root and an id there can't be referenced by an IDREF from the light-DOM trigger, same limitation already accepted in Popover.ts. The panel is instead only named via `aria-labelledby` inside the shadow root.
- SidePanel: `swipeable` is exposed as a reflected boolean property/attribute for API parity but no swipe gesture is wired up on the web platform — the doc parenthesizes the swipe-to-open half as '(native only)' and the Lit platform notes don't describe a gesture handler (unlike BottomSheet's explicit pointer-drag implementation), so I left it inert on Lit and noted this rather than guessing at a touch implementation.
- SidePanel: copy.openLabel ('Open menu') has no natural home in the component itself since `trigger` is fully consumer-supplied slotted content (the component never renders its own trigger text) — I used it verbatim as the trigger button's label in the stories to satisfy 'use copy.* verbatim', but a real consumer would follow the guidance text ('Menu', 'Filters') instead.
- SidePanel: the example `<ds-icon name="menu">` from the platform notes can't be used — 'menu' is not in Icon's `IconName` union (packages/lit/src/Icon.ts). Stories render the trigger as a label-only button instead of guessing at a substitute glyph.
- SidePanel: 'A Link followed inside the panel closes it with reason navigation' is implemented as a click listener on the body wrapper checking for an `<a>` or `<ds-link>` in the composed path; the doc doesn't specify the exact detection heuristic (e.g. whether it should also cover a `<ds-button>` acting as a link), so this is a best-effort interpretation.
- SidePanel: safe-area padding is only applied via `env(safe-area-inset-bottom)` on the footer row (relevant since the panel is full-height); the web/React notes also mention `env(safe-area-inset-left)`/`-right`, but those are physical properties that don't map cleanly onto the `side`-based logical-property layout used here, and the Lit platform notes don't call safe-area out explicitly, so inline safe-area was left out.
- SidePanel: the non-modal scrim `<div>` shows/hides via the `hidden` attribute rather than crossfading; the modal path gets a real transition through the native `<dialog>::backdrop`, but doc doesn't specify whether the non-modal scrim should also fade, so I kept it simple.
- SidePanel: in persistent mode the landmark role is always `complementary` — the schema has no prop letting a Lit consumer choose `navigation` (the React version gets this via a `Landmark as="nav"` composition the schema doesn't expose here), so a navigation-heavy panel can't get the more specific role on this platform without an added prop.

## 2026-09-16 07:39 — round 1

- SidePanel: platforms.lit.notes says 'Shadow <dialog> for overlay mode' for both overlay modes, but the role prop says a modal panel is a dialog and a non-modal one is a landmark region, and ARIA in HTML allows no landmark role on <dialog>. I render non-modal as <aside>/<nav> with `hidden` and use <dialog> + showModal() only when modal. The Lit note should separate the two modes.
- SidePanel: the Lit note says persistent mode renders an <aside>, but landmark 'navigation' can't sit on <aside> (ARIA in HTML allows no navigation role there). I render <nav> for navigation and <aside> for complementary. The docs don't say whether Lit should compose ds-landmark as web does (composition doesn't list Landmark); I don't.
- SidePanel: dismiss by outside click has no reason value (the enum lists scrim but no 'outside'). A pointerdown outside a non-modal panel with no scrim (scrim: false) reports reason 'scrim'.
- SidePanel: reason 'action' ('a footer action asked to close') has no mechanism: no method, event or attribute lets a slotted footer control ask to close, and a light-DOM form method=dialog can't reach the shadow <dialog>. Only a native close() of the modal dialog maps to 'action'; the doc should name the mechanism (e.g. a close() method or a data attribute).
- SidePanel: copy.expanded ('Expanded') has no use on Lit: aria-expanded carries the state (Button's `expanded` property on a ds-button trigger, the attribute on any other element). It is only meaningful for SwiftUI's accessibilityValue; mark it platform-scoped.
- SidePanel: the doc has no defaultOpen, so open-at-start is only possible by controlling `open`; the stories and examples (cart, detail-panel) are therefore controlled and re-set `open` in an open-change listener. An uncontrolled panel always starts closed.
- SidePanel: scrim, modal and hideHeading are not in platforms.lit.reflect; I use attributes no-scrim (negated, since scrim defaults true), modal and hide-heading without reflecting them. The `role` prop is the `landmark` property/attribute (unreflected), per the doc.
- SidePanel: the keyboard block says Escape works 'from inside' while the web note says 'anywhere inside'; it is unclear whether Escape with focus on the slotted trigger (non-modal, focus stays there on open) should close. I only handle Escape from inside the surface, so Escape on the trigger does nothing.
- SidePanel: the parts section says composed parts receive 'exactly the listed props', but none are listed for heading/body/footer/closeButton. I chose ds-heading level 2 size lg, ds-box inset lg (the `inset` binding), ds-stack horizontal gap tight justify end, and ds-button ghost icon-only with a close ds-icon.
- SidePanel: the `partGap` and `inset` bindings have no part; I apply partGap as CSS gap on the focusScope column and inset as header/footer padding plus the body ds-box inset (override forwarded as paddingBlock/paddingInline).
- SidePanel: modal initial focus is 'the first control (or the title)' without saying whether footer controls count or whether the close button comes before body content. I pick the first focusable in the body slot, then the footer, then the close button, then the heading.
- SidePanel: the exit binding describes motion.easing.exit and enter uses motion.easing.standard, but neither easing is a style binding or overridable; hard-wired to those tokens. The scrim fade reuses enter/exit durations.
